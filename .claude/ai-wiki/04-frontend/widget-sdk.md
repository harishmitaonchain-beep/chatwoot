# Website Widget & Client SDK

## Purpose
This module is everything that runs on the *end customer's* side of a Chatwoot install, as opposed to the agent-facing dashboard. It has two distinct layers that talk to each other only through `window.postMessage`:

1. **`app/javascript/sdk/`** — the tiny embed script (`sdk.js` entrypoint) that a site owner pastes into their page (`window.chatwootSDK.run({ websiteToken, baseUrl })`). It owns the DOM outside the iframe: the floating bubble, the `<iframe>` element itself, injected CSS, cookies, and the public `window.$chatwoot` JS API (`toggle`, `setUser`, `setCustomAttributes`, `setLocale`, `setColorScheme`, `reset`, etc.) that host-page JS calls.
2. **`app/javascript/widget/`** — the full Vue 3 app that actually renders *inside* that iframe: the chat UI, pre-chat form, conversation view, campaigns, unread-messages popup, article/help-center viewer. It is server-rendered by `app/views/widgets/show.html.erb` (`Widgets::BaseController`/`WidgetsController`, outside the investigated paths) and mounted via `app/javascript/entrypoints/widget.js`.

The two layers are bridged by a hand-rolled string-based postMessage protocol (`chatwoot-widget:<json>`), not a formal RPC framework — every event name is a literal string matched in a big `if/else` chain or a lookup object.

## Key Files & Classes

### SDK (outside the iframe)
- `app/javascript/entrypoints/sdk.js` — the widget-embed entrypoint. Builds `window.$chatwoot` (settings + public API), reads `window.chatwootSettings` set by the host page, wires up Turbo/Turbolinks/Astro "before-render" listeners so SPA-style page swaps don't destroy the widget DOM (`restoreWidgetInDOM`), and calls `IFrameHelper.createFrame`.
- `app/javascript/sdk/IFrameHelper.js` — the core of the SDK side. `createFrame` builds and injects the `<iframe>` + bubble holder; `sendMessage`/`initPostMessageCommunication` implement the postMessage protocol; `IFrameHelper.events` is a lookup object of handlers for every message the widget iframe can send outward (`loaded`, `error`, `setAuthCookie`, `toggleBubble`, `popoutChatWindow`, `setUnreadMode`, `handleNotificationDot`, `set-color-scheme`, etc.).
- `app/javascript/sdk/sdk.js` — exports `SDK_CSS`, a large template-literal string of the bubble/iframe-holder CSS (z-index `2147483000`, flat vs. standard bubble styles, responsive breakpoints at 667px), injected via `<style id="cw-widget-styles">`.
- `app/javascript/sdk/bubbleHelpers.js` — builds the bubble DOM (SVG icon, expanded-bubble text node) and owns bubble open/close state transitions (`onBubbleClick`, `handleBubbleToggle`), dispatching `chatwoot:opened`/`chatwoot:closed` window events.
- `app/javascript/sdk/DOMHelpers.js` — low-level DOM class/CSS helpers plus `onLocationChangeListener`, a `MutationObserver`-based SPA route-change detector that notifies the iframe (`change-url` message) so campaigns can be triggered on URL match.
- `app/javascript/sdk/cookieHelpers.js` — `cw_conversation` / `cw_user_<websiteToken>` cookie naming and an MD5 hash (`computeHashForUserData`) used to dedupe repeated `setUser()` calls so they don't re-send identical identify calls.
- `app/javascript/sdk/settingsHelper.js` + `app/javascript/sdk/constants.js` — validate/clamp `type` (`BUBBLE_DESIGN`), `widgetStyle` (`WIDGET_DESIGN`), `darkMode` (`DARK_MODE: ['light','auto','dark']`) against small whitelists, falling back to the first (default) value for anything unrecognized.

### Widget app (inside the iframe)
- `app/javascript/entrypoints/widget.js` — mounts the Vue app (`App.vue`) with i18n, Vuex `store`, `router`, FormKit (for the pre-chat form's phone-number validation rules `startsWithPlus`/`isValidPhoneNumber`), and `vue3-click-away`; also instantiates `ActionCableConnector` on `window.onload`.
- `app/javascript/widget/App.vue` — the app root. On mount it distinguishes three embed contexts (`isIFrame`, `isRNWebView` for the React Native mobile SDK, or bare/non-embedded), reads `window.chatwootWebChannel` (the inbox config injected server-side), sets locale/widget color/dark-mode CSS var, and owns the giant `registerListeners()` handler that is the widget-side half of the postMessage protocol (`config-set`, `set-user`, `set-custom-attributes`, `set-label`, `toggle-open`, `set-color-scheme`, …).
- `app/javascript/widget/router.js` — `vue-router` with hash history; routes: `home`, `prechat-form`, `messages`, `article-viewer` (nested under `ViewWithHeader`), plus top-level `unread-messages` and `campaigns`. A global `beforeEach`/`afterEach` pair sets `appConfig/isUpdatingRoute` to block duplicate submits during navigation (references chatwoot/chatwoot#10736).
- `app/javascript/widget/helpers/actionCable.js` — `ActionCableConnector extends BaseActionCableConnector` (`app/javascript/shared/helpers/BaseActionCableConnector.js`). Subscribes to `message.created/updated`, `conversation.typing_on/off`, `conversation.status_changed`, `conversation.created`, `presence.update`, `contact.merged`; forwards `message.created` both into Vuex (`conversation/addOrUpdateMessage`) and out to the SDK/host page as the `chatwoot:on-message` custom event.
- `app/javascript/widget/store/` — Vuex modules: `agent`, `appConfig` (widget chrome/config state — position, color, dark mode, welcome copy, feature toggles), `contacts`, `conversation/` (actions/getters/mutations/helpers split into files), `conversationAttributes`, `conversationLabels`, `events`, `message`, `campaign`, `article`, plus the shared `globalConfig` module.
- `app/javascript/widget/api/` — one file per REST resource against `/api/v1/widget/*` (public, token-scoped endpoints — no agent auth): `conversation.js`, `message.js`, `agent.js`, `contacts.js`, `campaign.js`, `conversationLabels.js`, `article.js`, `integration.js`, `events.js`, with URL/param building centralized in `endPoints.js`. All requests go through `helpers/axios.js`'s `API` instance (`APP_BASE_URL = ''`, `withCredentials: false`), authenticated via `X-Auth-Token` header (`setHeader`) rather than cookies.
- `app/javascript/widget/composables/useDarkMode.js` — resolves the widget's effective dark/light state: `auto` reads `window.matchMedia('(prefers-color-scheme: dark)')`, otherwise it's a direct `light`/`dark` toggle driven by the `appConfig/darkMode` Vuex getter (itself set from `chatwootSettings.darkMode` via the SDK, or via `window.$chatwoot.setColorScheme()`).
- `app/javascript/widget/composables/useAvailability.js` + `helpers/availabilityHelpers.js` — business-hours/online-agent computation (`isOnline`, `isInWorkingHours`) driven by `window.chatwootWebChannel.workingHours`/`workingHoursEnabled`/`timezone`/`utcOffset`, consumed by `Availability/AvailabilityText.vue` and the pre-chat/home screens.
- `app/javascript/widget/mixins/configMixin.js` — a small computed-properties mixin read by many components, exposing feature flags off `window.chatwootWebChannel.enabledFeatures` (`emoji_picker`, `attachments`, `end_conversation`, `use_inbox_avatar_for_bot`) and derived pre-chat-form state (`shouldShowPreChatForm` — true only if pre-chat is enabled **and** at least one field is enabled).
- `app/javascript/widget/components/PreChat/Form.vue` — the pre-chat form UI, built on `@formkit/vue` with a custom `PhoneInput` input type; validates against `preChatFormOptions.pre_chat_fields` from the server config.
- `app/javascript/widget/helpers/campaignHelper.js` / `campaignTimer.js` + `store/modules/campaign.js` — client-side campaign-trigger logic (URL matching, delay timer) that decides when to auto-pop the campaign view; snoozing is cookie-based (`cw_snooze_campaigns_till`, set by the SDK side in `IFrameHelper.js`).
- `app/javascript/widget/helpers/popoutHelper.js` — implements "open chat in a new window" (`showPopoutButton`/`popoutChatWindow`), carrying the `cw_conversation` cookie value through as a URL param since the popout window is a separate origin context.
- `app/javascript/widget/i18n/` — ~70 locale JSON files plus `index.js`; the widget has its own independent i18n tree from the dashboard's.
- `app/views/widgets/show.html.erb` — not in the investigated paths but the actual seam: it's the ERB view that injects `window.chatwootWebChannel`, `window.chatwootPubsubToken`, `window.authToken`, `window.globalConfig` as inline `<script>` globals before `vite_javascript_tag 'widget'` loads the Vue app. Every "config" field the widget reads off `window.chatwootWebChannel` (avatar, working hours, pre-chat options, enabled features, CSAT flag, etc.) originates here from the backend `WebWidget` model.

## How It Fits Together
- **Backend surface**: all `widget/api/*.js` calls hit `/api/v1/widget/*`, i.e. [[widget-backend]] (`Api::V1::Widget::*` controllers) — a token-authenticated, non-agent API distinct from [[api-v1-controllers]]. `article.js` also hits `/hc/<slug>/<locale>/articles.json`, tying into the Help Center portal covered in [[portal-survey-superadmin]].
- **Real time**: `ActionCableConnector` subscribes over the same WebSocket infrastructure documented for the dashboard; message/typing/presence/status events originate from the same backend event dispatch that [[events-listeners]] and [[messages-services]] produce on the agent side — this is the customer-facing mirror of that pipeline.
- **Models touched indirectly**: everything here is a thin client over `WebWidget`/`Inbox`/`Conversation`/`Contact`/`Message`/`ContactInbox` records exposed through the widget API — see [[models]] and [[widget-backend]] for the actual Rails-side objects (e.g. `@web_widget`, `@contact_inbox`, `@token` set in `show.html.erb`).
- **SDK ↔ Widget bridge**: the two layers never share JS state directly — every interaction is a serialized string over `window.postMessage`, matched by literal `event` names on both sides (`sdk/IFrameHelper.js#events` on the host-page side, `App.vue#registerListeners` on the iframe side; shared constant `SDK_SET_BUBBLE_VISIBILITY` lives in `app/javascript/shared/constants/sharedFrameEvents.js`, one of only two message names promoted to a shared constant — the rest are inline string literals).
- **Public JS API → CustomEvents**: `window.$chatwoot`'s public methods (`setUser`, `setCustomAttributes`, `setLocale`, …) send postMessage into the iframe; the iframe's reactions (new message, ready, postback, error) come back out as `window` `CustomEvent`s (`chatwoot:ready`, `chatwoot:on-message`, `chatwoot:postback`, `chatwoot:error`, `chatwoot:opened`, `chatwoot:closed` — `app/javascript/widget/constants/sdkEvents.js`) that host-page JS listens for. This is the mechanism behind the official guide's "SDK additional user info" (`setUser`/`setCustomAttributes`) and identity-validation/HMAC docs (the `identifier_hash` field flows through `cookieHelpers.js#getUserString`/`computeHashForUserData`, though the actual HMAC verification is server-side, outside this module).
- **React Native / mobile**: `RNHelper` in `widget/helpers/utils.js` is a second transport (`window.ReactNativeWebView.postMessage`) parallel to the iframe path, used when the widget is loaded inside Chatwoot's mobile app WebView instead of a browser iframe.
- **Turbo/Turbolinks/Astro**: `entrypoints/sdk.js` and `DOMHelpers.js#restoreWidgetInDOM` specifically defend against SPA-style full-body replacement wiping out the injected bubble/iframe/style nodes, keyed off `dataset.turboPermanent`.

## Product Behavior
- The **Website live chat** install guides (GTM, Docusaurus, Webflow, Gatsby, WordPress, React Native, Next.js, Vue.js) all boil down to the same `window.chatwootSDK.run({ websiteToken, baseUrl })` snippet handled by `entrypoints/sdk.js` — differences between guides are purely about *how* to inject that script tag per platform, not about SDK behavior itself.
- **SDK additional user info** guide maps directly to `window.$chatwoot.setUser()` / `setCustomAttributes()` / `setConversationCustomAttributes()` in `entrypoints/sdk.js`, deduped client-side via the cookie hash in `cookieHelpers.js` so repeated identical calls are no-ops.
- **Dark mode** guide maps to the `darkMode` setting (`light`/`auto`/`dark`) threaded from `chatwootSettings.darkMode` → `window.$chatwoot.darkMode` → `config-set` postMessage → `appConfig` Vuex store → `useDarkMode()` composable, plus the runtime `setColorScheme()` API for changing it after load.
- Pre-chat forms, business-hours/availability text, and campaigns (URL-triggered popups) are widget-side implementations of the **Advanced features: pre-chat forms / wildcard URL campaigns** and **Features explained: business hours/auto-responder** guide topics — the actual field/URL/hours configuration is authored in the dashboard (inbox settings) and only consumed here.
- The **"Continue via email"** and **CSAT surveys** guide topics reference `sendEmailTranscript`/`csatSurveyEnabled` flags visible in the API/config surface (`api/conversation.js#sendEmailTranscript`, `chatwootWebChannel.csatSurveyEnabled`) but this investigation did not read the CSAT-rendering component itself.

## Notes for AI Agents
- The postMessage protocol is entirely string-matched — there is no shared enum/type on both sides for most event names (`'loaded'`, `'toggle-open'`, `'set-user'`, etc. are hand-typed in two different files). When adding a new SDK↔widget message, you must edit both `sdk/IFrameHelper.js#events` (or `App.vue#registerListeners`, depending on direction) and keep the string literal identical — a typo silently no-ops instead of erroring.
- `window.$chatwoot`, `window.chatwootWebChannel`, `window.authToken`, `window.chatwootPubsubToken` are global mutable state, not passed as props/injected — nearly every file in both `sdk/` and `widget/` reaches into these globals directly. Don't refactor toward passing them explicitly without checking every call site.
- The SDK guards `runSDK` with `if (window.$chatwoot) return;` — calling `chatwootSDK.run()` twice on the same page is a safe no-op, not a duplicate-widget bug.
- `IFrameHelper.createFrame` also guards `if (IFrameHelper.getAppFrame()) return;` (frame already exists) — combined with the above, re-running the embed script is idempotent by design.
- `useAvailability`/`availabilityHelpers` compute business-hours state independently in the widget for prechat/home display; this is separate from and does not gate the actual conversation-routing/auto-responder logic that lives server-side — treat it as display-only unless you've verified otherwise.
- `bubbleHelpers.js`, `DOMHelpers.js` etc. create raw DOM nodes at module load time (`export const widgetHolder = document.createElement('div')`) — these are module-level singletons, not per-instance state, matching the fact that only one widget can exist per page.
- `router.js`'s `isUpdatingRoute` global-navigation-guard pattern (blocking UI during route transitions) is widget-specific plumbing for chatwoot/chatwoot#10736 — check `appConfig/getIsUpdatingRoute` before adding new async router-triggered actions in this app to stay consistent with that convention.
- `widget/store/modules/conversation/actions.js#createConversation` and `sendMessageWithData` both swallow errors silently in the `catch` block (comment `// Ignore error` in `createConversation`; `sendMessageWithData` marks the message `status: 'failed'` but the caught `error` itself is unused) — failed-state UI is driven by the message's `status` field, not by surfacing the actual error.
- Two classes named `IFrameHelper` exist with different responsibilities: `app/javascript/sdk/IFrameHelper.js` (host-page side, builds/controls the iframe) and the `IFrameHelper` exported from `app/javascript/widget/helpers/utils.js` (iframe-side, just `isIFrame`/`sendMessage`/`isAValidEvent`/`getMessage`). Don't conflate them when tracing a message across the boundary.
