# Routing & App-wide Configuration

## Purpose

This module is the glue layer that isn't owned by any single feature: the single `routes.rb` that maps every URL (dashboard SPA, four API surfaces, public inbox APIs, channel webhooks, Super Admin, Sidekiq Web, OAuth callbacks) to a controller, the Rails `Application` bootstrap that wires the enterprise overlay into the load path, the account-level feature-flag catalog (`config/features.yml`), the `sidekiq-cron` schedule (`config/schedule.yml`), and the ~35 `config/initializers/*.rb` files that configure cross-cutting concerns (CORS, CSP, sessions, rate limiting, OmniAuth, Sidekiq, enterprise `prepend`/`extend` hooks). Nothing here is business logic — it decides *whether a request reaches a controller at all*, *what capabilities an account has turned on*, and *what runs on a timer*.

## Key Files & Classes

- `config/routes.rb` (755 lines) — the entire route table. Notable regions:
  - devise_token_auth mount (`mount_devise_token_auth_for 'User', at: 'auth'`) with overridden controllers under `devise_overrides/`.
  - Root route branches on `CW_API_ONLY_SERVER` env var — SPA (`dashboard#index`) vs API-only (`api#index`).
  - `namespace :api do namespace :v1 do resources :accounts do ... end end end` — the huge account-scoped block covering nearly every agent-facing feature (conversations, contacts, captain, inboxes, integrations, portals, reports v2 in a separate `namespace :v2`).
  - `namespace :platform` — Platform API (external system-to-Chatwoot integration, token-based).
  - `namespace :public do namespace :api do namespace :v1 do resources :inboxes` — the contact-facing Public API (widget/API-channel contacts create conversations/messages without agent auth) plus `hc/:slug/...` Help Center portal routes.
  - Channel webhook routes are flat, unauthenticated-by-signature endpoints: `mount Facebook::Messenger::Server, at: 'bot'`, `webhooks/twitter`, `webhooks/line/:line_channel_id`, `webhooks/telegram/:bot_token`, `webhooks/sms/:phone_number`, `webhooks/whatsapp/:phone_number` (get=verify/post=process), `webhooks/instagram`, `webhooks/tiktok`, `webhooks/shopify`.
  - OAuth callback routes per provider: `twitter/callback`, `linear/callback`, `shopify/callback`, `microsoft/callback`, `google/callback`, `instagram/callback`, `tiktok/callback`, `notion/callback`; Twilio has its own namespace with voice routes gated by `ChatwootApp.enterprise?`.
  - `.well-known/*` routes for app-link verification (`assetlinks.json`, `apple-app-site-association`, `microsoft-identity-association.json`) and Cloudflare custom-domain SSL challenge (`custom_domains#verify`).
  - Super Admin block: `devise_for :super_admins`, then `namespace :super_admin` (accounts, users, agent_bots, installation_configs, platform_apps/banners, instance_status, settings), and `authenticated :super_admin do mount Sidekiq::Web => '/monitoring/sidekiq' end` plus `Sidekiq::Cron::Web`.
  - `ChatwootApp.enterprise?` gates whole route subtrees inline (enterprise account API under `namespace :enterprise`, `whatsapp_calls`, `calls`, Twilio voice, conference/WhatsApp-calling member routes on inboxes) rather than living in a separate enterprise routes file.
- `config/application.rb` — `Chatwoot::Application < Rails::Application`. Key responsibilities: adds `lib`, `enterprise/lib`, `enterprise/listeners`, and all of `enterprise/app/**` to `eager_load_paths`; unshifts `enterprise/app/views` onto the view path so enterprise views override/extend OSS ones; explicitly `require`s every `.rb` under `enterprise/config/initializers` (so enterprise initializers run alongside core ones); `config.x = config_for(:app)` exposes `config/app.yml` as `Chatwoot.config`; conditionally configures Active Record Encryption (used for MFA) only when `ACTIVE_RECORD_ENCRYPTION_PRIMARY_KEY` etc. are set (`Chatwoot.encryption_configured?` / `Chatwoot.mfa_enabled?`).
- `lib/chatwoot_app.rb` — the `ChatwootApp` module used everywhere for environment/edition checks: `.enterprise?` (checks `enterprise/` dir exists and `DISABLE_ENTERPRISE` env var), `.chatwoot_cloud?`, `.self_hosted_enterprise?`, `.custom?` (checks `custom/` dir — a third, less-documented overlay), `.extensions` (returns `%w[enterprise custom]`/`%w[enterprise]`/`%w[]`, drives `prepend_mod_with`), `.advanced_search_allowed?`, `.otel_enabled?`.
- `config/initializers/01_inject_enterprise_edition_module.rb` — defines `InjectEnterpriseEditionModule`, prepended onto `Module` itself, giving every class/module `prepend_mod_with`, `extend_mod_with`, `include_mod_with`, `prepend_mod`, `extend_mod`, `include_mod`. These resolve a same-named constant under `Enterprise::<ClassName>` (or `Custom::...`) via `ChatwootApp.extensions` and prepend/extend/include it. This is the mechanical basis for the whole enterprise-overlay pattern referenced across the codebase.
- `config/features.yml` (274 lines) — the account feature-flag catalog: each entry is `name`, `display_name`, `enabled` (default-on for new accounts), optional `help_url`, `premium`, `chatwoot_internal`, `deprecated`, and `column`. A committed comment block states the `feature_flags` bitset column is **full (63/63)** and any new flag **must** set `column: feature_flags_ext_1`, appended at the end — bit positions are persisted per account row and must never be reordered/reused.
- `app/models/concerns/featurable.rb` — `Featurable` concern (included into `Account`) that turns `features.yml` into `FlagShihTzu` bitset flags. Builds `FEATURES_BY_COLUMN` by assigning each feature a 1-based bit position per column, raises `ArgumentError` if a column would exceed `MAX_FEATURES_PER_COLUMN` (63) or if an unknown column name is used. Defines `feature_<name>?`, `enable_features`, `disable_features`, `feature_enabled?`, `all_features`/`enabled_features`/`disabled_features`. New accounts get flags turned on via `before_create :enable_default_features`, which reads the `ACCOUNT_LEVEL_FEATURE_DEFAULTS` `InstallationConfig` row (not directly from the YAML at request time).
- `lib/config_loader.rb` — `ConfigLoader#process`, run on deploy/boot, reconciles `config/installation_config.yml` and `config/features.yml` into the `InstallationConfig` DB table (`ACCOUNT_LEVEL_FEATURE_DEFAULTS` row holds the feature list used by `enable_default_features` above). Supports `reconcile_only_new` to avoid clobbering configs an admin edited in Super Admin.
- `enterprise/config/premium_features.yml` — a flat list of feature names (e.g. `sla`, `audit_logs`, `captain_integration_v2`) that are gated as premium; cross-reference against the `premium: true` flags in `config/features.yml`.
- `config/schedule.yml` — declarative `sidekiq-cron` schedule loaded by `config/initializers/sidekiq.rb`. Each entry maps a job name to `cron`, `class`, `queue`. Loaded via `Sidekiq::Cron::Job.load_from_hash!(schedule, source: 'schedule')` inside `Rails.application.reloader.to_prepare`, only when `Sidekiq.server?`. A hardcoded cleanup list (`bulk_auto_assignment_job`) explicitly destroys stale Redis-persisted cron jobs left over from before the `source` tag existed — a one-off migration shim, not a general pattern. Current jobs: `Internal::TriggerDailyScheduledItemsJob` (daily), `TriggerScheduledItemsJob` (every 5 min), `Internal::TriggerHourlyScheduledItemsJob` (hourly), `Inboxes::FetchImapEmailInboxesJob` (every minute), `Internal::RemoveStaleContactInboxesJob` / `Internal::RemoveStaleRedisKeysJob` (daily 22:30 UTC), `Internal::DeleteAccountsJob` (daily 01:00 UTC), `AutoAssignment::PeriodicAssignmentJob` (every 30 min — see [[assignment]]), `Notification::RemoveOldNotificationJob` (daily), `Internal::RemoveOrphanConversationsJob` (every 12h). One job (`Internal::ProcessStaleContactsJob`) is commented out with a note it's disabled "investigating if this job is the source of orphan conversations".
- `config/initializers/rack_attack.rb` — `Rack::Attack` throttling config, ~30 named throttles. Uses a custom `Rack::Attack::Request` subclass (`remote_ip` via `action_dispatch.remote_ip`, `allowed_ip?` reads `RACK_ATTACK_ALLOWED_IPS` env, `path_without_extensions` normalizes `.json`/trailing-slash variants so `/auth`, `/auth.json`, `/auth/` share one bucket). Safelists trusted IPs and `/health`. Covers super-admin login, `/auth/sign_in` (with an explicit MFA-token bypass so MFA verification isn't double-throttled by the login rule), password reset, resend-confirmation, MFA verify, account signup, widget conversations/messages/contact-update/load/transcript (each individually toggleable via `ENABLE_RACK_ATTACK_WIDGET_*` env vars, keyed on `ip:website_token` where relevant), and several account-scoped Application API endpoints (conversation transcript/delete, agent create/delete, upload, contact search, reports v2 — user-level and account-level). Blocked requests are logged via an `ActiveSupport::Notifications.subscribe('throttle.rack_attack')` hook that masks API tokens. `Rack::Attack.enabled` is forced `false` outside production regardless of the `ENABLE_RACK_ATTACK` env var.
- `config/initializers/cors.rb` — `Rack::Cors` config: always allows `*` for `/packs/*`, `/audio/*`, `/public/api/*`; opens up everything (`resource '*'`) when `CW_API_ONLY_SERVER` is set or in development; opens `/api/*` when `ENABLE_API_CORS` env var is true. Also disables ActionCable request-forgery protection (`disable_request_forgery_protection = true`) so the API channel can be reached cross-origin.
- `config/initializers/session_store.rb` — cookie session store (`_chatwoot_session`), explicitly noted as used **only** for the Super Admin dashboard's flash/CSRF, not for API auth (agent/API auth is devise_token_auth, header-token based). `secure` is driven by `FORCE_SSL` env var.
- `config/initializers/content_security_policy.rb` — entirely commented-out Rails boilerplate; Chatwoot does not set an application-wide CSP header here (CSP-like frame/embedding controls, if any, live elsewhere, e.g. `feature_policy.rb`/`permissions_policy.rb`, not read in depth for this page).
- `config/initializers/omniauth.rb` — configures only `google_oauth2` as an OmniAuth provider (`provider_ignores_state: true`); other OAuth-like integrations (Twitter, Microsoft, Instagram, TikTok, Notion, Shopify, Linear) are handled via their own `namespace :x do resource :authorization` API routes and `x/callback` routes rather than OmniAuth strategies. `enterprise/config/initializers/omniauth_saml.rb` adds SAML as an additional enterprise-only OmniAuth strategy.
- `config/initializers/event_handlers.rb` — three lines that wire `Dispatcher.instance` (see `app/dispatchers/dispatcher.rb`) into `Rails.configuration.dispatcher` and call `load_listeners` inside `config.to_prepare` (so listeners reload correctly in development). See [[events-listeners]].
- `config/initializers/00_init.rb` — loads `APPS_CONFIG` from `config/integration/apps.yml` as a global constant (integration app catalog, e.g. for Dashboard Apps / `Api::V1::Integrations::AppsController`). The `00_` prefix forces it to load before other initializers that may depend on it.
- `config/installation_config.yml` (581 lines) — the much larger sibling catalog to `features.yml`: installation-wide (not per-account) settings such as branding (`INSTALLATION_NAME`, `LOGO*`, `BRAND_URL`), reconciled into the DB the same way via `ConfigLoader`, readable via `GlobalConfig`/`InstallationConfig` (`lib/global_config.rb`, `lib/global_config_service.rb` — not read in depth here).

## How It Fits Together

- **Routing → controllers**: `routes.rb` is the entry point for essentially every other backend module in this vault — [[api-v1-controllers]] (the big `api/v1/accounts` block), [[public-platform-api]] (the `public` and `platform` namespaces), [[whatsapp]]/[[facebook-instagram]]/[[other-channels]] (the flat `webhooks/*` routes and OAuth callbacks), [[widget-backend]] (`api/v1/widget/*`, `resource :widget`), [[captain-ai]] (`api/v1/accounts/.../captain/*`), and the Super Admin frontend ([[portal-survey-superadmin]]).
- **Enterprise gating happens at two levels**: (1) route-level, via inline `if ChatwootApp.enterprise?` blocks directly in `routes.rb` (not a separate enterprise routes file merged in) — see [[controllers-jobs-listeners]] and [[models-services]] for what those enterprise controllers/models actually do; (2) class-level, via `prepend_mod_with`/`extend_mod_with`/`include_mod_with` from `01_inject_enterprise_edition_module.rb`, which OSS classes across the codebase call to let `enterprise/app/**` classes prepend/extend behavior — this is the mechanism, not a specific feature.
- **Feature flags gate product behavior, not routes**: `Featurable`/`features.yml` flags are checked inside controllers/services/frontend (`feature_enabled?`), not in `routes.rb` — the routes for a feature typically always exist; the controller or Vue guard decides whether to honor the request. Cross-reference [[account-onboarding]] for how `Account` (which includes `Featurable`) is created and defaulted.
- **Scheduled jobs**: `config/schedule.yml` is the declarative source of truth for what runs on a timer; the actual job classes live in [[jobs]] (e.g. `AutoAssignment::PeriodicAssignmentJob` documented in [[assignment]], `Internal::RemoveOrphanConversationsJob`, `Notification::RemoveOldNotificationJob` documented in [[notifications]]). `sidekiq.rb` is purely the loader/wiring, not job logic.
- **Rate limiting sits in front of controllers**: `rack_attack.rb` throttles reference the same URL space as `routes.rb` (widget endpoints tie into [[widget-backend]]/[[widget-sdk]], reports throttles tie into [[reports]]) but are enforced at the Rack middleware layer before any controller/Pundit policy runs — distinct from [[authorization-policies]], which governs *who* can do *what* once a request is already let through.
- **`event_handlers.rb`** is the single wiring point for [[events-listeners]] — nothing in this module fires or listens to events itself, it just boots the dispatcher.

## Product Behavior

- The **Feature Flags and Premium Features** area of the product guide corresponds directly to `config/features.yml` + `enterprise/config/premium_features.yml` + `Featurable`: Super Admin's installation-wide feature toggles and an account's Settings → Features page are both reading/writing these same bitset columns. `premium: true` entries (e.g. `sla`, `audit_logs`, `captain_integration_v2`, `custom_roles`, `saml`, `advanced_search`) are the features documented in the guide as requiring an Enterprise/paid plan.
- Channel webhook setup guides (WhatsApp embedded/manual signup, Facebook, Instagram, Telegram, Line, SMS, TikTok, Shopify) all ultimately point a third party at one of the flat `webhooks/*` routes in `routes.rb`; the WhatsApp guide's "manual flow auto-configures the webhook" behavior corresponds to the `register_webhook` member route on `resources :inboxes`.
- The Help Center guide's public portal (custom domain, articles, categories, sitemap) is served by the `hc/:slug/...` routes defined directly in `routes.rb` rather than under the `public/api` namespace block, even though they dispatch to `public/api/v1/portals*` controllers.
- "Environment Variables and Configuration" (DeepWiki) maps most directly to the `ENV.fetch(...)` calls scattered through the initializers here (`CW_API_ONLY_SERVER`, `ENABLE_RACK_ATTACK*`, `RATE_LIMIT_*`, `RACK_ATTACK_ALLOWED_IPS`, `FORCE_SSL`, `ENABLE_API_CORS`, `GOOGLE_OAUTH_CLIENT_ID/SECRET`, `DISABLE_ENTERPRISE`) plus `config/installation_config.yml` for settings that are DB-backed and Super-Admin-editable instead of env-only.

## Notes for AI Agents

- **`config/features.yml` order and `column` are load-bearing.** The file's own header comment says bit positions are persisted per account row: never reorder or delete existing entries, never change an existing feature's `column`, and the default `feature_flags` column is stated as full (63/63) — any new flag must use `column: feature_flags_ext_1`. `Featurable.validate_feature_count!` will raise `ArgumentError` at boot if this is violated.
- **`enable_default_features` reads from the DB, not the YAML directly.** A newly-added flag in `features.yml` doesn't take effect for new accounts until `ConfigLoader#process` (run via a rake task/deploy step, not automatically on every boot) reconciles it into the `ACCOUNT_LEVEL_FEATURE_DEFAULTS` `InstallationConfig` row.
- **`ChatwootApp.enterprise?` is a directory check** (`root.join('enterprise').exist?`), gated off by `DISABLE_ENTERPRISE` env var — it is not a license check. `chatwoot_cloud?` and `self_hosted_enterprise?` layer `GlobalConfig` values (`DEPLOYMENT_ENV`, `INSTALLATION_PRICING_PLAN`) on top. Don't assume `enterprise?` true implies a paid plan is active.
- **Enterprise route/class overlay is inline, not merged from a separate file.** There is no `enterprise/config/routes.rb`; enterprise-only routes are `if ChatwootApp.enterprise?` blocks inside the single OSS `routes.rb`. When adding an enterprise-gated endpoint, follow that existing pattern rather than inventing a new routes file.
- **`prepend_mod_with`/`extend_mod_with`/`include_mod_with` resolve enterprise classes by naming convention**: for a class `Foo`, `prepend_mod_with('Foo')` looks for `Enterprise::Foo` (and `Custom::Foo` if `custom/` exists). Getting the enterprise-side namespace wrong silently no-ops (`each_extension_for` just doesn't yield) rather than raising — worth double-checking when an enterprise override doesn't seem to take effect.
- **`custom/` is a real third overlay tier** (`ChatwootApp.custom?`), same mechanism as `enterprise/`, stacked after it in `extensions`. It is not documented elsewhere in this investigation; a directory named `custom/` at repo root would activate it in `application.rb`'s eager-load paths were the `application.rb` list to include it — as read, `application.rb` only explicitly adds `enterprise/*` eager-load paths, so confirm whether `custom/` needs its own eager-load wiring before relying on it.
- **`schedule.yml` has a one-off migration shim** (`Sidekiq::Cron::Job.destroy('bulk_auto_assignment_job')` on every boot) — the file comment says to remove names from that list "once they've been through a deploy cycle." If adding a similar cleanup, follow that pattern and remember to clean it up later; don't leave it permanently.
- **`Rack::Attack` is force-disabled outside production** regardless of `ENABLE_RACK_ATTACK` — don't expect throttle behavior to reproduce in development/test without also stubbing `Rails.env`.
- **Session cookies are Super-Admin-only.** Don't reach for `session_store.rb`/cookie sessions when reasoning about agent/API auth — that's devise_token_auth headers (`access-token`/`client`/`uid`), which is why CORS explicitly `expose`s those headers.
- I did not deeply read `config/initializers/monkey_patches/` (a directory, contents unexamined), `feature_policy.rb`/`permissions_policy.rb`, `devise.rb`/`devise_token_auth.rb` internals, `active_record_query_trace.rb` (flagged elsewhere as a known dev-perf footgun — see memory), or `lib/global_config.rb`/`lib/global_config_service.rb` in depth — flagging so a future pass can fill these in if they matter.
