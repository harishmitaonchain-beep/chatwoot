# Database Schema & Data Model Overview

## Purpose
This page maps the shape of Chatwoot's PostgreSQL schema as defined in `db/schema.rb` — the single source of truth for every table, column, index, and (sparse) foreign key in the application. It is not a description of the Rails model layer itself (see [[models]] for that); it is the ground truth for how data is actually laid out, which tenancy pattern is used, which polymorphic/STI-style joins exist, and which constraints are enforced by Postgres versus left to the application.

## Key Files & Classes
- `db/schema.rb` — auto-generated, checked-in snapshot of the full schema (currently at version `2026_08_04_000003`, ~100 tables). Never hand-edited; regenerated by running migrations (`db:migrate`) or loaded directly (`db:schema:load`).
- `db/migrate/` (not read in detail here) — the incremental migration files that produce `schema.rb`; this is where actual schema changes are authored.
- Enabled Postgres extensions (declared at the top of the file): `pg_stat_statements`, `pg_trgm` (trigram indexes used for fuzzy text search on `contacts`, `tags`, `messages.content`), `pgcrypto` (`gen_random_uuid()` used for `conversations.uuid`), `plpgsql`, `vector` (`pgvector`, backing `article_embeddings.embedding` and `captain_assistant_responses.embedding` for Captain's semantic search / RAG).
- Two DB-level triggers (`create_trigger` blocks near the bottom of the file) implement **per-account sequences**: on `accounts` insert, Postgres sequences `conv_dpid_seq_<account_id>` and `camp_dpid_seq_<account_id>` are created; on `conversations`/`campaigns` insert, `display_id` is populated from `nextval()` of the matching per-account sequence. This is how `conversations.display_id` and `campaigns.display_id` stay small, sequential, and unique *per account* rather than being global auto-increment IDs.
- `add_foreign_key` statements: only **four** exist in the entire schema (`active_storage_attachments`/`active_storage_variant_records` → `active_storage_blobs`, `inboxes` → `portals`, `user_sessions` → `users`). Every other relationship (`account_id`, `conversation_id`, `contact_id`, `inbox_id`, etc. on ~100 tables) is a plain bigint/integer column with an index but **no DB-level foreign-key constraint** — referential integrity for those is enforced entirely in the Rails model layer (`belongs_to`, validations, `dependent:` callbacks), not by Postgres.

## How It Fits Together
**Tenancy.** `accounts` is the tenant root. Nearly every table carries an `account_id` column and a corresponding index (frequently a composite index with `account_id` first, e.g. `index_conversations_on_account_id_and_display_id`, `index_messages_on_account_id_and_inbox_id`). There is no Postgres row-level security or schema-per-tenant — isolation is purely a Rails-layer `account_id` scoping convention (relevant to [[authorization-policies]] and every controller in [[api-v1-controllers]]).

**Users vs agents.** `users` is a single table (Devise-backed: `encrypted_password`, `reset_password_token`, OTP/2FA columns `otp_secret`/`otp_required_for_login`/`otp_backup_codes`) shared across all accounts. The join table `account_users` carries the *per-account* role (`role` integer), `custom_role_id` (FK-less pointer to `custom_roles`), `availability`, `auto_offline`, and `agent_capacity_policy_id` — i.e. account membership and role are relationship attributes, not user attributes. See [[account-onboarding]].

**Conversations core.** `conversations` (id: serial) is the hub: `account_id`, `inbox_id`, `contact_id`, `contact_inbox_id`, `assignee_id` (a `users.id`, no FK), `assignee_agent_bot_id`, `team_id`, `campaign_id`, `sla_policy_id`, plus `status`, `priority`, `additional_attributes`/`custom_attributes` (jsonb), `cached_label_list` (denormalized text), `uuid` (via `gen_random_uuid()`, used for public-facing links), and the per-account `display_id` described above. `messages` (id: serial) belongs to `conversation_id`/`inbox_id`/`account_id` with a polymorphic `sender_type`/`sender_id`, `content_type`, `external_source_ids` (jsonb, per-channel IDs), and a `content` trigram index for search. This pair is the backbone consumed by [[conversations-services]] and [[messages-services]].

**Contacts & identity.** `contacts` holds one row per person per account (unique indexes on `email`+`account_id` and `identifier`+`account_id`), with `company_id` linking to `companies`. `contact_inboxes` is the join that gives a contact a **channel-specific identity per inbox** — `source_id` (e.g. WhatsApp wa_id, email address, Facebook PSID) is unique per `inbox_id`, and `pubsub_token`/`hmac_verified` support the widget/API-channel identity-verification flows described in the *Website live chat: identity validation/HMAC* guide topic. This table is the one implicated in the coexistence-duplicate-contact class of bugs noted in project memory (`project_whatsapp_coexistence_duplicate_conversation.md`). See [[contacts-services]].

**Inboxes & channel polymorphism.** `inboxes` does **not** use Rails STI (`type` column); instead it holds a generic `channel_id` + `channel_type` pair (e.g. `channel_type: "Channel::Whatsapp"`, `channel_id` pointing into `channel_whatsapp.id`) — a delegated/polymorphic-by-convention pattern, confirmed by the one-model-per-channel-table layout in `app/models/channel/` (`api.rb`, `email.rb`, `facebook_page.rb`, `instagram.rb`, `line.rb`, `sms.rb`, `telegram.rb`, `tiktok.rb`, `twilio_sms.rb`, `twitter_profile.rb`, `web_widget.rb`, `whatsapp.rb`). Each `channel_*` table stores that channel's credentials/config (e.g. `channel_whatsapp.business_management_token`, `channel_twilio_sms.auth_token`, `channel_email.smtp_password`) directly in plaintext columns — there is no column-level encryption in the schema itself. `inboxes` also carries cross-channel settings (`auto_assignment_config`, `working_hours_enabled`, `csat_config`, `lock_to_single_conversation`) that apply regardless of channel type. See [[whatsapp]], [[email]], [[facebook-instagram]], [[other-channels]].

**Automation, assignment, SLA.** `automation_rules` (`event_name`, `conditions`/`actions` jsonb) pairs with `automation_rule_pending_executions` (delayed/episode-based execution, `episode_key`, `due_at`, `skip_reason`) — see [[automation-rules]]. `assignment_policies` + `inbox_assignment_policies` + `agent_capacity_policies` + `inbox_capacity_limits` implement round-robin/fair-distribution assignment (see [[assignment]]); `sla_policies` + `applied_slas` + `sla_events` track SLA breach state per conversation.

**Reporting.** `reporting_events` is an append-only event-log table (`name`, `value`, `value_in_business_hours`, scoped by `account_id`/`inbox_id`/`user_id`/`conversation_id`) that backend report calculations read from — see [[reports]]. `reporting_events_rollups` is a separate pre-aggregated table (unique key on `account_id, date, dimension_type, dimension_id, metric`) that looks like a rollup/materialization layer for faster dashboard queries.

**Notifications & webhooks.** `notifications` uses a polymorphic `primary_actor_type`/`primary_actor_id` (+ optional `secondary_actor`) to reference whatever triggered it — see [[notifications]]. `webhooks` stores a jsonb `subscriptions` array (default list includes `conversation_status_changed`, `message_created`, etc.) per account/inbox — see [[events-listeners]] and [[jobs]] for what fires them.

**Captain / AI.** `captain_assistants`, `captain_documents`, `captain_assistant_responses` (with `pgvector` `embedding` column + `ivfflat` index), `captain_faq_suggestions`/`captain_faq_observations`, `captain_scenarios`, `captain_custom_tools`, `captain_message_reports`, `conversation_outcomes` (episode-based handoff/CSAT tracking with `episode_trigger`, `started_at`/`ended_at`), and `agent_sessions` (tracks LLM run metadata: `llm_model`, `credits_consumed`, `faq_ids`, `document_ids`) together form the data layer behind Captain — see [[captain-ai]].

**Help Center.** `portals`, `categories`, `folders`, `articles` (with `draft_title`/`draft_content` for unpublished edits, `locale`, `slug`), `article_embeddings` (pgvector, per-term embeddings) form the Help Center content model — see [[portal-survey-superadmin]].

**Enterprise-only tables.** Several tables clearly back Enterprise-only features present in OSS schema but implemented in `enterprise/`: `sla_policies`/`applied_slas`/`sla_events`, `custom_roles`, `agent_capacity_policies`/`inbox_capacity_limits`, `assignment_policies`/`inbox_assignment_policies`, `captain_*`, `agent_sessions`, `copilot_threads`/`copilot_messages`, `account_saml_settings`, `data_import*`, `leaves`. See [[models-services]] and [[controllers-jobs-listeners]] for the Enterprise-side model/service code that reads and writes them.

## Product Behavior
- The `channel_*` table split (one row per inbox's channel config, joined generically from `inboxes`) is the DB-level reflection of the "channel vs inbox" concept the *Setup account* guide topic explains to end users: a channel (WhatsApp number, email address, Facebook Page) is connected once, then wrapped in an inbox that carries Chatwoot-specific settings (auto-assignment, business hours, agents).
- `channel_whatsapp` having a single flat config (`provider`, `provider_config` jsonb, `business_management_token`, `phone_number_health`) rather than separate embedded-signup vs manual-signup tables confirms those are just different `provider_config` shapes on the same row — consistent with the *Other channels: WhatsApp (embedded signup, manual flow, Twilio)* and *embedded-signup-to-manual migration* guide topics, and with the coexistence-signup work referenced in this session's git log/branch name.
- `contact_inboxes.hmac_verified`/`pubsub_token` and `channel_web_widgets.hmac_mandatory`/`hmac_token` are the schema-level backing for the *Website live chat: identity validation/HMAC* guide topic.
- `csat_survey_responses.csat_review_notes`/`review_notes_updated_by_id` back the *CSAT review notes* feature described under Features explained.
- `working_hours` + `inboxes.working_hours_enabled`/`out_of_office_message` back the *business hours/auto-responder* guide topic.

## Notes for AI Agents
- **Do not assume a foreign key exists just because a column is named `*_id`.** Only 4 FK constraints exist in the whole schema. Deleting/orphaning a parent row (e.g. an `account`, a `conversation`) will not be blocked by Postgres — any cascade/cleanup behavior lives in Rails callbacks or background jobs, so when tracing "what happens on delete," look at the model (`dependent:` options) or job layer, not the schema.
- **`display_id` is not a normal auto-increment column.** It's populated by a `BEFORE INSERT` trigger (`conversations_before_insert_row_tr`, `campaigns_before_insert_row_tr`) pulling from a per-account Postgres sequence created by an `AFTER INSERT ... ON accounts` trigger. If you ever see raw SQL inserts into `conversations`/`campaigns` bypassing Rails, they'll need `display_id` handled manually or the trigger will do it — but a manually-seeded account row won't have its sequence yet unless the insert-trigger ran.
- **Channel tables are not STI.** `inboxes.channel_type`/`channel_id` point at a separate table per channel (`channel_whatsapp`, `channel_email`, etc.), not a `type` column on a single `channels` table. When adding a new channel type, expect a new `channel_<name>` table plus a corresponding `app/models/channel/<name>.rb`, not a subclass.
- **Multi-tenancy is convention-only.** There's no row-level security; every query must be scoped by `account_id` at the application layer. Missing an `account_id` scope in a controller or service is a cross-tenant data leak, not something the DB will catch.
- **Sensitive channel credentials are stored in plaintext columns** (`channel_whatsapp.business_management_token`, `channel_twilio_sms.auth_token`, `channel_email.smtp_password`, etc.) — no `encrypts` / ActiveRecord Encryption declared in the schema. Treat these columns as secrets when logging, dumping, or exporting data.
- **jsonb "bag" columns are pervasive**: `additional_attributes`, `custom_attributes`, `settings`, `provider_config`, `meta`, `content_attributes` appear across many tables as the extensibility mechanism instead of new columns. When looking for where a specific per-channel or per-feature setting lives, check these jsonb columns before assuming a dedicated column exists.
- **`accounts.feature_flags` / `feature_flags_ext_1`** are bigint bitmask columns (two of them — the `_ext_1` suffix implies the first ran out of bits) — see [[models-services]] / feature-flag handling rather than expecting a features table.
- Only look here for *shape*, not for validations, callbacks, or business rules — those live entirely in `app/models/**` (see [[models]]) and are not derivable from `schema.rb` alone.
