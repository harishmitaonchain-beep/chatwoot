# Background Jobs (Sidekiq)

## Purpose

`app/jobs` holds every `ActiveJob` job class Chatwoot enqueues onto Sidekiq: webhook delivery, inbound/outbound channel message processing, notifications, data imports, avatar fetching, scheduled housekeeping/cron work, bulk actions, and cross-cutting glue like event dispatch and ActionCable broadcast. It is the async execution layer the rest of the backend (controllers, services, event listeners) offloads work to instead of blocking a request.

## Key Files & Classes

- `app/jobs/application_job.rb` — root `ActiveJob::Base` subclass; only shared behavior is discarding jobs on `ActiveJob::DeserializationError` (e.g. the referenced record was deleted before the job ran).
- `app/jobs/mutex_application_job.rb` — base class adding Redis-backed distributed locking (`with_lock`, `Redis::LockManager`) plus a `retry_on_lock_conflict` class helper and a `LockAcquisitionError`. Explicitly documents that unlocks are **not owner-checked**, so a TTL-expired lock can be stolen and later deleted by the original (stale) holder — treated as an acceptable race dampener, not a correctness guarantee.
- `app/jobs/event_dispatcher_job.rb` — queue `critical`; the async half of the event system. `app/dispatchers/async_dispatcher.rb` enqueues this for every internal event, and `perform` calls `Rails.configuration.dispatcher.async_dispatcher.publish_event` which fans out to registered listeners (see [[events-listeners]]).
- `app/jobs/action_cable_broadcast_job.rb` — queue `critical`; broadcasts events to ActionCable channel members. For conversation-update-shaped events it re-fetches the conversation and rebuilds `push_event_data` instead of trusting the payload, to avoid broadcasting stale/out-of-order data under high traffic.
- `app/jobs/hook_job.rb` (`MutexApplicationJob`, queue `medium`) — the integration-hook fan-out: dispatches `Hook` events (`message.created`, `contact.updated`, etc.) to Slack, Dialogflow, Google Translate, Linear, and LeadSquared processors via an `INTEGRATION_PROCESSORS` map. LeadSquared processing is wrapped in a Redis mutex keyed per-hook because contact-created → contact-updated → conversation-created events land within milliseconds and would otherwise race and create duplicate CRM leads.
- `app/jobs/webhook_job.rb` (queue `medium`) — generic outbound webhook delivery for account/inbox/agent_bot webhook types; delegates to `Webhooks::Trigger.execute`.
- `app/jobs/webhooks/*_events_job.rb` — inbound channel webhook processors (Facebook, Instagram, WhatsApp, Twilio, SMS, Telegram, Line, TikTok). `Webhooks::WhatsappEventsJob` (`MutexApplicationJob`, queue `low`) is the most elaborate: it resolves the target `Channel::Whatsapp` from the payload, skips inactive/reauth-required embedded-signup channels, distinguishes regular inbound messages from WhatsApp-coexistence "SMB message echoes" (messages sent from the WhatsApp Business app itself), and serializes concurrent webhooks per `(inbox, contact)` with a 30s Redis lock so multi-part album uploads append to one conversation instead of racing to create duplicates.
- `app/jobs/send_reply_job.rb` (queue `high`) — outbound message dispatch; maps `message.conversation.inbox.channel.class` to a per-channel `*::SendOn*Service` (Twitter, Twilio SMS, Line, Telegram, WhatsApp, generic SMS, Instagram, TikTok, Email) via a `CHANNEL_SERVICES` hash, with special-cased Facebook-page/Instagram-direct-message routing.
- `app/jobs/trigger_scheduled_items_job.rb` (queue `scheduled_jobs`) — the 5-minute cron heartbeat; fans out to one-off campaign triggering, snoozed-conversation/notification reopening, auto-resolution, WhatsApp template sync, and pending automation-rule execution. Ends with `prepend_mod_with('TriggerScheduledItemsJob')` so Enterprise can splice in its own scheduled work (see below).
- `app/jobs/internal/trigger_daily_scheduled_items_job.rb` / `trigger_hourly_scheduled_items_job.rb` — daily/hourly cron entry points. The daily job schedules `Internal::CheckNewVersionsJob` at a per-installation stable minute derived from `Digest::MD5.hexdigest(ChatwootHub.installation_identifier).hex % 1440`, so version checks spread across the day instead of all installations hitting the same minute.
- `app/jobs/automation_rules/trigger_pending_executions_job.rb` + `process_pending_execution_job.rb` — the delayed-automations sweep/execute pair (see [[automation-rules]]). The trigger job purges terminal rows, sweeps due `AutomationRulePendingExecution` rows up to a configurable `AUTOMATION_PENDING_EXECUTIONS_SWEEP_LIMIT` (`InstallationConfig`, default 1000), and enqueues one `ProcessPendingExecutionJob` per row. The process job does an atomic `claim!` so overlapping sweeps or stale reclaims can't double-execute, checks the `delayed_automations` account feature flag (pausing, not discarding, when off), re-validates conditions before executing, and marks the row `executing` **before** running actions so a mid-run crash never causes a duplicate send — the row simply stays stuck until a future sweep reclaims it.
- `app/jobs/auto_assignment/assignment_job.rb` / `periodic_assignment_job.rb` — bulk conversation assignment (see [[assignment]]). `AssignmentJob.enqueue_for_inbox` uses a Redis `SET NX` token to coalesce so at most one job per inbox is in-flight, with careful compare-and-delete release logic to avoid a TTL-expired job deleting a newer job's claim.
- `app/jobs/delete_object_job.rb` (queue `low`) — generic async-delete used for large models (`Account`, `Inbox`); batch-destroys "heavy" associations (`conversations`, `contacts`, `inboxes`, `reporting_events`) in 5,000-row batches before calling `destroy!`, to avoid `destroy_async` fan-out timeouts. `process_post_deletion_tasks` is an empty hook Enterprise overrides (`enterprise/app/jobs/enterprise/delete_object_job.rb`) to write an `Enterprise::AuditLog` entry and extend `heavy_associations` with `SlaPolicy`.
- `app/jobs/data_import_job.rb`, `app/jobs/data_imports/**` — CSV/Freshdesk/Intercom data-import pipeline; `DataImports::BaseJob` centralizes failure handling (`fail_import!`, stale-run detection via `active_import_run_id`) shared by the per-source contacts/conversations page jobs (see [[data-import]]).
- `app/jobs/notification/*` — notification lifecycle: `EmailNotificationJob` (skips already-read notifications), `PushNotificationJob`, `DeleteNotificationJob`, `RemoveDuplicateNotificationJob`, `RemoveOldNotificationJob` (queue `purgable`, trims to 300/user and >1 month old), `ReopenSnoozedNotificationsJob` (see [[notifications]]).
- `app/jobs/internal/*` — operational/housekeeping jobs run only via cron: `DeleteAccountsJob`, `RemoveOrphanConversationsJob`, `RemoveStaleContactInboxesJob`, `RemoveStaleRedisKeysJob`, `SeedAccountJob` (Super Admin account seeding), `CheckNewVersionsJob`.
- `app/jobs/migration/*` — one-off/backfill jobs (queue `async_database_migration` or `scheduled_jobs`), e.g. `BackfillCompaniesContactsCountJob`, `ConversationBatchCacheLabelJob`, `ValidateOpenaiHooksJob` — run once during a specific migration/deploy, not part of steady-state traffic.
- `app/jobs/avatar/*` — fetch/attach avatars from URL, Gravatar, or a site favicon (queue `purgable`).
- `app/jobs/bulk_actions_job.rb` / `app/jobs/contacts/bulk_action_job.rb` (queue `medium`) — dashboard bulk-select operations (label add/remove, status change, snooze) on conversations/contacts, permission-filtered via `Conversations::PermissionFilterService`.
- Enterprise mirrors, under `enterprise/app/jobs/`: `enterprise/trigger_scheduled_items_job.rb`, `enterprise/internal/trigger_daily_scheduled_items_job.rb`, `enterprise/delete_object_job.rb`, `enterprise/webhooks/whatsapp_events_job.rb` extend the OSS jobs above via `prepend_mod_with`. Enterprise also adds its own standalone job families not mirrored in OSS: `Captain::*` (conversation/document AI response building, embeddings, crawling — see [[captain-ai]]), `Sla::*` (SLA sweep/apply), `Voice::*` (call transcription, Twilio recording), `Saml::UpdateAccountUsersProviderJob`, `Companies::DeleteJob`/`SyncContactNamesJob`, `Portal::ArticleIndexingJob`.

## How It Fits Together

- **Config**: `config/sidekiq.yml` declares the queue priority order — `critical, high, medium, default, mailers, action_mailbox_routing, low, scheduled_jobs, deferred, purgable, housekeeping, async_database_migration, bulk_reindex_low, active_storage_analysis, active_storage_purge, action_mailbox_incineration` — queues are polled without weighting, so a busy `critical` queue can starve `low`/`housekeeping` work. Concurrency is `SIDEKIQ_CONCURRENCY` (default 10).
- **Cron/scheduling**: `config/schedule.yml` (loaded by `sidekiq-cron` in `config/initializers/sidekiq.rb`) drives all periodic jobs: `TriggerScheduledItemsJob` every 5 min, `Internal::TriggerDailyScheduledItemsJob` daily at 00:00 UTC, `Internal::TriggerHourlyScheduledItemsJob` hourly, `Inboxes::FetchImapEmailInboxesJob` every minute, plus daily/12-hourly housekeeping (stale contact-inboxes, stale Redis keys, orphan conversations, old notifications) and `AutoAssignment::PeriodicAssignmentJob` every 30 minutes. `Sidekiq::Cron::Job.load_from_hash!` upserts from the YAML and prunes Redis-persisted cron jobs no longer listed there.
- **Fan-out pattern**: several jobs are pure dispatchers that enqueue other jobs rather than doing work themselves — `TriggerScheduledItemsJob`, `Internal::TriggerHourlyScheduledItemsJob`, `AutomationRules::TriggerPendingExecutionsJob`. This keeps the cron entry points cheap and lets the actual work run on a different (often lower-priority) queue.
- **Event system integration**: `app/dispatchers/async_dispatcher.rb` is the bridge from synchronous domain events to Sidekiq — every `Events::Types` event fired in the app ends up as an `EventDispatcherJob.perform_later` call, which then re-publishes to listeners registered on `Rails.configuration.dispatcher`. See [[events-listeners]] for the listener side.
- **Channel send/receive loop**: inbound webhooks (`app/jobs/webhooks/*`) call into channel-specific `Incoming*Service` classes; outbound sends go through `SendReplyJob` → per-channel `SendOn*Service`. Both sides touch `Message`/`Conversation`/`Inbox` models (see [[models]]) and the channel-specific pages ([[whatsapp]], [[facebook-instagram]], [[other-channels]]).
- **Integrations**: `HookJob` is the sole entry point for the `Hook`-based integration model (Slack, Dialogflow, Google Translate, LeadSquared, Linear) — see [[integrations]].
- **Automation & assignment**: `AutomationRules::TriggerPendingExecutionsJob`/`ProcessPendingExecutionJob` implement the delayed side of the rules engine described in [[automation-rules]]; `AutoAssignment::AssignmentJob`/`PeriodicAssignmentJob` implement the async side of [[assignment]].
- **Notifications & mailers**: `Notification::*Job` classes are the async delivery layer for [[notifications]]; `conversation_reply_email_job.rb` runs on the dedicated `mailers` queue.
- **Locking primitive**: `MutexApplicationJob`/`Redis::LockManager` is reused by `HookJob` (LeadSquared) and `Webhooks::WhatsappEventsJob` (per-contact album serialization) — the only two observed consumers among the sampled files.

## Product Behavior

- The DeepWiki "Sidekiq Configuration and Queues" and "Scheduled Jobs" sections map directly onto `config/sidekiq.yml` and `config/schedule.yml` as read above.
- WhatsApp coexistence (Business-app-plus-Chatwoot dual sending) — covered in the official "WhatsApp embedded signup" / common-WhatsApp-issues guide topics — is implemented at the job layer in `Webhooks::WhatsappEventsJob` via the `smb_message_echoes` field handling and the `embedded_signup_channel?` reauthorization check.
- The daily/hourly cron jobs back several "invisible" product behaviors documented piecemeal across the guide: auto-resolution of conversations (business-hours/auto-responder features), WhatsApp template sync (WhatsApp template guide), snoozed-conversation reopening, and round-robin/auto-assignment sweeps (best-practices "round-robin assignment" article).
- Bulk conversation actions in the dashboard (label add/remove, status/snooze change) are backed by `BulkActionsJob`; this underlies the multi-select toolbar behavior in the conversation list.

## Notes for AI Agents

- **Enterprise override point**: several jobs end with `SomeJob.prepend_mod_with('SomeJob')` (`TriggerScheduledItemsJob`, `Internal::TriggerDailyScheduledItemsJob`, `Internal::TriggerHourlyScheduledItemsJob`, `DeleteObjectJob`, `Webhooks::WhatsappEventsJob`). When adding scheduled work or object-deletion side effects that are Enterprise-only, extend via a matching `enterprise/app/jobs/enterprise/...` module and `super`, not by editing the OSS `perform` directly.
- **`MutexApplicationJob#with_lock`'s unlock is not owner-checked** — a job that runs past its lock TTL can have its lock silently stolen and then deleted out from under the new holder. This is called out as an accepted tradeoff in the source comments, not a bug; don't "fix" it locally without reading the comment's reasoning first.
- **`Webhooks::WhatsappEventsJob` retry budget is coupled to its lock TTL** — the file has an explicit comment that the `retry_on LockAcquisitionError` budget (19 × 2s = 38s) must stay larger than the 30s lock TTL, or a webhook arriving just after lock acquisition can exhaust retries and silently drop a message. Any change to the lock TTL or retry count needs to preserve that inequality.
- **`AutomationRules::ProcessPendingExecutionJob` marks a row `executing` before running actions, not after** — this is deliberate (prevents double-send on retry) but means a crash mid-action leaves the row permanently `executing` unless a separate reclaim mechanism exists; don't assume `executing` rows are safe to re-enqueue without checking for a stale-reclaim path.
- **Queue choice is a priority signal, not just a label** — queues are polled in strict priority order with no fairness weighting (per `config/sidekiq.yml`'s comment), so putting new work on `critical`/`high` can starve `low`/`housekeeping`/`purgable` under load. Follow the existing convention (webhooks/inbound processing → `low`; realtime broadcast/event dispatch → `critical`; outbound sends → `high`).
- **`ApplicationJob` globally discards on `ActiveJob::DeserializationError`** — any job that takes an ActiveRecord object as an argument will silently no-op (with a log line) if that record is deleted before the job runs; don't add redundant existence checks purely to guard against this specific case, it's already handled at the base class.
- **`DeleteObjectJob#process_post_deletion_tasks` is an intentionally empty OSS hook** — only Enterprise fills it in (audit logging). Don't add OSS-only side effects there; add a new explicit step in `perform` instead if OSS needs one.
- Only a sample of `app/jobs` was read in full (roughly 25 of ~95 files, chosen for base classes, queue-priority spread, and cron/mutex/enterprise-override relevance). Directories not deeply inspected: `data_imports/freshdesk/*`, `data_imports/intercom/*` (per-source page-job pairs, structurally similar to the base job read), and most of `migration/*` (one-off backfill jobs, low ongoing relevance).
