# Authorization (Pundit Policies)

## Purpose

This module answers "is this user allowed to do this action, on this record, in this account?" for the agent-facing dashboard API. It is built entirely on the [Pundit](https://github.com/varvet/pundit) gem: one `*Policy` class per resource, each exposing `action_name?` predicate methods that controllers call via `authorize` / `policy_scope`. Authorization in Chatwoot is account-scoped and role-based — every check is a function of `(user, account, account_user)`, not of the user in isolation, because the same `User` row can be an `administrator` on one account and an `agent` on another.

## Key Files & Classes

- `app/policies/application_policy.rb` — base class every policy inherits from. Builds `user`, `account`, `account_user`, `record` out of the Pundit context hash; default-denies `create?`/`update?`/`destroy?`; default `show?` delegates to `scope.exists?(id: record.id)`. Also defines the nested `Scope` base class used for `policy_scope`.
- `app/policies/account_policy.rb`, `user_policy.rb`, `team_policy.rb`, `team_member_policy.rb`, `label_policy.rb`, `webhook_policy.rb`, `automation_rule_policy.rb`, `custom_attribute_definition_policy.rb`, `campaign_policy.rb`, `dashboard_app_policy.rb`, `agent_bot_policy.rb`, `assignment_policy_policy.rb`, `custom_filter_policy.rb`, `hook_policy.rb` — "settings"-style policies. Nearly all actions gate on `account_user.administrator?` (a few, e.g. `CustomFilterPolicy` and `CustomAttributeDefinitionPolicy#index?/show?`, also allow plain `agent?`).
- `app/policies/conversation_policy.rb` — the most nuanced OSS policy: `show?` is true for administrators, `AgentBot` users, or agents with inbox/team access (`user.inboxes` / `user.teams` membership against the record's `inbox_id`/`team_id`); `destroy?` is admin-only; `index?` is always true (list filtering happens elsewhere, not via `policy_scope`). Defines private helpers `assigned_to_user?`/`participant?` that aren't used in the OSS class itself but exist for the Enterprise override to call.
- `app/policies/contact_policy.rb`, `csat_survey_response_policy.rb`, `report_policy.rb`, `article_policy.rb`, `category_policy.rb`, `portal_policy.rb` — each ends with `PolicyName.prepend_mod_with('PolicyName')`, the extension point Enterprise hooks into (see below). Most base actions here are wide open (`ContactPolicy#show?/create?/update?` = `true`) or admin-only (`ReportPolicy#view?`).
- `app/policies/macro_policy.rb` — ownership-based: global macros (`record.global?`) require admin for update/destroy, personal macros require `author?` (`record.created_by == account_user.user`); `show?`/`execute?` allow either.
- `app/policies/data_import_policy.rb` — admin-only, plus a custom `Scope` that returns `scope.none` for non-admins instead of the default unfiltered scope.
- `app/policies/captain/tasks_policy.rb` — all actions (`rewrite?`, `summarize?`, `reply_suggestion?`, `label_suggestion?`, `follow_up?`) are `true`; any authenticated account member can call Captain AI helper actions.
- `enterprise/app/policies/enterprise/conversation_policy.rb` (`Enterprise::ConversationPolicy`) — prepended into `ConversationPolicy`; when the agent has a `custom_role`, replaces the plain inbox/team check with a permission lookup (`conversation_manage`, `conversation_unassigned_manage`, `conversation_participating_manage`) evaluated against `assigned_to_user?`/`participant?`/`unassigned_conversation?`.
- `enterprise/app/policies/enterprise/{report,contact,article,category,portal,csat_survey_response}_policy.rb` — same pattern: `custom_role.permissions.include?('report_manage' | 'contact_manage' | 'knowledge_base_manage')` then `|| super` to fall back to the OSS rule.
- `enterprise/app/policies/custom_role_policy.rb`, `account_saml_settings_policy.rb`, `sla_policy_policy.rb`, `agent_capacity_policy_policy.rb`, `company_policy.rb`, `captain/assistant_policy.rb`, `captain/custom_tool_policy.rb`, `captain/scenario_policy.rb`, `captain/faq_suggestion_policy.rb` — standalone Enterprise-only policies (no OSS counterpart), same admin-gated shape.
- `enterprise/app/models/custom_role.rb` — defines the actual permission vocabulary in a `PERMISSIONS` array and doc-comment: `conversation_manage`, `conversation_unassigned_manage`, `conversation_participating_manage`, `contact_manage`, `report_manage`, `knowledge_base_manage`. This is the enum the Enterprise policy overrides above all check against.
- `app/controllers/application_controller.rb` — defines `pundit_user`, returning `{ user: Current.user, account: Current.account, account_user: Current.account_user }`; this hash is what every policy's `initialize` receives as `user_context`.
- `app/controllers/api/base_controller.rb` — `check_authorization(model = nil)` infers the policy class from `controller_name` (e.g. `TeamsController` → `authorize(Team)`) and is wired as a `before_action :check_authorization` in ~39 controllers; `check_admin_authorization?` is a blunt `raise Pundit::NotAuthorizedError unless Current.account_user.administrator?` escape hatch used outside the policy-class pattern.
- `app/controllers/concerns/request_exception_handler.rb` — the single place that rescues `Pundit::NotAuthorizedError` and turns it into a 401/403 `render_unauthorized` JSON response.

## How It Fits Together

- **Model side**: `AccountUser` (`app/models/account_user.rb`) is the join row every policy pivots on — `enum role: { agent: 0, administrator: 1 }` plus `custom_role_id` (Enterprise). Its `#permissions` method returns `['administrator']` or `['agent']` for OSS; Enterprise's `CustomRole#permissions` array (a Postgres text array) supplies the finer-grained strings consumed above.
- **Controller side**: policies are invoked two ways — explicit `authorize @record, :action?` calls (24 controllers, e.g. `Api::V1::Accounts::ConversationsController#destroy` → `authorize @conversation, :destroy?`) and the blanket `before_action :check_authorization` (39 controllers) that authorizes against the whole model class using the controller-name-derived policy. `policy_scope` (only 3 call sites: `data_imports_controller.rb`, `inboxes_controller.rb`, `labels_controller.rb`) drives list-endpoint filtering through each policy's nested `Scope#resolve`.
- **Extension point**: OSS policies that Enterprise needs to extend end with `PolicyName.prepend_mod_with('PolicyName')`; the matching `enterprise/app/policies/enterprise/policy_name.rb` module is prepended ahead of the OSS methods, so `super` inside the Enterprise module falls through to the OSS rule. Not every OSS policy has this hook (e.g. `InboxPolicy`, `TeamPolicy`, `UserPolicy`, `AutomationRulePolicy`, `LabelPolicy`, `CampaignPolicy` have no `prepend_mod_with` and no Enterprise override today).
- **Touches**: [[models]] (`Account`, `User`, `AccountUser`, `Conversation`, `Inbox`, `Team`, `Macro`, `CustomRole`), [[conversations-services]] and [[messages-services]] (which call these policies indirectly through controllers, not directly), [[api-v1-controllers]] (the controllers that call `authorize`/`policy_scope`), [[controllers-jobs-listeners]] (Enterprise controller layer for SAML settings, agent capacity policies, SLA policies), [[captain-ai]] (`Captain::TasksPolicy`, `Captain::AssistantPolicy`).
- Policies are pure permission checks — they never enqueue jobs, fire events, or write to the database themselves; all side effects happen in the controller action after authorization passes.

## Product Behavior

This backend layer is the enforcement mechanism behind the "Manage team access control with flexible role-based permissions" feature described in the official user guide: the two built-in roles (Agent / Administrator) map directly to `AccountUser#role`, and the flexible custom-role permissions (contacts, reports, knowledge base, and the three conversation-visibility tiers) map directly to the `CustomRole::PERMISSIONS` list and the `Enterprise::*Policy` modules that check it. The three conversation permission tiers (`conversation_manage`, `conversation_unassigned_manage`, `conversation_participating_manage`) are the backend implementation of whatever the role-based-permissions guide describes as levels of conversation visibility for a custom role (e.g. all conversations vs. unassigned-and-own vs. assigned-or-participating-only).

## Notes for AI Agents

- Every policy's `initialize` destructures `user_context` into `user`/`account`/`account_user`/`record`. `account_user` can be `nil` in theory (e.g. platform/system contexts) — most policies call `@account_user.administrator?` without a safe-navigation `&.`, so a nil `account_user` raises `NoMethodError` rather than denying gracefully; this is only safe because `pundit_user` is only built inside authenticated, account-scoped controllers.
- `ApplicationPolicy#show?`'s default (`scope.exists?(id: record.id)`) is a real fallback used by policies that don't override `show?` at all — check for that before assuming a resource has no read-authorization behavior.
- The Enterprise pattern is always additive-then-fallback: `custom_role_permission_check || super`. Never edit an OSS policy to add Enterprise-only logic directly — add/extend the `enterprise/app/policies/enterprise/*.rb` module and call `prepend_mod_with` from the OSS file (per this repo's Enterprise Edition conventions).
- `ConversationPolicy`'s private `assigned_to_user?` and `participant?` look unused by static analysis of the OSS file alone — they exist purely so `Enterprise::ConversationPolicy` (prepended into the same class) can call them. Don't "clean up" seemingly-dead private methods in policies that have a `prepend_mod_with` line without checking the matching `enterprise/` module first.
- Authorization coverage is inconsistent by design/history: some controllers call `authorize` per-action, others rely on the blanket `check_authorization` before_action inferring the policy from `controller_name`, and a few (e.g. `check_admin_authorization?` in `Api::BaseController`) bypass the policy-class pattern entirely with an inline admin check. When adding a new controller action, check what pattern the surrounding controller already uses rather than introducing a third style.
- `CustomRole::PERMISSIONS` in `enterprise/app/models/custom_role.rb` is the source of truth for valid permission strings — if you add a new custom-role permission, it needs both a `CustomRole::PERMISSIONS` entry and the corresponding `Enterprise::*Policy` module check; the two are not automatically linked.
- `policy_scope` is rarely used (only 3 controllers) — most index actions filter records with hand-written scopes/services rather than a Pundit `Scope` class, so don't assume every `index?` in a policy implies a matching `Scope#resolve` is actually wired up in the controller.
