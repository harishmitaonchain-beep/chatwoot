# Reports & Analytics Backend

## Purpose

This module computes agent, team, inbox, and account-level performance metrics — conversation counts, message counts, average first response/resolution/reply time, resolution counts, bot resolutions/handoffs — for the Reports section of the dashboard. It has two halves that live in the two investigated directories:

- `app/services/reporting_events/*` — the **write path**: turns raw `ReportingEvent` rows (emitted by `ReportingEventListener` when conversations resolve, get a first response, etc.) into pre-aggregated `ReportingEventsRollup` rows, incrementally on every event and in bulk via a per-day backfill.
- `app/services/reports/*` — the **read path**: a small registry of "public" report metrics and a `DataSource` that currently always queries the raw `reporting_events`/`conversations`/`messages` tables (not the rollups) to answer timeseries, aggregate, and grouped-summary queries used by the `V2::Reports::*` builders and `Api::V2::Accounts::ReportsController`.

## Key Files & Classes

**Read path — `app/services/reports/`**
- `app/services/reports/data_source.rb` — `Reports::DataSource`, the abstract base: holds query context (`account`, `metric`, `dimension_type`/`dimension_id`, `scope`, `range`, `group_by`, `timezone_offset`, `business_hours`) and a `.for(**context)` factory. The factory has a `TODO` comment and currently *always* returns `Reports::RawDataSource` — there is no rollup-backed data source wired in yet despite the rollup write path being fully built.
- `app/services/reports/raw_data_source.rb` — `Reports::RawDataSource < Reports::DataSource`, the only concrete implementation. Provides `timeseries`, `aggregate`, and `summary`, all built directly against `ReportingEvent`/`Conversation`/`Message` ActiveRecord scopes using the `groupdate`-style `group_by_period` (permitted periods: `hour/day/week/month/year`) and account `timezone_offset`. `summary` builds a raw-SQL `SELECT ... CASE WHEN name = '...' THEN ... END` per metric, grouped by dimension, then merges in conversation counts separately.
- `app/services/reports/report_metric_registry.rb` — `Reports::ReportMetricRegistry`, a `Data.define`-based registry (`Metric` struct) of the public, API-facing metrics: `conversations_count`, `incoming_messages_count`, `outgoing_messages_count`, `avg_first_response_time`, `avg_resolution_time`, `reply_time`, `resolutions_count`, `bot_resolutions_count`, `bot_handoffs_count`. Each entry carries `aggregate` (`:count`/`:average`), `raw_event_name`, `rollup_metric`, `summary_key`, and an optional `raw_count_strategy` (`:distinct_conversation` or `:exclude_bot_handoffs`). This is the single source of truth `RawDataSource`, `V2::Reports::DrilldownBuilder`, and the controller's param validation all read from.
- `app/services/reports/drilldown_timestamp_validator.rb` — `Reports::DrilldownTimestampValidator`, validates the `bucket_timestamp`/`since`/`until` params for the drilldown endpoint (used to click into a chart bucket and see underlying records), including that the requested bucket actually overlaps the `since..until` range for the given `group_by` granularity. Depends on constants defined on `V2::Reports::DrilldownBuilder` (`DEFAULT_GROUP_BY`, `SUPPORTED_GROUP_BY`).

**Write path — `app/services/reporting_events/`**
- `app/services/reporting_events/event_metric_registry.rb` — `ReportingEvents::EventMetricRegistry`: maps each raw event *name* (`conversation_resolved`, `first_response`, `reply_time`, `conversation_bot_resolved`, `conversation_bot_handoff`) to one or more rollup metrics it feeds (e.g. `conversation_resolved` → both `resolutions_count` (count) and `resolution_time` (duration)). This is the registry actually used by `RollupService` and `BackfillService`.
- `app/services/reporting_events/rollup_service.rb` — `ReportingEvents::RollupService`, called synchronously right after a `ReportingEvent` is saved (from `ReportingEventListener`). For each of the three dimensions (`account`, `agent`/`user_id`, `inbox`/`inbox_id`) it upserts a `ReportingEventsRollup` row per metric with `INSERT ... ON CONFLICT DO UPDATE` additive SQL (`count = count + EXCLUDED.count`, etc.), keyed on `[account_id, date, dimension_type, dimension_id, metric]`. Gated only by `account.reporting_timezone` being a valid `ActiveSupport::TimeZone` — explicitly *not* gated by a feature flag (per its own comment, the flag only controls whether reads use rollups).
- `app/services/reporting_events/backfill_service.rb` — `ReportingEvents::BackfillService`, a batch/idempotent day-level rebuild: deletes that account+date's rollup rows and rebuilds them from scratch via grouped SQL aggregation over `reporting_events`, split into a "standard" path (group-and-sum) and a `DISTINCT_COUNT_EVENTS = %w[conversation_bot_handoff]` path (queried per-dimension with `COUNT(DISTINCT conversation_id)` because distinct counts aren't additive across a group-then-sum). **Not currently invoked from any job, rake task, or scheduler in the codebase** — only referenced from its own spec.
- `app/services/reporting_events/metric_registry.rb` — `ReportingEvents::MetricRegistry`. Its own top-of-file comment says this exists because "raw reporting events and rollup rows do not share a single metric namespace" and is a `TODO: split into separate registries`. That split has already happened — `EventMetricRegistry` (write-side) and `Reports::ReportMetricRegistry` (read-side) supersede it. **This file has zero callers anywhere else in the codebase** (confirmed via repo-wide grep) — it appears to be superseded/dead code left over from the registry split.

## How It Fits Together

- **Models**: `ReportingEvent` (raw, one row per resolution/first-response/reply/bot-handoff) and `ReportingEventsRollup` (pre-aggregated, one row per account+date+dimension+metric, with a Rails `enum :dimension_type` of `account/agent/inbox/team` and `enum :metric` of `resolutions_count/first_response/resolution_time/reply_time/bot_resolutions_count/bot_handoffs_count`). See [[models]].
- **Listener**: `app/listeners/reporting_event_listener.rb` (`ReportingEventListener < BaseListener`) is the actual producer — it handles `conversation_resolved`, `first_reply_created`, `reply_created`, `conversation_bot_handoff`, and `conversation_opened` domain events (fired via the event dispatcher, see [[events-listeners]]), builds a `ReportingEvent`, saves it, and — except for `conversation_opened`, which has no rollup metric — calls `ReportingEvents::RollupService.perform` inside a `rescue StandardError` guard (`safe_rollup`) so a rollup failure never blocks the raw event write or bubbles into the dispatcher.
- **Controllers**: `app/controllers/api/v2/accounts/reports_controller.rb` is the HTTP entry point (`index`, `summary`, `bot_summary`, `agents`/`inboxes`/`labels`/`teams`/`conversations_summary`/`conversation_traffic` CSV exports, `drilldown`, `conversations`, `bot_metrics`, `inbox_label_matrix`, `first_response_time_distribution`, `outgoing_messages_count`). It authorizes via `authorize :report, :view?` (Pundit — see [[authorization-policies]]) and the `drilldown` action is further gated to `Current.account_user.administrator?`.
- **Builders**: A large `app/builders/v2/reports/*` layer (outside this task's investigated scope, but the direct consumer) sits between the controller and `Reports::DataSource`/`Reports::ReportMetricRegistry`. Notably `V2::Reports::Timeseries::BaseTimeseriesBuilder` and `V2::Reports::BaseSummaryBuilder` both build a `Reports::DataSource.for(...)` and call `.timeseries`/`.summary` on it; `V2::Reports::DrilldownBuilder` reads `Reports::ReportMetricRegistry.fetch` directly to decide which raw scope (`messages`, `conversations`, or `reporting_events`) to drill into. A separate, older `app/builders/v2/report_builder.rb` (`V2::ReportBuilder`) still powers the `conversations` action independently of this metric registry.
- **Enterprise overlay**: `enterprise/app/listeners/captain/reporting_event_listener.rb` extends reporting for Captain (AI agent) message-level reports, and `enterprise/app/controllers/api/v1/accounts/reporting_events_controller.rb` / `enterprise/app/views/.../conversations/reporting_events.json.jbuilder` expose raw `ReportingEvent` data via the v1 Enterprise API surface — a separate, older path from the v2 reports builders described above.
- **Events consumed**: `conversation_resolved`, `first_reply_created`, `reply_created`, `conversation_bot_handoff`, `conversation_opened` — all dispatched elsewhere in the codebase (conversation/message services) and picked up by `ReportingEventListener`. See [[conversations-services]] and [[messages-services]] for where these fire.

## Product Behavior

The Reports section of the dashboard (per the official user guide's Reports category — overview/realtime, CSAT, conversations, bot, and SLA reports) is backed by this module for the conversation/agent/team/inbox metrics (response time, resolution time, resolution/handoff counts, message volume). The "drilldown" behavior (clicking a chart bucket to see the underlying conversations/messages) maps to `V2::Reports::DrilldownBuilder`. Bot-related reporting (`bot_resolutions_count`, `bot_handoffs_count`, the `bot_summary` controller action) corresponds to the guide's bot reports topic. CSAT and SLA reports are not covered by the two directories investigated here — they are not present in `app/services/reports` or `app/services/reporting_events` and likely live in separate CSAT/SLA-specific service code not covered by this page.

## Notes for AI Agents

- **The rollup read path does not exist yet.** `Reports::DataSource.for` has a literal `TODO` and always instantiates `Reports::RawDataSource`. Do not assume `ReportingEventsRollup` is being read anywhere in the live query path — it is currently write-only (populated by `RollupService` on every event, and rebuildable via `BackfillService`), but nothing reads it back for reports today. If you're asked to "make reports faster/use rollups," the rollup infra is already there — the read side is the missing piece.
- **`ReportingEvents::BackfillService` is unwired.** It exists and is fully tested (per its spec) but has no caller outside its spec — no rake task, no scheduled job, no controller action invokes it. If you need it to actually run in production, you must wire it into a job/scheduler yourself; don't assume it already runs nightly.
- **`ReportingEvents::MetricRegistry` looks dead.** It has zero callers besides itself and is superseded by `ReportingEvents::EventMetricRegistry` (write side) + `Reports::ReportMetricRegistry` (read side), per its own `TODO` comment about the split already having happened elsewhere. Don't add new usages of it; if touching this area, it's a reasonable candidate for deletion (confirm with the team/PR history first since this page is read-only investigation, not a change).
- **Metric definitions are duplicated across three registries with slightly different shapes**: `Reports::ReportMetricRegistry::METRICS` (`Data.define`, read-side, public API names), `ReportingEvents::EventMetricRegistry::EVENTS` (`Data.define`, write-side, keyed by raw event name), and the apparently-dead `ReportingEvents::MetricRegistry` (plain hashes, both directions). When adding a new metric, you need to touch at minimum the first two — check `spec/services/reports/report_metric_registry_spec.rb` and `spec/services/reporting_events/event_metric_registry_spec.rb` for the expected shape.
- **`raw_count_strategy` is a shared vocabulary** (`:distinct_conversation`, `:exclude_bot_handoffs`) that both `Reports::RawDataSource#reporting_event_count_scope` and `V2::Reports::DrilldownBuilder#reporting_event_scope` implement *independently* — the same two strategies are hand-coded in both places rather than shared. If you change counting semantics for `bot_handoffs_count` or `bot_resolutions_count`, you must update both call sites or the drilldown and the summary/timeseries numbers will disagree.
- **Bot-handoff uniqueness is enforced in application code, not the DB.** `ReportingEventListener#conversation_bot_handoff` guards against duplicate events with a `find_by` check before insert, but there's no unique index — both `BackfillService` (via its `DISTINCT_COUNT_EVENTS` special-case path) and the raw data source/drilldown builder (via `distinct_conversation` strategy) work around this by counting `DISTINCT conversation_id` rather than raw row count. This is called out explicitly as a `TODO` in `BackfillService`.
- **`RollupService` failures are swallowed on purpose.** `ReportingEventListener#safe_rollup` rescues `StandardError` around the rollup call and only reports to `ChatwootExceptionTracker` — the raw `ReportingEvent` write is never rolled back if rollup fails. This is a deliberate design choice per the inline comment (raw events are the source of truth; rollups are rebuildable), not an oversight.
- **`Reports::DataSource.for` uses a bare `**context` hash, not keyword-validated params** — passing an unsupported key silently does nothing (no error), and a missing key just becomes `nil`. Errors from malformed report params tend to surface downstream (e.g. `ReportMetricRegistry.fetch` returning `nil` and later methods silently returning `nil`/empty) rather than at construction time.
