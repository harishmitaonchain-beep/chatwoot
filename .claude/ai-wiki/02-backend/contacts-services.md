# Contact Services

## Purpose
The `Contacts::` service namespace (`app/services/contacts/`) holds the plain Ruby service objects that back contact management operations that don't belong on the `Contact` model itself: bulk operations (delete, label add/remove) triggered from the contacts list UI, the segment/filter query builder used by "Segment Contacts" and CSV export, figuring out which inboxes a given contact can be messaged through (used to start a new conversation from the contact profile), and normalizing a couple of derived fields on save. It is a small, focused directory — seven files, no sub-concerns or base classes of its own beyond inheriting from the account-wide `FilterService`.

## Key Files & Classes
- `app/services/contacts/bulk_action_service.rb` — `Contacts::BulkActionService`: dispatches a bulk-action payload (`{ action_name, ids, labels: { add:, remove: } }`) to one of the three services below based on which keys are present; logs and returns `{ success: false, error: 'unknown_operation' }` for anything else.
- `app/services/contacts/bulk_delete_service.rb` — `Contacts::BulkDeleteService`: loads `account.contacts.where(id: contact_ids)` and calls `destroy!` on each via `find_each`.
- `app/services/contacts/bulk_assign_labels_service.rb` — `Contacts::BulkAssignLabelsService`: calls `contact.add_labels(labels)` (from the `Labelable` concern, `app/models/concerns/labelable.rb`) per contact.
- `app/services/contacts/bulk_remove_labels_service.rb` — `Contacts::BulkRemoveLabelsService`: mirror of the above, does `contact.update!(label_list: contact.label_list - labels)`.
- `app/services/contacts/filter_service.rb` — `Contacts::FilterService < FilterService`: builds the SQL for advanced contact segments/filters (the "Segment Contacts" feature and the Filter panel on the Contacts page). Supplies contact-specific `base_relation` (`account.contacts.resolved_contacts(...)`), `filter_config`, and custom `filter_values` handling for `phone_number` (normalizes leading `+`) and `country_code` (downcases).
- `app/services/contacts/contactable_inboxes_service.rb` — `Contacts::ContactableInboxesService`: given a contact, returns the list of `{ source_id:, inbox: }` pairs describing which of the account's inboxes a new conversation could be started on for that contact (email present for Email inboxes, phone present for WhatsApp/SMS/Twilio, etc.), used to power "New Conversation" from a contact's profile. Declares an enterprise extension point via `prepend_mod_with('Contacts::ContactableInboxesService')`.
- `app/services/contacts/sync_attributes.rb` — `Contacts::SyncAttributes`: run on contact save (via `Contact#sync_contact_attributes`) to copy `additional_attributes['city']`/`['country']` into the top-level `location`/`country_code` columns, and to promote a contact from `visitor` to `lead` once it has an email, phone number, or any `social_*` additional attribute.

## How It Fits Together
- **Model**: all services operate on `Contact` (`app/models/contact.rb`). `Contact#sync_contact_attributes` (a `before_save` style private method) is the only place `Contacts::SyncAttributes` is invoked from — see [[models]].
- **Controller**: `Api::V1::Accounts::ContactsController` (`app/controllers/api/v1/accounts/contacts_controller.rb`) calls `Contacts::FilterService` directly in `#filter` and `Contacts::ContactableInboxesService` directly in `#contactable_inboxes`. It rescues the `CustomExceptions::CustomFilter::*` family that `FilterService` (the shared base, `app/services/filter_service.rb`) raises for invalid attribute/operator/value combinations. See [[api-v1-controllers]].
- **Bulk action path**: `Api::V1::Accounts::BulkActionsController#create` (`app/controllers/api/v1/accounts/bulk_actions_controller.rb`) authorizes `Contact, :destroy?` up front only when the action is `delete`, then enqueues `Contacts::BulkActionJob` (`app/jobs/contacts/bulk_action_job.rb`), which re-loads the `Account`/`User` by id and calls `Contacts::BulkActionService#perform` inside a Sidekiq job — see [[jobs]]. There is a matching `Actions::BulkActionsJob` path for conversations, kept separate.
- **Export**: `Account::ContactsExportJob` (`app/jobs/account/contacts_export_job.rb`) also instantiates `Contacts::FilterService` directly (bypassing the controller) to generate the CSV for a saved/ad-hoc segment.
- **Enterprise override**: `enterprise/app/services/enterprise/contacts/contactable_inboxes_service.rb` prepends `Enterprise::Contacts::ContactableInboxesService`, which intercepts `Channel::TwilioSms` inboxes with `voice_enabled?` and routes them to a `voice_contactable_inbox` branch (phone-number-based) before falling back to `super` — see [[models-services]] and [[controllers-jobs-listeners]].
- **Captain**: `enterprise/app/services/captain/audience_matcher.rb` explicitly comments that it duplicates `Contacts::FilterService`'s SQL-casting behavior for numeric/date custom attributes so that Captain audiences match the same contacts a segment would — worth checking both files together if filter semantics change. See [[captain-ai]].
- **Feature flag**: `Contact.resolved_contacts(use_crm_v2:)` (in `contact.rb`) branches between the legacy `email/phone/identifier` presence filter and, when the account has the `crm_v2` feature (`config/features.yml`), a simpler `contact_type == 'lead'` filter. `Contacts::FilterService#base_relation` and the controller's own `#resolved_contacts` both thread `account.feature_enabled?('crm_v2')` into this call — they must stay in sync if the flag's semantics change.
- `Contacts::ContactableInboxesService` reads `inbox.channel_type` / `inbox.channel.medium` directly rather than going through a channel-specific service, so it needs a new `when` branch (and enterprise consideration) any time a new inbox channel type is added — see [[whatsapp]], [[facebook-instagram]], [[other-channels]].

## Product Behavior
- The contact-list bulk delete / bulk label add-remove actions map to the multi-select toolbar on the Contacts page described in the **Understanding Contacts** guide topic.
- `Contacts::FilterService` is the backend for the **Segment Contacts** feature (advanced filter builder + saved segments) and is also reused, unmodified, by CSV export and by Captain's audience matching — so changes to filter operators/attribute handling here affect all three surfaces at once.
- `Contacts::ContactableInboxesService` determines which "Start new conversation" inbox options appear on a contact profile; an inbox only appears if the contact already has the relevant identifier (email for Email inboxes, phone number for WhatsApp/SMS/Twilio) or, for Website/API inboxes, an existing `contact_inbox` record with no live conversation yet (Website only).

## Notes for AI Agents
- `Contacts::BulkAssignLabelsService` / `BulkRemoveLabelsService` both return `{ success: true, updated_contact_ids: [] }` early when `contact_ids` or `labels` is blank — but note they compute `updated_contact_ids` by re-`pluck`ing the same `contacts` relation *after* the mutation loop, not by tracking which contacts actually changed, so the id list is really "all requested ids that exist," not "ids that were actually modified."
- `Contacts::BulkDeleteService#perform` returns `nil` (via a bare `return` guard) when `contact_ids` is blank, whereas the label services return a `{ success:, updated_contact_ids: }` hash in the equivalent case — the three sibling services do not share a uniform return contract, so don't assume `BulkActionService#perform`'s return value has a consistent shape across action types.
- `Contact#destroy!` cascades through `dependent: :destroy_async` on `conversations`, `contact_inboxes`, `csat_survey_responses`, `messages`, and `notes` (see `app/models/contact.rb`), so `BulkDeleteService` synchronously calling `destroy!` in a `find_each` loop can enqueue a large number of async-destroy jobs per contact — expect Sidekiq load, not blocking DB load, for large bulk deletes.
- `Contacts::ContactableInboxesService.get_contactable_inbox` is a `case` on `inbox.channel_type` string with **no `else`/default branch** — inboxes on channel types not listed there (or hitting the enterprise override's `Channel::TwilioSms` non-voice path via `super`) simply return `nil` and get filtered out by `filter_map`; this is silent by design, not a bug, but it's easy to forget to add a new channel type here.
- The enterprise override in `enterprise/app/services/enterprise/contacts/contactable_inboxes_service.rb` is a real, working example of the `prepend_mod_with` extension pattern for a plain service object (not a model/controller) — follow it as the template for other OSS-vs-EE service divergence in this module.
- `Contacts::FilterService#filter_values` special-cases `phone_number` (re-adds a leading `+`) and `country_code` (downcases) before falling through to the shared `FilterService#filter_values`/`case_insensitive_values` logic in the parent class — if you add a new filterable contact attribute with format quirks, this is the method to extend, not the parent.
- `Contacts::SyncAttributes#set_contact_type` only ever promotes `visitor -> lead`; it explicitly never downgrades or otherwise changes `contact_type` once it's anything else (`return unless @contact.contact_type == 'visitor'`), so manually setting a contact back to `visitor` will not get auto-corrected by this service.
- `Contacts::ContactableInboxesService` and `Contacts::FilterService` both use unconventional initializers relative to a plain `def initialize` — the former uses the `pattr_initialize` macro (attr_extras gem) for a single required `contact:` keyword, the latter inherits `FilterService#initialize(params, user)` but reorders args to `(account, user, params)` with a `TODO` comment noting the base class's argument order is awkward.
