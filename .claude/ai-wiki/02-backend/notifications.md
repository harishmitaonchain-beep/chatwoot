# Notifications & Mailers

## Purpose
Two related but distinct concerns live here. `app/services/notification/*` (plus the `Notification` model, `NotificationBuilder`, and `Notification::*Job`s) implement Chatwoot's **in-app notification system** — per-agent records ("you were assigned", "you were mentioned", "SLA missed") that fan out to real-time UI updates, web/FCM push, and email. `app/mailers/*` is the broader **transactional email layer** for the whole app: agent notification emails, conversation reply emails (the actual customer-facing email channel), admin/account emails (deletion, imports, integration disconnects), team automation emails, and help-center portal instructions. `Notification::EmailNotificationService` is the bridge between the two: it turns a `Notification` record into a call into `AgentNotifications::ConversationNotificationsMailer`.

## Key Files & Classes

**Notification services** (`app/services/notification/`)
- `email_notification_service.rb` — `Notification::EmailNotificationService`: guards (already read, user unconfirmed, not subscribed, account email rate limit via `account.within_email_rate_limit?`) then calls `AgentNotifications::ConversationNotificationsMailer` and increments the account's sent-email counter.
- `push_notification_service.rb` — `Notification::PushNotificationService`: iterates the user's `notification_subscriptions` and, per subscription, tries browser push (`WebPush` gem + VAPID keys), Firebase Cloud Messaging (`Notification::FcmService`), and — only if Firebase creds are absent — falls back to relaying through `ChatwootHub` (the hosted push-relay service, gated by `ENABLE_PUSH_RELAY_SERVER`). Destroys subscriptions on `WebPush::ExpiredSubscription`/`InvalidSubscription`/`Unauthorized` or FCM error responses.
- `fcm_service.rb` — `Notification::FcmService`: thin wrapper around the `fcm` gem; mints and caches a Google service-account OAuth token (`Google::Auth::ServiceAccountCredentials`) from `FIREBASE_CREDENTIALS`/`FIREBASE_PROJECT_ID` (loaded via `GlobalConfigService`), refreshing when expired.
- `push_test_service.rb` — `Notification::PushTestService`: Super Admin-facing "send a test push" utility; mirrors the browser-push/FCM/hub branching above but returns a structured per-subscription result (`success`/`failure`/`skipped`) instead of firing real notifications.
- `mark_conversation_read_service.rb` — `Notification::MarkConversationReadService`: bulk-sets `read_at` on all of a user's unread notifications for a given conversation (called when the agent opens/reads it).

**Supporting model/builder/jobs** (not in the investigated paths but essential context)
- `app/models/notification.rb` — the `Notification` AR model. `NOTIFICATION_TYPES` enum (`conversation_creation`, `conversation_assignment`, `assigned_conversation_new_message`, `conversation_mention`, `participating_conversation_new_message`, `sla_missed_first_response`, `sla_missed_next_response`, `sla_missed_resolution`). `after_create_commit` fans out to `Notification::PushNotificationJob`/`Notification::EmailNotificationJob` (only if the user's `NotificationSetting` flag for that type+channel is on) plus `Notification::RemoveDuplicateNotificationJob`, and dispatches `NOTIFICATION_CREATED`/`UPDATED`/`DELETED` events consumed by `ActionCableListener` for live UI updates.
- `app/models/notification_setting.rb` — per-account-per-user email/push opt-in flags, one bit per notification type, stored as bitmask columns (`email_flags`/`push_flags`) via the `FlagShihTzu` gem.
- `app/builders/notification_builder.rb` — `NotificationBuilder`: the only place `Notification.create!` should be called from application code; enforces the "user subscribed" check (for `conversation_creation`), the blocked-contact skip, and a `ConversationPolicy#show?` access check before creating.
- `app/listeners/notification_listener.rb` — `NotificationListener < BaseListener`: reacts to `conversation_bot_handoff`, `conversation_created`, `assignee_changed`, `message_created` domain events and calls `NotificationBuilder`, `Messages::MentionService`, `Messages::NewMessageNotificationService`.
- `app/jobs/notification/` — `email_notification_job.rb`, `push_notification_job.rb` (thin `ApplicationJob` wrappers around the two services above), plus `remove_old_notification_job.rb`, `remove_duplicate_notification_job.rb`, `reopen_snoozed_notifications_job.rb`, `delete_notification_job.rb` for lifecycle/cleanup.

**Mailers** (`app/mailers/`)
- `application_mailer.rb` — `ApplicationMailer < ActionMailer::Base`: base for all mailers. Sets `Current.account` from mailer params, switches `I18n.locale` to the account's locale, resolves templates DB-first via `EmailTemplate.resolver` (account-specific > installation-specific > file fallback), and centralizes `send_mail_with_liquid` (renders through the Liquid template handler with `liquid_droppables`/`liquid_locals`) and SMTP exception handling (`rescue_from ExceptionList::SMTP_EXCEPTIONS`).
- `agent_notifications/conversation_notifications_mailer.rb` — `AgentNotifications::ConversationNotificationsMailer`: the actual email-sending target for in-app notifications (`conversation_creation`, `conversation_assignment`, `conversation_mention`, `assigned_conversation_new_message`, `participating_conversation_new_message`). The `assigned_*`/`participating_*` methods skip sending if `OnlineStatusTracker` shows the agent currently online (no email spam while active). Extended via `prepend_mod_with('AgentNotifications::ConversationNotificationsMailer')`.
- `enterprise/app/mailers/enterprise/agent_notifications/conversation_notifications_mailer.rb` — the Enterprise module prepended into the mailer above, adding `sla_missed_first_response`/`sla_missed_next_response`/`sla_missed_resolution`.
- `conversation_reply_mailer.rb` (+ `conversation_reply_mailer_helper.rb`, `conversation_reply_mailer_attachment_helper.rb`, `references_header_builder.rb`) — `ConversationReplyMailer`: the outbound customer-facing email channel itself (not an "internal notification" but the biggest/most complex mailer here). `email_reply` sends a single outgoing message; `reply_with_summary`/`reply_without_summary` batch queued replies; `conversation_transcript` emails a full transcript. Handles reply-to/message-id/`References:` headers for threading, CC/BCC from `content_attributes`, per-inbox "friendly" vs "professional" sender name, and branded-layout selection (`branded_email_templates` feature / inbox `branded_email_layout_available?`).
- `administrator_notifications/base_mailer.rb` + siblings (`account_notification_mailer.rb`, `account_compliance_mailer.rb`, `channel_notifications_mailer.rb`, `integrations_notification_mailer.rb`) — admin-facing transactional emails (account deletion scheduled/for-inactivity, contact import complete/failed, contact export complete, automation rule auto-disabled, channel OAuth disconnects for Facebook/Instagram/TikTok/WhatsApp/email, Slack/Dialogflow/OpenAI integration disconnects). All route through `send_notification`, defaulting `to:` the account's administrators.
- `team_notifications/automation_notification_mailer.rb` — `TeamNotifications::AutomationNotificationMailer#conversation_creation`: emails every member of a team when an automation rule action sends a team email (called from `AutomationRules::ActionService`).
- `portal_instructions_mailer.rb` — sends Help Center custom-domain CNAME setup instructions.

## How It Fits Together
- **Trigger path**: domain events (conversation created/assigned, message created) → `NotificationListener` → `NotificationBuilder` → `Notification.create!` → `after_create_commit` enqueues `Notification::PushNotificationJob` / `Notification::EmailNotificationJob` based on the user's `NotificationSetting` flags, and dispatches `NOTIFICATION_CREATED` for `ActionCableListener` to broadcast over the socket (see [[events-listeners]]).
- **Email delivery**: `Notification::EmailNotificationJob` → `Notification::EmailNotificationService` → `AgentNotifications::ConversationNotificationsMailer` (`.deliver_later`), which is itself an `ApplicationMailer` subclass sharing template resolution/Liquid rendering with every other mailer in this module.
- **Push delivery**: `Notification::PushNotificationJob` → `Notification::PushNotificationService`, fanning out over the user's `NotificationSubscription` rows to WebPush (browser), FCM (native/mobile via `Notification::FcmService`), or `ChatwootHub` (Chatwoot Cloud's push relay, used when a self-hosted install has no Firebase credentials of its own).
- **Reads/state**: `Notification::MarkConversationReadService` is called (from a controller, not read here) when an agent opens a conversation, so pending push/email jobs can see `read_at` and skip sending.
- **Automation rules**: `AutomationRules::ActionService` calls `TeamNotifications::AutomationNotificationMailer` directly for "send email to team" actions — see [[automation-rules]].
- **Conversations/messages**: `ConversationReplyMailer` is invoked from `app/services/action_service.rb`, `Email::SendOnEmailService`, `ConversationReplyEmailJob`, and the conversations controllers whenever an outgoing email-channel message needs delivery — see [[conversations-services]] and [[messages-services]] and [[email]].
- **Enterprise overlay**: SLA-missed notification emails are added purely via `prepend_mod_with` in `enterprise/app/mailers/enterprise/agent_notifications/conversation_notifications_mailer.rb`; the OSS `Notification::NOTIFICATION_TYPES` enum already reserves `sla_missed_*` values, so OSS and Enterprise stay schema-compatible. See [[models-services]].
- **Config**: mailer sender address (`MAILER_SENDER_EMAIL`), SMTP presence (`smtp_config_set_or_development?`), Firebase/VAPID/push-relay config all come through `ENV`/`GlobalConfigService`/`GlobalConfig` rather than being hardcoded — see [[routing-config]].

## Product Behavior
The official user guide's "Setting up notifications" and "notification troubleshooting" articles map directly onto this module: per-account, per-type email/push toggles are `NotificationSetting`'s `email_flags`/`push_flags` bitmask; the guide's troubleshooting steps (browser push permissions, VAPID/Firebase setup for self-hosted installs, "why am I not getting emails") correspond respectively to `Notification::PushNotificationService`'s `can_send_browser_push?`/Firebase-credentials branching and `Notification::EmailNotificationService`'s subscribed/rate-limit guards. The Super Admin "send test push" flow described implicitly by that troubleshooting guide is `Notification::PushTestService`. Channel-disconnect admin emails (`AdministratorNotifications::ChannelNotificationsMailer`) back the various "Other channels" setup guides' reauthorization flows (Facebook, Instagram, TikTok, WhatsApp, email).

## Notes for AI Agents
- Never call `Notification.create!` directly — always go through `NotificationBuilder`, which enforces the conversation-access (`ConversationPolicy#show?`) and blocked-contact checks that the model itself does not.
- `Notification::PushNotificationService` and `Notification::PushTestService` duplicate almost identical browser-push/FCM/hub branching logic (`firebase_credentials_present?`, `chatwoot_hub_enabled?`, `fcm_options` shape) — if you fix a bug in one, check the other.
- Firebase vs. ChatwootHub push is mutually exclusive by design: `send_fcm_push` requires `firebase_credentials_present?`, `send_push_via_chatwoot_hub` requires the opposite (`return if firebase_credentials_present?`) — a self-hosted install with its own Firebase project never routes through Chatwoot's hub.
- `AgentNotifications::ConversationNotificationsMailer#assigned_conversation_new_message` / `#participating_conversation_new_message` silently no-op if `OnlineStatusTracker` reports the agent online — don't expect an email in dev/test unless you clear presence.
- Almost every mailer method starts with `return unless smtp_config_set_or_development?` — mail silently does nothing in production without `SMTP_ADDRESS` configured; this is intentional, not a bug, but easy to mistake for a broken test.
- `ApplicationMailer` resolves templates from the DB first (`EmailTemplate.resolver`) before falling back to files in `app/views/mailers` — if an email's content looks wrong/stale in a given account, check for an account-specific or installation-specific `EmailTemplate` override before assuming the `.liquid`/view file is the source.
- `AgentNotifications::ConversationNotificationsMailer` is extended via `prepend_mod_with('AgentNotifications::ConversationNotificationsMailer')` at the bottom of the file — Enterprise's SLA-missed methods (`sla_missed_first_response`/`next_response`/`resolution`) live entirely in `enterprise/app/mailers/enterprise/agent_notifications/conversation_notifications_mailer.rb` and are invisible if you only read the OSS file.
- `Notification::EmailNotificationService#send_notification_email` has a `# TODO: Clean up whatever happening over here / Segregate the mailers properly` comment in the source — treat the dynamic `public_send(notification.notification_type.to_s, ...)` dispatch as a known rough edge, not something to silently "fix" without checking all notification types have matching mailer methods (OSS + Enterprise combined).
- `NotificationSetting` flags are managed by the `FlagShihTzu` gem (bitmask columns `email_flags`/`push_flags`), not individual boolean columns — adding a new `Notification::NOTIFICATION_TYPES` entry automatically gets `email_<type>?`/`push_<type>?` predicate methods for free, but the bit position is derived from hash order, so don't reorder existing `NOTIFICATION_TYPES` entries.
- Sampling note: only skimmed the automation/mention message services (`app/services/messages/mention_service.rb`, `new_message_notification_service.rb`) and did not read the full `Notification::*Job` cleanup jobs (`remove_old_notification_job.rb`, `reopen_snoozed_notifications_job.rb`, `delete_notification_job.rb`, `remove_duplicate_notification_job.rb`) in depth — worth a closer look for [[jobs]] if you're touching notification lifecycle/retention.
