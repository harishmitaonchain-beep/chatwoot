# Public & Platform APIs

## Purpose

Three separate, unauthenticated-by-default namespaces that sit outside the agent-facing dashboard API (`api/v1/accounts/*`, covered by [[api-v1-controllers]]):

- **`app/controllers/api/v2`** — a small, newer namespace nested under the same `Api::BaseController`/access-token auth as `api/v1`, used almost entirely for reporting (agent/team/inbox/label summaries, timeseries, drilldowns, CSV exports) plus self-serve account signup (`Api::V2::AccountsController#create`). Despite the "v2" name it is not a full v2 of the whole API — it only exists where v1's report endpoints needed a redesign.
- **`app/controllers/public`** — the contact-facing "API channel" surface: lets a website/app embed create contacts, start conversations, send/receive messages, and answer CSAT surveys against a `Channel::Api` inbox, without any Chatwoot user session. Also hosts the entire public Help Center (portal) rendering — HTML pages and a JSON API for categories/articles/search.
- **`app/controllers/platform`** — the account-provisioning API for Chatwoot resellers/hosts: create/update/delete `Account`s, `User`s, `AgentBot`s, and `AccountUser` memberships, plus a one-off email-channel bulk-migration endpoint. Authenticated by a `PlatformApp`-owned `AccessToken`, a completely different credential from both the dashboard's user-owned access token and the public API's HMAC.

## Key Files & Classes

### `api/v2`
- `app/controllers/api/v2/accounts_controller.rb` — `Api::V2::AccountsController < Api::BaseController`; the only `create` (self-service signup) action in this namespace. Skips the normal auth chain for `create` (`skip_before_action :authenticate_user!, ...`), gates on `GlobalConfigService.account_signup_enabled?` and an hCaptcha check (`ChatwootCaptcha`), then delegates to `AccountBuilder`. Ends with `prepend_mod_with('Api::V2::AccountsController')`.
- `app/controllers/api/v2/accounts/reports_controller.rb` (214 lines, the largest file in this module) — `Api::V2::Accounts::ReportsController < Api::V1::Accounts::BaseController` (note: inherits from the **v1** accounts base, not a v2-specific one). Thin controller that builds params and delegates to `V2::Reports::*Builder`/`V2::ReportBuilder` service objects (`ReportBuilder`, `MetricBuilder`, `DrilldownBuilder`, `BotMetricsBuilder`, `InboxLabelMatrixBuilder`, `FirstResponseTimeDistributionBuilder`, `OutgoingMessagesCountBuilder`) — all under `app/services/v2/reports/` (not read in this pass). CSV-export actions (`agents`, `inboxes`, `labels`, `teams`, `conversations_summary`, `conversation_traffic`) share a `generate_csv` helper that renders a `.csv` template with `Content-Disposition: attachment`.
- `app/controllers/api/v2/accounts/summary_reports_controller.rb` — per-dimension summary endpoints (`agent`/`team`/`inbox`/`label`/`channel`), each a thin call into a `V2::Reports::*SummaryBuilder`. `channel` rejects date ranges over 6 months (`date_range_too_long?`).
- `app/controllers/api/v2/accounts/live_reports_controller.rb` — real-time open/unattended/unassigned/pending conversation counts, optionally grouped by `team_id`/`assignee_id`.
- `app/controllers/api/v2/accounts/year_in_reviews_controller.rb` — builds (via `YearInReviewBuilder`) and caches a per-user, per-year report inside `Current.user.ui_settings`, keyed `"year_in_review_#{account_id}_#{year}"` — cache lives on the `users` row, not Redis/a table.

### `public` (contact-facing API channel + Help Center)
- `app/controllers/public_controller.rb` — the root base class, `ActionController::Base` (a comment notes a past attempt to switch to `ActionController::API` broke a spec and was reverted). Skips CSRF (`skip_before_action :verify_authenticity_token`), and provides `ensure_custom_domain_request` (looks up `Portal.find_by(custom_domain: request.host)`) and `ensure_portal_feature_enabled` (paywalls the `help_center` feature on Chatwoot Cloud only).
- `app/controllers/public/api/v1/inboxes_controller.rb` — `Public::Api::V1::InboxesController`; resolves `Channel::Api` by `identifier` and cascades `set_inbox_channel → set_contact_inbox → set_contact_inbox`/`set_conversation`, all `find_by!`. Parent class for the nested `contacts`/`conversations`/`messages` controllers below.
- `app/controllers/public/api/v1/inboxes/contacts_controller.rb` — create/update a `ContactInbox` under the channel. `create` goes through `ContactInboxWithContactBuilder` (`app/builders/contact_inbox_with_contact_builder.rb`); `update` goes through `ContactIdentifyAction` (`app/actions/contact_identify_action.rb`). Implements the widget/API-channel HMAC identity check itself (`process_hmac`/`valid_hmac?`, `OpenSSL::HMAC.hexdigest` + `ActiveSupport::SecurityUtils.secure_compare`) rather than reusing a shared concern.
- `app/controllers/public/api/v1/inboxes/conversations_controller.rb` — list/create conversations (via `ConversationBuilder`, `app/builders/conversation_builder.rb`), `toggle_status` (resolve, with `Current.contact` set as resolver), `toggle_typing` (dispatches `CONVERSATION_TYPING_ON/OFF` through `Rails.configuration.dispatcher`), `update_last_seen` (enqueues `Conversations::UpdateMessageStatusJob`). Every finder branches on `@contact_inbox.hmac_verified?` to decide whether to scope by the single `contact_inbox` or the whole `contact` (all its inboxes/conversations) — the same HMAC-verified/unverified split recurs in `messages_controller.rb` and `csat_survey`-adjacent code.
- `app/controllers/public/api/v1/inboxes/messages_controller.rb` — list (`MessageFinder`, `filter_internal_messages: true`), create (incoming message + attachments), update (CSAT response payload, locked after 14 days via `check_csat_locked`).
- `app/controllers/public/api/v1/csat_survey_controller.rb` — standalone CSAT survey show/update by conversation `uuid`, independent of the `inboxes/*` HMAC nesting; same 14-day lock pattern duplicated here.
- `app/controllers/public/api/v1/portals/base_controller.rb` — shared portal concerns: plain-layout toggle (`?show_plain_layout=true`, used for iframe embedding — `allow_iframe_requests` strips `X-Frame-Options`), dark/light theme param, locale switching (`switch_locale_with_portal`/`switch_locale_with_article`, careful to keep `@locale` as the portal's own code like `th_TH` for content queries while falling back to a valid `I18n.locale` for UI strings), and the shared `render_404` (`public/api/v1/portals/error/404`).
- `app/controllers/public/api/v1/portals_controller.rb`, `portals/articles_controller.rb`, `portals/categories_controller.rb`, `portals/search_controller.rb` — the public Help Center: portal home, article list/show/`show_markdown` (raw markdown at `.md` URLs)/`tracking_pixel` (1x1 PNG view-count beacon, 24h private cache), category list/show, and article search (`@articles.search(...)`, an Article model scope). `articles_controller.rb` and `search_controller.rb` end with `prepend_mod_with(...)`.

### `platform`
- `app/controllers/platform_controller.rb` — `PlatformController < ActionController::API`; the single base class for the whole namespace. Auth is `ensure_access_token` (reads `api_access_token`/`HTTP_API_ACCESS_TOKEN` header, looks up `AccessToken`) then `set_platform_app` (401 unless the token's polymorphic `owner` is a `PlatformApp`). `set_resource` is an abstract method every subclass must override (`raise 'Overwrite this method in your controller'` if not). `validate_platform_app_permissible` (run before `show`/`update`/`destroy`) 401s unless a `PlatformAppPermissible` row links the app to that exact resource — the platform-API-wide multi-tenancy boundary.
- `app/controllers/platform/api/v1/accounts_controller.rb` — CRUD for `Account`; `index` lists only accounts permissible to this `PlatformApp`; `create`/`update` split `features`/`limits`/`custom_attributes` out and toggle features individually via `Account#enable_features`/`disable_features`; `destroy` is async (`DeleteObjectJob.perform_later`).
- `app/controllers/platform/api/v1/users_controller.rb` — `create` finds-or-builds by email (`User.from_email`) and `skip_confirmation!`s; `login` returns an SSO URL (`@resource.generate_sso_link`); `update` uses Devise's `skip_reconfirmation!` so a platform-driven email change doesn't require the normal reconfirm-by-email step.
- `app/controllers/platform/api/v1/account_users_controller.rb` — nested under an account; `create` is `find_or_initialize_by(user_id:)` + `update!` (so it's really an upsert of the membership `role`).
- `app/controllers/platform/api/v1/agent_bots_controller.rb` — CRUD for `AgentBot`; avatar handled specially — `avatar_url` param is stripped from `agent_bot_params` and instead processed async via `Avatar::AvatarFromUrlJob`.
- `app/controllers/platform/api/v1/email_channel_migrations_controller.rb` — bulk-create `Channel::Email` + `Inbox` pairs for an account from an array of `{email, provider, imap_*}` entries. Gated behind `ENV['EMAIL_CHANNEL_MIGRATION']` (feature-flag env var, not a per-account feature) and capped at `MAX_MIGRATIONS = 25`. Only `google`/`microsoft` are `SUPPORTED_PROVIDERS`; each entry runs in its own `ActiveRecord::Base.transaction` and failures are captured per-entry (`rescue StandardError => e`) into the response array rather than aborting the whole batch.

## How It Fits Together

- **Routing**: `config/routes.rb` — `api/v2` is nested inside the same `namespace :api` block as `api/v1` (~line 507); `platform` (~line 574) and `public` (~line 600) are top-level namespaces with `defaults: { format: 'json' }`. The Help Center also gets bare `hc/:slug...` routes (no `/public/api/v1` prefix) mapped directly to the `public/api/v1/portals*` controllers for clean public URLs.
- **Three distinct auth mechanisms** in one module: `api/v2` reuses `Api::BaseController`'s dashboard access-token/session auth ([[api-v1-controllers]]) via `AccessTokenAuthHelper`; `platform` uses its own `AccessToken` lookup scoped to `owner_type: 'PlatformApp'`; `public` has no token auth at all for the API-channel contact endpoints (identity is instead asserted via optional per-inbox HMAC) and a separate custom-domain check for the Help Center.
- **Models touched**: `Channel::Api` / `Inbox` / `ContactInbox` / `Contact` / `Conversation` / `Message` (public API-channel path — see [[models]]), `Portal` / `Category` / `Article` (Help Center), `Account` / `User` / `AgentBot` / `AccountUser` / `PlatformApp` / `PlatformAppPermissible` / `AccessToken` (platform), `Channel::Email` (email-channel-migrations).
- **Services/builders called into**: `AccountBuilder` (signup), `ContactInboxWithContactBuilder`, `ContactIdentifyAction`, `ConversationBuilder`, `MessageFinder` (see [[contacts-services]], [[conversations-services]], [[messages-services]]), `V2::Reports::*` / `V2::ReportBuilder` / `YearInReviewBuilder` (see [[reports]]).
- **Jobs enqueued**: `Conversations::UpdateMessageStatusJob` (public conversations `update_last_seen`), `DeleteObjectJob` (platform account/user `destroy`), `Avatar::AvatarFromUrlJob` (platform agent-bot avatar) — see [[jobs]].
- **Events**: `public/api/v1/inboxes/conversations_controller.rb`'s `toggle_typing` dispatches `CONVERSATION_TYPING_ON`/`CONVERSATION_TYPING_OFF` straight through `Rails.configuration.dispatcher` — see [[events-listeners]].
- **Enterprise overlay**: `Api::V2::AccountsController`, `Public::Api::V1::Portals::ArticlesController`, and `Public::Api::V1::Portals::SearchController` each end with `prepend_mod_with(...)`, giving Enterprise a splice point (e.g. Cloud-only signup/billing behavior, Enterprise Help Center article indexing — see [[controllers-jobs-listeners]]). None of the other controllers in this module call `prepend_mod_with`.
- **Authorization**: `api/v2` report controllers use Pundit (`authorize :report, :view?`, matching the account-scoped policy model in [[authorization-policies]]); `platform` and `public` controllers use no Pundit policies at all — their access control is entirely the token-ownership/HMAC checks described above.

## Product Behavior

- The `platform` namespace is the backend for the **Platform API (Account Provisioning)** capability referenced in Chatwoot's docs: it's how a hosting/reseller product creates and manages Chatwoot accounts, agents, and bots programmatically, distinct from anything an agent does inside the dashboard.
- The `public/api/v1/inboxes/*` controllers back the **API channel** ("Other channels" > API channel in the user guide) — the generic channel type for custom integrations that aren't a first-party social/messaging provider, and also the transport the website widget/mobile SDKs use for messaging. HMAC verification here (`identifier_hash`, `hmac_mandatory`) is the same identity-validation mechanism documented for widget "Identity Validation/HMAC" — confirmed present here specifically for API-channel contacts, not just the widget.
- `public/api/v1/portals/*` and the `hc/:slug` routes are the entire public-facing **Help Center** rendering layer (portal home, categories, articles, search, markdown export, view-count tracking pixel) — corresponds to the "Help Center" user-guide category (setup, custom domain, analytics). `ensure_portal_feature_enabled` gates this behind the `help_center` account feature, but only on Chatwoot Cloud (`ChatwootApp.chatwoot_cloud?`), not self-hosted.
- `csat_survey_controller.rb` and the CSAT-update action in `messages_controller.rb` implement the **CSAT survey** response flow the customer clicks through from an email/message link — both independently enforce a 14-day submission window.
- `api/v2/accounts/*_reports` back the dashboard's **Reports** screens (CSAT, conversations, bot, per-agent/team/inbox/label reports, and the newer "Year in Review" feature) — see the Reports category in the user guide.

## Notes for AI Agents

- `Api::V2::Accounts::ReportsController`, `SummaryReportsController`, `LiveReportsController`, and `YearInReviewsController` all inherit from `Api::V1::Accounts::BaseController`, **not** from any `Api::V2::Accounts::BaseController` — there is no v2-specific base class. Don't assume "v2" implies a parallel controller hierarchy; it's the v1 auth/locale stack (`current_account`, `validate_token_api_access`, `switch_locale_using_account_locale`) reused as-is.
- `PlatformController#set_resource` is a hard `raise` if a subclass doesn't override it — new platform controllers must define `set_resource`, and it must run before the framework's `validate_platform_app_permissible` before_action (declared `only: [:update, :show, :destroy]` in the base class) will work correctly.
- The public API-channel controllers repeat the same `@contact_inbox.hmac_verified? ? contact.conversations : contact_inbox.conversations` branch in at least three places (`ConversationsController#index`/`#set_conversation`, `InboxesController#set_conversation`). If you touch HMAC-verification logic, check all of them — there's no single shared helper.
- HMAC comparison in `contacts_controller.rb` is done with `ActiveSupport::SecurityUtils.secure_compare` after an explicit `bytesize` check — a timing-safe pattern; don't replace it with `==`.
- `Public::Api::V1::CsatSurveyController#check_csat_locked` and `Public::Api::V1::Inboxes::MessagesController#check_csat_locked` are separately implemented with the same 14-day cutoff — another place the same rule is duplicated rather than shared.
- `Platform::Api::V1::EmailChannelMigrationsController` is feature-flagged purely by `ENV['EMAIL_CHANNEL_MIGRATION']`, cast with `ActiveModel::Type::Boolean.new.cast(ENV.fetch(...))` — this is an installation-wide env var, not a per-account or per-plan `feature_enabled?` flag like most other gating in the codebase; don't confuse the two patterns.
- `PublicController` is deliberately still `ActionController::Base`, not `ActionController::API` — a comment in the file says an attempt to migrate broke a spec ("revisit in future"); don't "fix" this without checking why the earlier attempt failed.
- This pass sampled `V2::Reports::*Builder`/`YearInReviewBuilder` and `AccountBuilder` only by reference, not by reading their source — see [[reports]] for the reports-builder internals.
