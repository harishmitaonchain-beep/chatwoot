# Account, Onboarding, MFA, Sessions

## Purpose
A grab-bag of small, single-responsibility service objects that sit around account creation and the login lifecycle: validating a signup email, building the first workspace ("account"), stepping a new account through onboarding, two-factor authentication (TOTP + backup codes), tracking/limiting active user sessions, and soft-deleting accounts that were marked for removal. None of this is one cohesive "module" in the codebase — it's five independent concerns that happen to all live under `app/services/` and get touched from the signup and Devise session controllers.

## Key Files & Classes

- `app/services/account/sign_up_email_validation_service.rb` — `Account::SignUpEmailValidationService`: validates a signup email via the `valid_email2` gem (syntax + disposable-domain check) and rejects domains listed in the `BLOCKED_EMAIL_DOMAINS` global config. Raises `CustomExceptions::Account::InvalidEmail`.
- `lib/custom_exceptions/account.rb` — `CustomExceptions::Account` namespace: `InvalidEmail`, `UserExists`, `InvalidParams`, `UserErrors`, `SignupFailed`, `PlanUpgradeRequired`, `EmailLimitExceeded` (the only one with a custom `http_status` of `:too_many_requests`).
- `app/builders/account_builder.rb` — `AccountBuilder`: the actual account+user creation transaction. Validates email/uniqueness (delegating to the service above), creates the `Account` with `custom_attributes['onboarding_step'] = 'account_details'`, creates or reuses a `User`, and links them via `AccountUser` with role `administrator`.
- `app/services/onboarding/web_widget_creation_service.rb` — `Onboarding::WebWidgetCreationService`: creates (or reuses) a `Channel::WebWidget` inbox for a freshly onboarded account, deriving widget color/title/tagline from `account.custom_attributes['brand_info']` (populated by an earlier, out-of-scope enrichment step) or falling back to a website URL / account name. Declares an enterprise override point via `prepend_mod_with`.
- `enterprise/app/services/enterprise/onboarding/web_widget_creation_service.rb` — `Enterprise::Onboarding::WebWidgetCreationService`: overrides `welcome_tagline_text` to ask `Captain::Llm::WidgetTaglineService` for an LLM-generated tagline, falling back to `super` (the OSS brand_info logic) on any error.
- `app/controllers/api/v1/accounts/onboardings_controller.rb` — `Api::V1::Accounts::OnboardingsController`: drives the onboarding state machine (`account_details` → `inbox_setup` → done) purely through `account.custom_attributes['onboarding_step']`. `inbox_setup` only runs on `ChatwootApp.chatwoot_cloud?`; self-hosted finishes after `account_details`. Uses `send("complete_#{params[:onboarding_step]}")` guarded by a whitelist (`ONBOARDING_STEPS`).
- `app/models/account.rb` — `Account#onboarding_step`: reads `custom_attributes['onboarding_step']` but reports a synthetic `'enrichment'` step if a Redis key (`Redis::Alfred::ACCOUNT_ONBOARDING_ENRICHMENT`) exists, meaning an async enrichment job is still running (that job itself is outside the investigated paths).
- `app/services/mfa/authentication_service.rb` — `Mfa::AuthenticationService`: single entry point to verify either an OTP code (via Devise's `validate_and_consume_otp!`) or a backup code (delegating to `Mfa::ManagementService`).
- `app/services/mfa/management_service.rb` — `Mfa::ManagementService`: owns the full OTP lifecycle — enable/disable, provisioning URI, backup-code generation (10 codes, `SecureRandom.hex(4).upcase`), backup-code validation with constant-time comparison (`ActiveSupport::SecurityUtils.secure_compare`) and burn-on-use (marks a code `'XXXXXXXX'`).
- `app/services/mfa/token_service.rb` — `Mfa::TokenService < BaseTokenService`: short-lived (5 minute) JWT that represents "this user passed password auth, now needs MFA" — carries only `user_id` + `exp`.
- `app/services/base_token_service.rb` — `BaseTokenService`: generic JWT encode/decode helper (`HS256`, signed with `Rails.application.secret_key_base`); swallows `JWT::ExpiredSignature`/`JWT::DecodeError` into an empty hash.
- `app/controllers/devise_overrides/sessions_controller.rb` — `DeviseOverrides::SessionsController < DeviseTokenAuth::SessionsController`: the real center of gravity for this page. Handles password login, MFA challenge/verify, SSO-token login (impersonation included), a session-limit picker (`MAX_USER_SESSIONS`, default 25) that lets the client evict a specific session or all sessions, and post-login session tracking.
- `app/controllers/api/v1/profile/mfa_controller.rb` — `Api::V1::Profile::MfaController`: self-service MFA enable/verify/disable/backup-codes endpoints, gated behind `Chatwoot.mfa_enabled?`.
- `app/services/user_session_tracking_service.rb` — `UserSessionTrackingService`: upserts a `UserSession` row per `(user, client_id)` on login (`create_or_update!`) and throttled-updates `last_activity_at` on every authenticated request (`update_activity!`). Parses UA via the `browser` gem, with a hand-rolled patch for legacy Chatwoot mobile-app user agents (`okhttp/…` for Android, `CFNetwork` for iOS — both fall back to `'Unknown Browser'` from the `browser` gem otherwise) and a header-based path (`X-Chatwoot-Client-Name` etc.) for newer mobile clients.
- `app/controllers/concerns/track_session_activity.rb` — `TrackSessionActivity` concern: `after_action` hook that calls `UserSessionTrackingService#update_activity!` on every request carrying a `client` header; failures are logged and swallowed, never surfaced to the user.
- `app/models/user_session.rb` — `UserSession`: one row per device/session (`client_id`, unique per user), holds parsed browser/platform/geo fields and `last_activity_at`. `should_update_activity?` throttles activity writes to once per `ACTIVITY_THROTTLE` (5 minutes).
- `app/services/account_deletion_service.rb` — `AccountDeletionService`: runs when an account's grace period for deletion has expired. Soft-deletes users who belong *only* to this account (rewrites their email to `"#{user.id}@chatwoot-deleted.invalid"`, skips reconfirmation) so the email can be reused elsewhere, sends a compliance notification mailer, then hands off to `DeleteObjectJob.perform_later(account)` for the actual destroy.
- `app/jobs/internal/delete_accounts_job.rb` — `Internal::DeleteAccountsJob` (scheduled): finds accounts where `custom_attributes->>'marked_for_deletion_at'` is set and in the past, and runs `AccountDeletionService` on each.
- `app/jobs/delete_object_job.rb` — `DeleteObjectJob`: generic polymorphic destroyer; pre-purges heavy associations (`conversations`, `contacts`, `inboxes`, `reporting_events` for `Account`) in batches of 5,000 before `object.destroy!`, to avoid `destroy_async` fan-out timeouts.
- `lib/tasks/mfa.rake` — ops rake tasks (`mfa:reset`, `mfa:reset_all`, `mfa:generate_backup_codes`) for support/ops to reset a locked-out user's MFA or mint new backup codes outside the UI.
- `config/application.rb` — `Chatwoot.mfa_enabled?`: MFA is only available at all when `ACTIVE_RECORD_ENCRYPTION_PRIMARY_KEY` / `..._DETERMINISTIC_KEY` / `..._KEY_DERIVATION_SALT` env vars are set (since `otp_secret`/`otp_backup_codes` are `encrypts`-ed columns on `User`). No feature flag — it's an environment/deployment gate.

## How It Fits Together

- **Signup**: `AccountBuilder` (called from wherever public signup / omniauth callback lives — see `app/controllers/devise_overrides/omniauth_callbacks_controller.rb`) → `Account::SignUpEmailValidationService` → creates `Account` + `User` + `AccountUser` in one transaction → fires `ACCOUNT_CREATED` via `Rails.configuration.dispatcher` (see [[events-listeners]]) from `Account#notify_creation`.
- **Onboarding**: `Api::V1::Accounts::OnboardingsController` drives `Account.custom_attributes['onboarding_step']` forward; on the cloud-only `inbox_setup` step it calls `Onboarding::WebWidgetCreationService`, which creates a `Channel::WebWidget` + `Inbox` + `InboxMember` — the inbox layer connects onward to [[whatsapp]]/[[email]]/[[other-channels]] siblings and to [[models]] (`Inbox`, `InboxMember`). The enterprise override swaps in an LLM-generated tagline via Captain (see [[captain-ai]]).
- **Login / MFA**: `DeviseOverrides::SessionsController#create` branches on MFA-verification vs SSO vs password login. Password login that hits an MFA-enabled user short-circuits into `Mfa::TokenService` (issues a 5-minute JWT) instead of signing in; the follow-up `mfa_token` + `otp_code`/`backup_code` request goes through `Mfa::AuthenticationService`, which delegates OTP checks to Devise's `two_factor_authenticatable` module on `User` and backup-code checks to `Mfa::ManagementService`. `Api::V1::Profile::MfaController` is the separate self-service path (enable/verify/disable/regenerate codes) for an already-authenticated user, not used during login.
- **Sessions**: Every successful login (`render_create_success`) calls `track_user_session`, which invokes `UserSessionTrackingService#create_or_update!`, writing/updating a `UserSession` row and enqueuing `UserSessionIpLookupJob` (see [[jobs]]) for IP geolocation. Every subsequent authenticated request (any controller including `TrackSessionActivity`) throttled-updates `last_activity_at`. `MAX_USER_SESSIONS` caps concurrent devices; when reached, browser clients get a 409 "session picker" (list of active sessions to revoke) while non-browser clients (mobile apps, API-only user agents) are silently evicted (oldest session first, using `UserSession` if tracked, else falling back to the oldest Devise token in `user.tokens`).
- **Account deletion**: something elsewhere (dashboard settings / support tooling) sets `custom_attributes['marked_for_deletion_at']` on an `Account`. The scheduled `Internal::DeleteAccountsJob` (see [[jobs]]) picks up expired ones and calls `AccountDeletionService`, which soft-deletes orphaned users' emails, sends a compliance mailer, and enqueues `DeleteObjectJob` to actually cascade-destroy the account and its heavy associations (conversations, contacts, inboxes, reporting events — see [[models]], [[conversations-services]], [[contacts-services]]).
- **Enterprise SAML** (adjacent, not in the investigated paths but relevant to product behavior): `enterprise/app/builders/saml_user_builder.rb`, `enterprise/app/models/account_saml_settings.rb`, and `enterprise/app/controllers/api/v1/accounts/saml_settings_controller.rb` provide an enterprise-only SSO path that ultimately still creates/links `User`/`AccountUser` records, parallel to the OSS `AccountBuilder` flow. Not read in depth for this page — flagged for the [[models-services]] / [[controllers-jobs-listeners]] enterprise pages instead.

## Product Behavior

- The **Creating a Chatwoot Account** guide topic maps to `AccountBuilder` + `Account::SignUpEmailValidationService` (email/domain validation, disposable-email rejection) and the onboarding-step flow in `OnboardingsController` (account details → inbox setup on Cloud, or a single step self-hosted).
- The **SAML Authentication** guide topic maps to the enterprise SAML files noted above (`account_saml_settings`, `saml_user_builder`) — not deeply investigated here.
- The **Audit Logs** guide topic is not implemented in any of the investigated files; session tracking (`UserSession`) is a device/activity list for the user's own security settings, not a general audit trail. No audit-log service was found under the investigated paths.
- The "sessions limit reached" picker (409 response with a session list, `revoke_session_id` / `revoke_all_sessions` params) is a security/device-management feature: users logging in past `MAX_USER_SESSIONS` active devices get to choose which session to sign out, mirroring typical "manage your devices" UX.

## Notes for AI Agents

- **MFA is gated by encryption key env vars, not a plan/feature flag.** `Chatwoot.mfa_enabled?` (`config/application.rb`) just checks that `ACTIVE_RECORD_ENCRYPTION_*` env vars are present, because `User#otp_secret`/`otp_backup_codes` use `encrypts`. If those env vars are missing in a dev/test environment, the whole MFA UI/API reports "unavailable" — this is an easy false negative to chase as a "bug" when it's actually missing local env config.
- **`User` delegates its MFA API to `Mfa::ManagementService` via `delegate`** (`two_factor_provisioning_uri`, `backup_codes_generated?`, `enable_two_factor!`, etc., `app/models/user.rb` lines ~179-188). Don't add MFA logic directly to `User` — it belongs in the service.
- **Backup codes are burned in place, not deleted**: `Mfa::ManagementService#mark_code_as_used` overwrites the used code with the literal string `'XXXXXXXX'` rather than removing it from the array — `find_matching_code_index` explicitly excludes `'XXXXXXXX'` entries as "already used." If you ever need to check "does this code exist," remember the sentinel value.
- **`Onboarding::WebWidgetCreationService` and `AccountDeletionService` both swallow all `StandardError`** and log-and-return-nil / continue rather than raising — by design (best-effort onboarding step, and soft-delete shouldn't block the account-level teardown), but it means failures here are silent unless someone greps logs for `[WidgetCreation]`.
- **Enterprise override point**: `Onboarding::WebWidgetCreationService.prepend_mod_with('Onboarding::WebWidgetCreationService')` is the seam Enterprise uses to swap in an LLM-generated widget tagline (`Enterprise::Onboarding::WebWidgetCreationService#welcome_tagline_text`, calling `super` on failure). Follow this same `prepend_mod_with` pattern for other account/onboarding extension points rather than editing OSS files directly.
- **Session eviction has two parallel data sources that can disagree**: `user.tokens` (a hash on the `User` row, managed by `devise_token_auth`) and `UserSession` rows (managed by `UserSessionTrackingService`, added later). `evict_oldest_session` explicitly checks `user.user_sessions.count < user.tokens.size` to detect "there are untracked legacy tokens" and falls back to evicting from `user.tokens` directly in that case — don't assume every token has a matching `UserSession`.
- **The onboarding step dispatch (`send("complete_#{params[:onboarding_step]}")`) is guarded by an explicit whitelist** (`ONBOARDING_STEPS = [STEP_ACCOUNT_DETAILS, STEP_INBOX_SETUP]`) checked *before* the `send` — if you add a new onboarding step, you must add it to this array or the controller will 422 rather than silently no-op.
- **`Account#onboarding_step` can report a value (`'enrichment'`) that never appears in `ONBOARDING_STEPS`** — it's synthesized from a Redis key set by an out-of-scope enrichment job, not from `custom_attributes` directly. Don't assume `account.onboarding_step` and `account.custom_attributes['onboarding_step']` always match.
- **`AccountDeletionService` only soft-deletes users with no other account membership** (`next if user.account_users.where.not(account_id: account.id).exists?`) — users shared across multiple accounts keep their real email and are left alone; only the account itself gets destroyed via `DeleteObjectJob`.
- I sampled rather than exhaustively reading every enterprise SAML file (`enterprise/app/builders/saml_user_builder.rb`, `enterprise/app/jobs/saml/*`, `enterprise/app/helpers/saml_authentication_helper.rb`) since they were outside the investigated paths list — flagging them here so a future pass on enterprise auth doesn't miss them.
