# Backend Support Objects (Builders, Finders, Helpers, Admin Fields)

## Purpose

This page covers six small, non-`app/models` / non-`app/services` directories that Rails' loose conventions leave scattered around the app tree. None of them is large individually, but together they form the "plumbing" layer that other subsystems (controllers, services, jobs) lean on constantly:

- `app/builders` — plain Ruby objects that assemble a single new record (or small graph of records) from request params, encapsulating creation logic that's too involved for a model callback or a one-line `Model.create!`.
- `app/finders` — plain Ruby objects that turn controller params into a filtered/sorted/paginated ActiveRecord scope, keeping that logic out of controllers.
- `app/fields` and `app/dashboards` — [Administrate](https://github.com/thoughtbot/administrate) gem customizations that power the Rails **Super Admin** panel (`/super_admin`).
- `app/drops` — [Liquid](https://github.com/Shopify/liquid) `Drop` classes that expose safe, whitelisted attributes of Chatwoot models (`{{contact.name}}`, `{{agent.first_name}}`, etc.) to Liquid templates used in outgoing messages and campaigns.
- `app/helpers` — a grab-bag of Rails view/controller helper modules; in Chatwoot's API-only-ish usage most of these are `include`d into controllers or PORO builders rather than used in ERB views.

## Key Files & Classes

### Builders (`app/builders`)
- `app/builders/account_builder.rb` — `AccountBuilder` creates an `Account` + `User` + `AccountUser` (administrator role) in a transaction; used at signup. Raises `CustomExceptions::Account::UserExists`/`UserErrors`.
- `app/builders/agent_builder.rb` — creates a `User` and links it to an account as an agent; extended by `enterprise/app/builders/enterprise/agent_builder.rb`.
- `app/builders/contact_inbox_builder.rb` — `ContactInboxBuilder` derives the right `source_id` per channel type (WhatsApp strips the `+`, Twilio prefixes `whatsapp:`, email/SMS use the raw value, API/WebWidget get a `SecureRandom.uuid`) and creates the `ContactInbox`, with a documented race-condition retry path (`RecordNotUnique` → mutate the colliding row's `source_id` → retry). Extended by `enterprise/app/builders/enterprise/contact_inbox_builder.rb`.
- `app/builders/contact_inbox_with_contact_builder.rb` — `ContactInboxWithContactBuilder` finds-or-creates a `Contact` (by identifier → email → phone →, for Instagram, a shared Facebook-page contact match) and delegates inbox-linking to `ContactInboxBuilder`. Note the Instagram special case: it intentionally reuses a contact created via `Channel::FacebookPage` but still creates a *fresh* `ContactInbox`.
- `app/builders/conversation_builder.rb` — `ConversationBuilder` either reuses the contact_inbox's last conversation (when `inbox.lock_to_single_conversation?`) or creates a new one.
- `app/builders/messages/message_builder.rb` — `Messages::MessageBuilder`, the single largest builder. Builds a `Message` from controller params: resolves `sender` (agent, `AgentBot`, or contact for incoming), attaches uploaded files, tags voice messages, populates `cc_emails`/`bcc_emails`/`to_emails` for email inboxes, and — for outgoing/template messages on email inboxes — runs the message content through Liquid (`Liquid::Template.parse` + `drops_with_sender`, rescuing `Liquid::Error` silently) before building `content_attributes[:email][:html_content|:text_content]`. Extended by `enterprise/app/builders/enterprise/messages/message_builder.rb`.
- `app/builders/messages/{facebook,instagram,messenger}/message_builder.rb` — per-channel inbound message builders (not read in full during this pass; same "build a Message from a webhook payload" shape as the base builder).
- `app/builders/email/base_builder.rb`, `from_builder.rb`, `reply_to_builder.rb` — compute the `From`/`Reply-To` headers for outgoing email based on the channel's IMAP/SMTP/OAuth/forwarding configuration (`Email::FromBuilder` has an explicit case-statement over connection type: standard IMAP+SMTP, Google/Microsoft OAuth, "forwarding with own SMTP", "IMAP with Chatwoot-managed SMTP", falling back to the account's support email if the channel's own address isn't `verified_for_sending`).
- `app/builders/notification_builder.rb` — `NotificationBuilder` creates a `Notification`, gated by three checks: the user's `NotificationSetting` (only for `conversation_creation`), the contact not being blocked (except for mentions), and a live `ConversationPolicy#show?` check so a user is never notified about a conversation they can't access.
- `app/builders/notification_subscription_builder.rb`, `campaigns/campaign_conversation_builder.rb`, `csat_surveys/response_builder.rb`, `year_in_review_builder.rb` — narrower single-purpose builders (not read in depth; names are self-describing and match the pattern above).
- `app/builders/v2/**` — the V2 reporting builder tree (`V2::ReportBuilder` plus `V2::Reports::*SummaryBuilder`/`*TimeseriesBuilder`/`DrilldownBuilder` classes). `V2::ReportBuilder` is the entry point for the legacy-compatible report API (`timeseries`, `summary`, `bot_summary`, `conversation_metrics`); the `Reports/` subtree builds per-dimension (agent/inbox/team/label/channel) summaries on top of `Reports::DataSource`. This tree is large (18 files) — treated here as one unit and cross-referenced to [[reports]] rather than enumerated file-by-file.

### Finders (`app/finders`)
- `app/finders/conversation_finder.rb` — `ConversationFinder`, the backbone of the conversation list API. Applies inbox scoping (from the current user's `assigned_inboxes`), delegates account-wide visibility to `Conversations::PermissionFilterService`, then chains status/team/label/query/source_id filters and a `SORT_OPTIONS` table (`last_activity_at`, `created_at`, `priority`, `waiting_since`, `unread`, plus deprecated aliases marked "to be removed in v3.5.0"). Computes `mine_count`/`unassigned_count`/`all_count` with a single `FILTER (WHERE ...)` SQL query when the base scope has no limit/offset/eager-load applied, falling back to three separate `.count` calls (`legacy_count_for_all_conversations`) otherwise. Extended by `enterprise/app/finders/enterprise/conversation_finder.rb`.
- `app/finders/message_finder.rb` — `MessageFinder` implements cursor-style pagination over a conversation's messages using `before`/`after` message IDs (not timestamps), with different page sizes per direction (`after`: 100, `before`: 20, `between`: 1000, default "latest": 20). Extended by `enterprise/app/finders/enterprise/message_finder.rb`.
- `app/finders/notification_finder.rb` — filters/paginates a user's notifications by `snoozed`/`read` inclusion flags passed as `params[:includes]`.
- `app/finders/email_channel_finder.rb` — `EmailChannelFinder` resolves which `Channel::Email` an inbound email belongs to. Checks `To`/`Cc`/`X-Original-To` headers first, then falls back to `Bcc` recipients — but BCC-derived matches can be disabled per-account via the `SKIP_INCOMING_BCC_PROCESSING` global config (comma-separated account IDs).
- `app/finders/data_import_error_finder.rb`, `data_import_skip_log_finder.rb` — narrow finders for the contact CSV import UI (see [[data-import]]).
- `enterprise/app/finders/call_finder.rb`, `enterprise/app/finders/captain/faq_suggestion_finder.rb` — enterprise-only finders with no OSS counterpart.

### Admin Fields & Dashboards (`app/fields`, `app/dashboards`)
Both directories are [Administrate](https://github.com/thoughtbot/administrate) gem extension points (`gem 'administrate'`, `Gemfile:97`) that drive the Rails **Super Admin** panel, mounted at `/super_admin` via `devise_for :super_admins` in `config/routes.rb`.

- `app/dashboards/*_dashboard.rb` — one `Administrate::BaseDashboard` subclass per admin-manageable model (`AccountDashboard`, `UserDashboard`, `AgentBotDashboard`, `AccountUserDashboard`, `AccessTokenDashboard`, `InstallationConfigDashboard`, `PlatformAppDashboard`, `PlatformBannerDashboard`). Each declares `ATTRIBUTE_TYPES`, `COLLECTION_ATTRIBUTES` (index page), `SHOW_PAGE_ATTRIBUTES`, `FORM_ATTRIBUTES`, and `COLLECTION_FILTERS` (typeahead search-field filters like `active:`/`suspended:`/`recent:`). `AccountDashboard` is the most elaborate: it conditionally merges in enterprise-only fields (`limits`, `all_features`, `captain_models`, and — Chatwoot-Cloud-only — `manually_managed_features`) gated by `ChatwootApp.enterprise?` / `ChatwootApp.chatwoot_cloud?`, and overrides `permitted_attributes` to allow the enterprise hash/array params through strong params.
- `app/fields/*.rb` — custom `Administrate::Field::*` subclasses used by the dashboards above: `AccountStatusField` (adds suspension-category dropdown + `original_status`/`latest_suspension` helpers for the suspend/unsuspend form), `AvatarField`, `ConfirmedAtField`, `CountField` (renders `data.count` — used for `users`/`conversations`/`accounts` counts on index pages), `SecretField`, `SerializedField` (renders Hash/Array JSON columns), `SuspensionHistoryField` (renders the account's suspension audit trail).
- `enterprise/app/fields/*.rb` — `AccountFeaturesField`, `AccountLimitsField` (merges account-level limit overrides — `agents`, `inboxes`, `captain_responses`, `captain_documents`, `emails` — over `nil` defaults and renders as JSON), `CaptainModelOverridesField`, `ManuallyManagedFeaturesField` — all enterprise-only, referenced conditionally from `AccountDashboard`.

### Liquid Drops (`app/drops`)
- `app/drops/base_drop.rb` — `BaseDrop < Liquid::Drop`; every drop wraps a single `@obj` and exposes `id`/`name` via `.try` (so a `nil` object never raises inside a template).
- `app/drops/{account,contact,conversation,inbox,message,user}_drop.rb` — one drop per model exposed to templates. Notable behavior: `ContactDrop`/`UserDrop#name` title-cases each word of the stored name; `ContactDrop#custom_attribute` stringifies keys of `custom_attributes` for Liquid lookup; `ConversationDrop#id` overrides the base and returns `display_id` (the human-facing conversation number, not the PK); `ConversationDrop#recent_messages` renders each message through `MessageFormatHelper` (Markdown → sanitized HTML) and pulls in mention transforms; `InboxDrop#email` falls back from `email_address` to `channel.email`.
- `enterprise/app/drops/sla_policy_drop.rb` — enterprise-only SLA policy drop.
- The drops are assembled into a `{'contact' => ..., 'agent' => ..., 'conversation' => ..., 'inbox' => ..., 'account' => ...}` hash by three different call sites, each slightly different: `Liquidable#message_drops` (`app/models/concerns/liquidable.rb`, used for message content), `Liquid::CampaignTemplateService#message_drops` (campaigns — no `conversation` key, since a campaign fires before a conversation exists), and `EmailHelper#message_drops` (used by `Messages::MessageBuilder` for email HTML/text rendering).

### Helpers (`app/helpers`)
Not exhaustively enumerated (33 files); grouped by what they back:
- **Content/message rendering**: `message_format_helper.rb` (`MessageFormatHelper` — Markdown mention transform via CommonMark, `render_message_content` → `ChatwootMarkdownRenderer`), `email_helper.rb` (email address normalization + the `message_drops` builder above), `data_helper.rb` (`ensure_indifferent_access`, `convert_to_hash`, `safe_parse_json` — small JSON/hash coercion utilities shared by builders).
- **Contact/name parsing**: `contact_helper.rb` — `parse_name` splits a free-text full name into first/last, handling single-word names and conjunctions ("and", "&") in a name string.
- **File/attachment typing**: `file_type_helper.rb` — maps a content-type string to Chatwoot's internal `file_type` enum (`image`/`video`/`audio`/`file`/etc.), including a signed-ID lookup path (`file_type_by_signed_id`) for pre-uploaded attachments.
- **Reporting**: `date_range_helper.rb`, `report_helper.rb`, `reporting_event_helper.rb` (business-hours-aware "last non-human activity" calc), `helpers/api/v2/accounts/{heatmap_helper,reports_helper}.rb` — consumed by [[reports]].
- **API controller helpers**: `helpers/api/base_helper.rb`, `helpers/api/v1/{agents,canned_responses,conversations,inboxes}_helper.rb`, `helpers/api/v1/widget/messages_helper.rb`. `Api::V1::InboxesHelper` is the largest — it live-validates IMAP/SMTP credentials when creating/editing an email channel by opening a real `Net::IMAP`/`Net::SMTP` connection and mapping connection errors to translated `errors.inboxes.imap.*`/`errors.inboxes.smtp.*` messages.
- **Super Admin UI**: `super_admin/features_helper.rb` (loads `app/helpers/super_admin/features.yml` — the list of premium/enterprise features shown in the super admin UI — and formats the current `ChatwootHub.pricing_plan` badge text), `super_admin/navigation_helper.rb`, `super_admin/account_features_helper.rb`.
- **Third-party integration helpers**: `instagram/integration_helper.rb`, `linear/integration_helper.rb`, `shopify/integration_helper.rb`, `tiktok/integration_helper.rb` — see [[integrations]].
- **Misc**: `application_helper.rb` (locale list, `feature_help_urls` from `config/features.yml`), `frontend_urls_helper.rb` (`frontend_url` — builds a Vue-app URL from `root_url`), `billing_helper.rb` (plan/subscription display helpers), `timezone_helper.rb`, `cache_keys_helper.rb`, `portal_helper.rb` (Help Center portal theming/OG-image/link helpers — see [[portal-survey-superadmin]]), `widget_helper.rb`, `filters/filter_helper.rb`, `home_helper.rb` (empty module — no methods defined).
- `enterprise/app/helpers/` — `saml_authentication_helper.rb` and the `captain/*` helpers (`chat_helper`, `chat_response_helper`, `chat_generation_recorder`, `firecrawl_helper`) back [[captain-ai]].

## How It Fits Together

- **Builders** are called from controllers and services throughout the request lifecycle: `Messages::MessageBuilder` is invoked from `Api::V1::Accounts::Conversations::MessagesController` and from inbound-channel processing — see [[messages-services]]. `ContactInboxBuilder`/`ContactInboxWithContactBuilder` are the shared entry point for turning a webhook payload into a `Contact`+`ContactInbox`, used across [[whatsapp]], [[facebook-instagram]], and [[other-channels]]. `ConversationBuilder` is what channel-listeners call to open (or reuse) a conversation — see [[conversations-services]] and [[events-listeners]].
- **`AccountBuilder`** is the object behind account signup — see [[account-onboarding]].
- **`NotificationBuilder`** feeds [[notifications]] and is gated by the same `ConversationPolicy` used in [[authorization-policies]].
- **`ConversationFinder`** underlies the conversation list endpoint documented in [[api-v1-controllers]], and its `Conversations::PermissionFilterService` dependency ties it to [[authorization-policies]] / role-based visibility rules.
- **`V2::ReportBuilder`** and the `app/builders/v2/reports/**` tree are the backend for [[reports]]; this page only summarizes them at a high level since [[reports]] is the authoritative page for that subsystem.
- **Drops + Liquid** are the mechanism behind "template variables" in outgoing messages, canned responses, and campaigns — the product-facing feature documented in the official guide as **Template variables**. They're consumed from `Liquidable` (a model concern, see [[models]]), `Messages::MessageBuilder` (this page), and `Liquid::CampaignTemplateService`. Related: [[macros]], [[automation-rules]] (which can also inject dynamic content into messages).
- **Fields + Dashboards** are the entire implementation of the Rails Super Admin panel; see [[portal-survey-superadmin]] for the surrounding controllers, and note that enterprise-only admin fields (`AccountLimitsField`, `AccountFeaturesField`, `CaptainModelOverridesField`, `ManuallyManagedFeaturesField`) are conditionally wired in from OSS `AccountDashboard` via `ChatwootApp.enterprise?`/`ChatwootApp.chatwoot_cloud?` checks rather than an enterprise override of the dashboard class itself.
- Several classes in `app/builders`, `app/finders`, and `enterprise/app/fields` are `prepend_mod_with`-extended (`ContactInboxBuilder`, `Messages::MessageBuilder`, `AgentBuilder`, `ConversationFinder`, `MessageFinder`) — the standard Chatwoot pattern for enterprise behavior injection also seen in [[models-services]] and [[controllers-jobs-listeners]].

## Product Behavior

- **Liquid template variables**: the drops in `app/drops` are the literal implementation of the "Template variables" feature described in the official user guide (Advanced features → Template variables) — the `{{contact.name}}`, `{{agent.first_name}}`, `{{conversation.custom_attribute.x}}` syntax available in canned responses, automation actions, and outgoing message content.
- **Super Admin panel**: `app/fields`/`app/dashboards` implement the Enterprise Edition super admin panel referenced in the product guide's "Other topics → Enterprise Edition" and "Best practices" material — account suspension (with categorized reasons and an audit history shown via `SuspensionHistoryField`), per-account feature/limit overrides, and platform app management. This is an operator-facing tool (Chatwoot Cloud / self-hosted admin), not an end-user-facing feature.
- **Contact/email/IMAP validation** (`Api::V1::InboxesHelper`): backs the "Email channel" setup flow's live connection test when an admin configures IMAP/SMTP for a self-hosted mailbox.
- **Builders/Finders** (`ConversationFinder`, `MessageFinder`, `ContactInboxBuilder`, etc.) are internal plumbing with no direct 1:1 product-guide page — they implement behavior (conversation list sorting/filtering, message pagination, channel-specific contact identity) that the guide describes at a higher level in "Chatwoot 101" and the various channel setup guides, without naming these classes.

## Notes for AI Agents

- `pattr_initialize` (from the `attr_extras`/`pattr` pattern already established elsewhere in the codebase) is used heavily across `app/builders` for lightweight required/optional constructor args (e.g. `pattr_initialize [:contact, :inbox, :source_id, { hmac_verified: false }]`) — don't assume standard `initialize` when reading a builder; check for this macro first.
- `ContactInboxBuilder#create_contact_inbox` has a real, documented race-condition handler: on `ActiveRecord::RecordNotUnique` it mutates the *conflicting* row's `source_id` to a randomized value and retries, rather than raising. The comment in the file explains this is a workaround for a modeling flaw (contact_inbox conflated with "session"), not a permanent fix — relevant background if you're investigating duplicate-contact bugs (see the `WhatsApp coexistence duplicate conversation` case in memory).
- `ConversationFinder#set_count_for_all_conversations` has two code paths: a single-query `FILTER (WHERE ...)` fast path, and a 3-query fallback (`legacy_count_for_all_conversations`) used whenever the scope already has `limit`/`offset`/eager-loading applied (because `FILTER` on a limited/offset scope would double-apply the limit). Don't "simplify" this into one path without checking both call sites.
- `MessageFinder` is `id`-based cursor pagination, **not** timestamp-based — `before`/`after` params are message IDs compared with `<`/`>`. This matters if a caller ever tries to pass a timestamp instead (per the `messages.id ≠ created_at order` gap already tracked in memory, `id` ordering is not guaranteed to correlate with `created_at` on imported data).
- `Messages::MessageBuilder`'s Liquid processing (`process_liquid_in_email_body`) silently rescues `Liquid::Error` and falls back to the unprocessed content — a malformed `{{...}}` expression in a canned response or template will not raise, it will just render literally.
- `EmailChannelFinder`'s BCC fallback path is gated by the `SKIP_INCOMING_BCC_PROCESSING` **global config** (an admin-configurable installation-wide setting, comma-separated account IDs) — if inbound email via BCC silently stops working for one account, check this config before assuming a code regression.
- `app/dashboards/account_dashboard.rb` shows the established pattern for OSS/enterprise field wiring in Administrate dashboards: rather than an enterprise override class, OSS code directly branches on `ChatwootApp.enterprise?` / `ChatwootApp.chatwoot_cloud?` to merge in enterprise-only `ATTRIBUTE_TYPES`/`SHOW_PAGE_ATTRIBUTES`/`FORM_ATTRIBUTES`/`permitted_attributes`. This is a deliberate deviation from the `prepend_mod_with` convention used elsewhere — worth knowing if you're adding a new admin-manageable enterprise attribute.
- `app/helpers/home_helper.rb` is an empty module — a Rails-generated stub with no methods, kept only because Rails autoload conventions expect a helper module per controller.
- Files not read in full during this investigation (sampled by name/shape only, same pattern as their siblings): the per-channel builders under `app/builders/messages/{facebook,instagram,messenger}/`, most of `app/builders/v2/reports/**` (18 files), `app/builders/campaigns/campaign_conversation_builder.rb`, `app/builders/csat_surveys/response_builder.rb`, `app/builders/year_in_review_builder.rb`, `app/builders/notification_subscription_builder.rb`, and several `app/helpers/api/v2/accounts/*` and integration helpers.
