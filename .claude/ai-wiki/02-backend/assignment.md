# Assignment & Round Robin

## Purpose

Decides which agent a conversation gets assigned to, automatically. Chatwoot has two parallel auto-assignment systems that live side by side and are picked per-inbox at runtime:

- **Legacy ("V1") synchronous assignment** — runs inline inside the `Conversation` save callback chain, assigns one conversation at a time as it opens.
- **Assignment V2 (bulk, policy-driven)** — a Sidekiq job that scans an inbox's unassigned backlog and assigns agents in bulk, driven by an `AssignmentPolicy` record and (Enterprise only) `AgentCapacityPolicy` capacity limits.

Both systems ultimately hand off to the same Redis-backed round-robin queue per inbox (`AutoAssignment::InboxRoundRobinService`) so agent rotation order is shared regardless of which path triggered the assignment.

## Key Files & Classes

- `app/services/auto_assignment/assignment_service.rb` — `AutoAssignment::AssignmentService`: the V2 bulk assigner. `perform_bulk_assignment(limit:)` pulls an inbox's unassigned/open conversations (oldest-first or longest-waiting-first per policy), filters candidate agents by team/rate-limit, round-robins a pick, and atomically claims the conversation row with `SELECT ... FOR UPDATE SKIP LOCKED` before assigning — so two overlapping job runs can't double-assign the same conversation. `prepend_mod_with('AutoAssignment::AssignmentService')` is the Enterprise extension point.
- `app/services/auto_assignment/agent_assignment_service.rb` — `AutoAssignment::AgentAssignmentService`: the V1 legacy single-conversation assigner, used both for auto-assignment-on-open and for team-based assignee resolution. Re-locks the conversation row inside a transaction, re-checks `reassignment_still_needed?` (skips if already assigned to a bot or to a still-valid inbox member), then writes through the original `conversation` instance (not the locked clone) so ActiveRecord callbacks registered on it still fire.
- `app/services/auto_assignment/inbox_round_robin_service.rb` — `AutoAssignment::InboxRoundRobinService`: owns the per-inbox Redis list that tracks rotation order (`Redis::Alfred::ROUND_ROBIN_AGENTS` key, formatted per `inbox_id`). `available_agent(allowed_agent_ids:)` pops the next id from the intersection of the queue and the allowed set, then pushes it back to the tail (classic round-robin via a rotating list). Self-heals via `validate_queue?`/`reset_queue` if the queue's membership has drifted from `inbox.inbox_members`. Also exposes queue lifecycle hooks called from model callbacks (`add_agent_to_queue`, `remove_agent_from_queue`, `clear_queue`).
- `app/services/auto_assignment/round_robin_selector.rb` — `AutoAssignment::RoundRobinSelector`: thin adapter used by the V2 path — takes an `inbox_members` relation, maps to user ids, and asks `InboxRoundRobinService` for the next agent.
- `app/services/auto_assignment/rate_limiter.rb` — `AutoAssignment::RateLimiter`: per-inbox-per-agent fair-distribution cap for V2. Uses a Redis key-per-assignment pattern (`Redis::RedisKeys::ASSIGNMENT_KEY`/`ASSIGNMENT_KEY_PATTERN`) with a TTL equal to the policy's `fair_distribution_window` (default 5 minutes / `AssignmentPolicy` DB default 3600s — the service's own hardcoded fallback and the model column default disagree, see Notes), counting live keys against `fair_distribution_limit` (default 5, or the policy's value).
- `app/models/assignment_policy.rb` / `app/models/inbox_assignment_policy.rb` — `AssignmentPolicy` (per-account, named policy: `conversation_priority` enum `earliest_created`/`longest_waiting`, `assignment_order` enum `round_robin` — OSS only has `round_robin`, Enterprise adds `balanced` via `enterprise/app/models/enterprise/concerns/assignment_policy.rb`; `exclude_older_than_hours`, `fair_distribution_limit/window`) and `InboxAssignmentPolicy` (join table, one policy per inbox — `inbox_id` is uniquely constrained).
- `app/models/concerns/auto_assignment_handler.rb` — `AutoAssignmentHandler`: `Conversation` concern, `after_save :run_auto_assignment`. Branches on `inbox.auto_assignment_v2_enabled?` — V2 enqueues `AutoAssignment::AssignmentJob` (fire-and-forget bulk pass over the inbox); V1 calls `AgentAssignmentService` synchronously for the single conversation that just changed. Also fires on resolve/snooze transitions (V2 only) so the job can redistribute freed-up capacity, not just on open.
- `app/models/concerns/assignment_handler.rb` — `AssignmentHandler`: `Conversation` concern that handles *team* assignment. `before_save :ensure_assignee_is_from_team` clears an assignee that no longer belongs to the newly-set team and, if `team.allow_auto_assign`, picks a replacement via `AgentAssignmentService#find_assignee` scoped to team members with capacity. Also dispatches `ASSIGNEE_CHANGED`/`TEAM_CHANGED` events and writes the assignment activity message after commit.
- `app/models/concerns/inbox_agent_availability.rb` — `InboxAgentAvailability`: `Inbox` concern, `available_agents` (online inbox members) and the base `member_ids_with_assignment_capacity` (no capacity filtering — plain member ids). `prepend_mod_with('InboxAgentAvailability')` extension point.
- `app/jobs/auto_assignment/assignment_job.rb` — `AutoAssignment::AssignmentJob`: Sidekiq job wrapping `AssignmentService#perform_bulk_assignment`. `enqueue_for_inbox` coalesces bursts: a Redis `SET NX EX` claim (`AUTO_ASSIGNMENT_IN_FLIGHT_KEY`, 5-minute TTL) ensures at most one job per inbox is in-flight at a time; the job releases its own claim (token-checked) in an `ensure` block.
- `app/jobs/auto_assignment/periodic_assignment_job.rb` — `AutoAssignment::PeriodicAssignmentJob`: scheduled sweep across every account with the `assignment_v2` feature flag, every inbox that `joins(:assignment_policy)` (**inner join** — inboxes with no assignment policy attached are silently skipped by this sweep, see Notes) and has V2 enabled, re-enqueuing `AssignmentJob` for each. This is the self-healing mechanism that catches conversations the save-callback trigger missed.
- `app/services/action_service.rb` — `ActionService#assign_agent`/`#assign_team`: the *manual*/macro/automation-rule assignment entry point (not part of auto-assignment, but shares the same `conversation.with_lock` pattern to avoid racing with `AssignmentService`'s row claim). `assign_agent` resolves `'nil'` → unassign, `'last_responding_agent'` → last non-private outgoing message's sender, otherwise validates the agent is an inbox member or account admin and confirmed before assigning.
- Enterprise overlay (`enterprise/app/services/enterprise/auto_assignment/`): `Enterprise::AutoAssignment::AssignmentService` (prepended into the OSS service) adds policy-driven `assignment_config`, capacity filtering, and switches to `BalancedSelector` when the policy's `assignment_order` is `balanced` **and** the account has the `advanced_assignment` feature flag; `CapacityService#agent_has_capacity?` checks an agent's `AgentCapacityPolicy` → `InboxCapacityLimit` against their current open-conversation count in that inbox; `BalancedSelector` picks the agent with the fewest open conversations in the inbox instead of rotating a queue. `Enterprise::Inbox#member_ids_with_assignment_capacity` (prepended into `Inbox`) adds V1 max-assignment-limit filtering and V2 capacity filtering.

## How It Fits Together

- **Models touched**: `Conversation` (assignee_id, status, team_id), `Inbox` (`enable_auto_assignment`, `auto_assignment_config`, `assignment_policy` via `InboxAssignmentPolicy`), `InboxMember` (queue membership — `after_create`/`after_destroy` push/pop the round-robin Redis queue directly, see `app/models/inbox_member.rb`), `Team`, `AssignmentPolicy`, and Enterprise's `AgentCapacityPolicy`/`InboxCapacityLimit`.
- **Events fired**: `Events::Types::ASSIGNEE_CHANGED` (dispatched both by `AssignmentHandler#notify_assignment_change` on any conversation save, and explicitly by `AutoAssignment::AssignmentService#dispatch_assignment_event` after a V2 bulk claim) and `TEAM_CHANGED`. These feed [[events-listeners]] and downstream notification/webhook delivery — see [[notifications]].
- **Jobs enqueued**: `AutoAssignment::AssignmentJob` (per-inbox bulk pass, Redis-coalesced) and `AutoAssignment::PeriodicAssignmentJob` (scheduled account/inbox sweep) — see [[jobs]].
- **What calls into it**: `Conversation`'s `after_save`/`before_save` callbacks (`AutoAssignmentHandler`, `AssignmentHandler`) are the primary trigger on status/team changes. `ActionService#assign_agent`/`#assign_team` (invoked by [[automation-rules]] and [[macros]]) is the manual-assignment path and deliberately does not go through either auto-assignment service — it just writes `assignee_id` under a row lock.
- **Feature gating**: V2 is gated by the account-level `assignment_v2` feature flag (checked via `inbox.auto_assignment_v2_enabled?` → `account.feature_enabled?('assignment_v2')`) *and* an inbox needing an `AssignmentPolicy` attached (`inbox.assignment_policy`) to get periodic self-healing sweeps. `advanced_assignment` (Enterprise) additionally gates the `balanced` selector and agent-capacity filtering.
- **Redis dependency**: both round-robin ordering and rate limiting are Redis-backed (`Redis::Alfred`, `Redis::RedisKeys`), not DB-backed — restarting Redis or flushing it resets round-robin order and rate-limit windows (the queue self-heals from `inbox_members` on next read via `validate_queue?`, but the rate limiter has no such reconciliation — it just starts counting from zero).

## Product Behavior

- The **Advanced Assignment Policies** user-guide topic covers exactly the `AssignmentPolicy` model surfaced here: naming a policy, choosing round-robin vs. balanced assignment order (`balanced` is Enterprise/`advanced_assignment`-gated), conversation priority (earliest-created vs. longest-waiting), the stale-backlog age exclusion, and fair-distribution rate limiting — all fields read directly off `AssignmentPolicy` by `AutoAssignment::AssignmentService`.
- The **Agent Capacity Policies** guide topic maps to `AgentCapacityPolicy`/`InboxCapacityLimit` (Enterprise) — per-agent, per-inbox open-conversation limits enforced by `Enterprise::AutoAssignment::CapacityService`, plus the policy's own label/age exclusion rules layered on top of the assignment policy's exclusions.
- The **round-robin best practice** guide article describes the rotation behavior implemented by `InboxRoundRobinService`: agents are assigned in a rotating order, an agent who just received a conversation moves to the back of the queue, and only online agents with a capacity-eligible inbox membership are eligible.
- Both auto-assignment systems are configured from Inbox settings (`enable_auto_assignment` toggle) and, for V2, from Account-level Assignment Policy management — this is distinct from the `agent collision prevention` feature (mentioned in the guide's "Features explained" section), which is a UI-layer concern, not something this module implements.

## Notes for AI Agents

- **Two systems, one queue.** Don't assume `AutoAssignment::AssignmentService` (V2) is the only assignment path — `AgentAssignmentService` (V1) is still live and is what many accounts without the `assignment_v2` feature flag actually run. Both read/write the same `InboxRoundRobinService` Redis queue, so changes to queue semantics affect both.
- **Enterprise extension is `prepend_mod_with`, not `include_mod_with`, for `AssignmentService`.** `Enterprise::AutoAssignment::AssignmentService` is *prepended*, so its `find_available_agent`/`unassigned_conversations` overrides run before (and call `super` into) the OSS versions — read the prepended module first when tracing V2 behavior on an Enterprise install.
- **`assignment_config` in the Enterprise `AssignmentService` module appears unused** — it's defined but no caller in the OSS or Enterprise service was found calling it during this investigation; don't assume it's wired into `perform_bulk_assignment`'s behavior without re-checking.
- **`PeriodicAssignmentJob` uses an inner join on `assignment_policy`.** An inbox with V2 enabled but no `AssignmentPolicy` attached gets zero periodic sweep coverage — it only gets assigned via the save-callback trigger (`AutoAssignmentHandler`), so if that trigger is ever missed (e.g. a rolled-back save, a race), the conversation can sit unassigned indefinitely. See `reference_assignment_periodic_sweep_requires_policy.md` in project memory for a prior investigation of this exact gap.
- **Two independent SKIP LOCKED / row-lock disciplines, not one.** `AssignmentService#claim_and_assign` uses `lock('FOR UPDATE SKIP LOCKED')` to avoid blocking across overlapping bulk-job runs; `ActionService` and `AssignmentHandler`'s team-reassignment path use plain `with_lock`/`Conversation.lock.find_by`. They coexist correctly (both take `FOR UPDATE` under the hood) but read the code expecting *blocking* locks outside `AssignmentService` itself — only the bulk path opts into skip-locked semantics.
- **Rate limiter's window default silently diverges from the policy model's column default.** `AutoAssignment::RateLimiter#window` falls back to `5.minutes.to_i` (300s) when no policy is set, but `AssignmentPolicy.fair_distribution_window` defaults to `3600` (1 hour) at the DB level. These only diverge when there's no `AssignmentPolicy` at all (`inbox.assignment_policy` is nil) — worth double-checking if you see rate-limit windows that don't match a customer's configured policy.
- **`AgentAssignmentService#perform` writes through the original `conversation` object, not the row it locks.** It locks a *separate* `Conversation.lock.find_by(id:)` instance purely to decide eligibility, then calls `conversation.update(assignee: ...)` on the caller's original instance — this is deliberate (so callbacks registered on that instance fire) but means the eligibility check and the write are against two different in-memory objects; don't "simplify" this by writing through the locked instance.
- **In-flight job coalescing is best-effort, not a hard mutex.** `AssignmentJob.enqueue_for_inbox`'s Redis `SET NX` claim has a 5-minute TTL and is explicitly documented in `AssignmentService` comments as something that "can lapse on TTL" — the `FOR UPDATE SKIP LOCKED` claim inside `claim_and_assign` is the actual correctness guarantee against double-assignment, not the in-flight gate.
- **`Current.executed_by`** is set to `inbox.assignment_policy || inbox` around the claim-and-assign transaction in V2 — this is almost certainly for activity-message/audit attribution (who/what performed the assignment); check `Current` usage elsewhere (e.g. activity message generation) before changing this line.
