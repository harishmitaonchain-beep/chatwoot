# Event Dispatcher & Listeners

## Purpose
Chatwoot's internal pub/sub layer. Models, controllers, and services fire named domain events (`conversation.created`, `message.created`, `assignee.changed`, etc.) through a single `Dispatcher` singleton, which fans each event out to a fixed list of listener singletons. Listeners are the decoupling point between "something happened to a record" and everything that must react to it: ActionCable broadcasts to the dashboard/widget, outgoing webhooks, agent bot webhooks, automation rule evaluation, notifications, CSAT surveys, campaign conversation creation, reporting-event/analytics rows, and conversation-participant bookkeeping. It is built on the `wisper` gem (v2.0.0), not ActiveSupport::Notifications or Rails' own pub/sub.

## Key Files & Classes
- `lib/events/types.rb` — `Events::Types` module: the canonical registry of event-name string constants (`CONVERSATION_CREATED = 'conversation.created'`, etc.). Anything dispatching or listening includes this module or references the string directly.
- `lib/events/base.rb` — `Events::Base`: wraps `(name, timestamp, data)`; `method_name` turns `'conversation.created'` into `:conversation_created`, which is the Wisper subscriber method Ruby actually calls.
- `app/dispatchers/dispatcher.rb` — `Dispatcher` singleton (`Rails.configuration.dispatcher`, set up in `config/initializers/event_handlers.rb`). `Dispatcher.dispatch(event_name, timestamp, data, async)` is the single entry point every caller uses; it always calls both the sync and async dispatcher.
- `app/dispatchers/sync_dispatcher.rb` — publishes the event **in-process, synchronously**, immediately in the request/callback thread. Listeners: `ActionCableListener`, `AgentBotListener` (+ Enterprise `Captain::ConversationOutcomeEventListener`).
- `app/dispatchers/async_dispatcher.rb` — enqueues `EventDispatcherJob.perform_later` (Sidekiq, `:critical` queue) instead of publishing directly; the job later calls `publish_event`, which does the real Wisper `publish`. Listeners: `AutomationRuleListener`, `CampaignListener`, `CsatSurveyListener`, `HookListener`, `InstallationWebhookListener`, `NotificationListener`, `ParticipationListener`, `Conversations::UnreadCounts::Listener`, `ReportingEventListener`, `WebhookListener` (+ Enterprise `CaptainListener`, `Captain::ReportingEventListener`).
- `app/dispatchers/base_dispatcher.rb` — `include Wisper::Publisher`; `load_listeners` subscribes every listener in the `listeners` array (called once per boot from the initializer, via `config.to_prepare`).
- `app/jobs/event_dispatcher_job.rb` — the Sidekiq job that performs the deferred half of async dispatch.
- `app/listeners/base_listener.rb` — `BaseListener` (`include Singleton`); shared extractor helpers (`extract_conversation_and_account`, `extract_message_and_account`, `extract_contact_and_account`, `extract_inbox_and_account`, `extract_notification_and_account`, `extract_changed_attributes`) that every listener uses to pull `event.data[...]` into typed locals.
- `app/listeners/action_cable_listener.rb` — the biggest listener; translates ~20 event types into `ActionCableBroadcastJob` pushes to per-user/per-contact pubsub tokens (dashboard + widget realtime updates). Owns token-scoping logic (agents vs. contact vs. mentioned user) and stamps `performer: Current.user&.push_event_data` on outgoing payloads.
- `app/listeners/webhook_listener.rb` — delivers account-level and inbox-level (`Channel::Api`) outgoing webhooks via `WebhookJob`, gated by `hook.subscriptions` / `account.api_and_webhooks_enabled?`.
- `app/listeners/hook_listener.rb` — drives third-party app integrations (Slack, Dialogflow, Google Translate, Leadsquared, Linear) via `HookJob`, gated by a hardcoded `supported_events_map` of app_id → allowed event names.
- `app/listeners/agent_bot_listener.rb` — delivers webhook-type Agent Bot payloads (`AgentBots::WebhookJob`) for conversation and message events, resolving both the conversation's assigned bot and the inbox's active bot.
- `app/listeners/automation_rule_listener.rb` — evaluates `AutomationRule`s per account/event via `AutomationRules::ConditionsFilterService` and runs matches through `AutomationRules::ActionService`; also implements delayed-automation "arming" (`AutomationRulePendingExecution.schedule`) gated by the `delayed_automations` feature flag.
- `app/listeners/notification_listener.rb` — builds `Notification` records (`NotificationBuilder`) for conversation creation/assignment/bot-handoff, and drives `Messages::MentionService` / `Messages::NewMessageNotificationService` on `message_created`.
- `app/listeners/reporting_event_listener.rb` — writes `ReportingEvent` rows (resolution time, first-response time, reply time, bot handoff/resolved, reopen) and triggers `ReportingEvents::RollupService`, swallowing rollup failures via `ChatwootExceptionTracker`.
- `app/listeners/csat_survey_listener.rb` — sends CSAT surveys on resolution (`CsatSurveyService`) and records CSAT responses on `message_updated` (`CsatSurveys::ResponseBuilder`).
- `app/listeners/campaign_listener.rb` — builds a campaign-triggered conversation via `Campaigns::CampaignConversationBuilder`.
- `app/listeners/participation_listener.rb` — auto-adds the new assignee as a `conversation_participant` on `assignee_changed`, rescuing race-condition uniqueness/validation errors.
- `app/listeners/installation_webhook_listener.rb` — fires the platform-level `INSTALLATION_EVENTS_WEBHOOK_URL` webhook on `account.created`.
- `app/services/conversations/unread_counts/listener.rb` — `Conversations::UnreadCounts::Listener`, registered in `AsyncDispatcher#listeners`; unusual in that it is **both a subscriber and a re-publisher** — it reacts to `message_created`/`conversation_updated`/etc., and itself calls `Rails.configuration.dispatcher.dispatch(CONVERSATION_UNREAD_COUNT_CHANGED, ...)` to trigger a second event round that `ActionCableListener#conversation_unread_count_changed` and `WebhookListener` consume.
- `enterprise/app/dispatchers/enterprise/async_dispatcher.rb` / `enterprise/sync_dispatcher.rb` — `prepend_mod_with` extension points; append `CaptainListener`, `Captain::ReportingEventListener` (async) and `Captain::ConversationOutcomeEventListener` (sync) to the base listener arrays via `super + [...]`.
- `enterprise/app/listeners/enterprise/action_cable_listener.rb` — `Enterprise::ActionCableListener` module, prepended onto `ActionCableListener`, adds `copilot_message_created` broadcast handling.
- `enterprise/app/listeners/captain_listener.rb` — Captain AI reactions: CSAT tracking on `message_updated`, resolution tracking + contact-notes/FAQ generation on `conversation_resolved`.

## How It Fits Together
Producers call `Rails.configuration.dispatcher.dispatch(EVENT_CONSTANT, Time.zone.now, hash_of_data)` from inside models (`app/models/conversation.rb`, `message.rb`, `contact.rb`, `account.rb`, `inbox.rb`, `notification.rb`, `account_user.rb`, `mention.rb`), from services (`AutoAssignment::AssignmentService`, `Conversations::TypingStatusManager`, `Conversations::UnreadCounts::Notifier`), and from controllers (`Api::V1::Widget::EventsController`, `Api::V1::Accounts::Conversations::ParticipantsController`, public widget conversations controllers). There is no publish-time validation of the event name against `Events::Types` — any string works, and Wisper simply calls the corresponding snake_case method if a listener defines it, silently ignoring the event otherwise.

Downstream, listeners call into essentially every other backend subsystem: [[jobs]] (every non-ActionCable listener side-effect is deferred to a Sidekiq job — `WebhookJob`, `HookJob`, `AgentBots::WebhookJob`, `ActionCableBroadcastJob`, `Captain::Llm::ConversationFaqJob`), [[automation-rules]] (`AutomationRuleListener` is the sole trigger point for rule evaluation), [[notifications]] (`NotificationListener` → `NotificationBuilder`), [[reports]] (`ReportingEventListener` writes the `ReportingEvent` table consumed by reporting queries and `ReportingEvents::RollupService`), [[conversations-services]] and [[messages-services]] (event `data` payloads carry `Conversation`/`Message` model instances produced by those services), and [[models]] (event constants live alongside model callbacks that dispatch them; e.g. `Conversation#notify_conversation_status_changed`-style callback methods). The `Dispatcher` itself is also the mechanism [[captain-ai]] hooks into for CSAT/resolution tracking and memory/FAQ generation, and it is the extension point [[controllers-jobs-listeners]] (enterprise) uses via `prepend_mod_with('AsyncDispatcher')` / `prepend_mod_with('SyncDispatcher')` / `prepend_mod_with('ActionCableListener')`.

## Product Behavior
This subsystem is the plumbing behind several user-guide-documented features rather than a feature itself: real-time dashboard/widget updates (new message, conversation assignment, typing indicators — see the WebSocket connection topic under Advanced features), outgoing Webhooks (Apps and Integrations → Webhooks), Automation rules (Chatwoot 101 → Automation & routing), Agent Bots (Features explained), CSAT surveys, and the round-robin/assignment notification flow. None of these product docs mention the dispatcher/listener architecture directly — it's purely an implementation detail — but tracing "why does X happen when Y happens" in the product almost always leads back to one of these listener methods.

## Notes for AI Agents
- Listener method names are derived automatically from the event string (`.` → `_`); there's no explicit registration table per event, so grep for the exact method name (e.g. `def conversation_resolved`) across `app/listeners` to find every consumer of an event — don't assume one listener = one concern.
- Adding a new event: add the constant to `lib/events/types.rb`, call `Rails.configuration.dispatcher.dispatch(...)` from the producer, then add a same-named method to whichever listener(s) should react — **and register that listener in the right dispatcher's `listeners` array** (`SyncDispatcher` vs `AsyncDispatcher`) or it silently never fires. `Dispatcher#dispatch` always calls both, so an event only reaches a listener if that listener is in the array of the dispatcher whose `publish` path actually runs the method.
- Sync vs. async is a per-listener registration choice, not a per-event choice — the same event (e.g. `conversation_resolved`) can be handled synchronously by one listener and asynchronously by another, depending only on which dispatcher's array it's registered in. `ActionCableListener` and `AgentBotListener` are deliberately sync (low-latency realtime); everything else is async via `EventDispatcherJob` on the `:critical` Sidekiq queue.
- All listeners are Ruby `Singleton`s (`.instance`), so they must be stateless — don't add instance state to a listener class.
- `Conversations::UnreadCounts::Listener` re-dispatches `CONVERSATION_UNREAD_COUNT_CHANGED` from inside its own event handlers — a subscriber acting as a producer. If you're tracing an unread-count broadcast, expect two dispatcher round-trips, not one.
- Enterprise extends listener/dispatcher behavior purely via `prepend_mod_with`/module `super + [...]` — never edit the OSS `listeners` arrays or `ActionCableListener` directly to add Enterprise-only handling; follow the existing `enterprise/app/dispatchers/enterprise/*` and `enterprise/app/listeners/enterprise/*` pattern.
- `HookListener#supported_hook_event?` uses a hardcoded `app_id → [event names]` map — adding a new integration app that should react to events means editing that map, not just adding a method.
- `event.data` is an untyped hash; every listener trusts the producer to have passed the right keys (e.g. `:conversation`, `:message`, `:changed_attributes`), and `BaseListener`'s extractors will raise a `NoMethodError` on `nil` if a producer forgets a key — there's no schema/contract enforcement.
- I sampled `app/listeners` and `app/dispatchers` exhaustively (all 12 + 4 files) plus the Enterprise overlay and `lib/events`; I did not review every listener spec under `spec/listeners` and `spec/enterprise/listeners` line-by-line, only enough to confirm the singleton/registration pattern.
