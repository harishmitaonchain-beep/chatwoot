# Automation Rules Engine

## Purpose

Lets an account define event-triggered rules ("when a conversation is created/updated/resolved/opened, or a message is created, and these conditions match, do these actions") — e.g. auto-assign, add a label, send an auto-reply, notify a team, fire a webhook. Rules can fire immediately on the triggering event, or after a configurable delay (10 minutes to 30 days) measured from a well-defined "episode" anchor (e.g. "conversation stayed pending for N minutes", "customer waited N minutes without an agent reply"). The investigated path is `app/services/automation_rules/*`, but the engine is spread across a model, a listener, two services in that directory, two jobs, and an enterprise overlay — all read in full for this page.

## Key Files & Classes

- `app/models/automation_rule.rb` — the rule record (`conditions`/`actions` jsonb arrays, `event_name`, `execution_delay`, `active`). Validates that condition attribute keys and action names are on its allowlists (`conditions_attributes`, `actions_attributes`, extended by the enterprise module), validates AND/OR query operators, and restricts what delayed rules may key on (see Notes). Includes `Reauthorizable` — repeated invalid-condition errors auto-disable the rule.
- `app/models/automation_rule_pending_execution.rb` — the delayed-execution queue row. Encodes the whole "episode" state machine: `status` enum (`pending/processing/executed/skipped/executing`), `episode_key` (identifies one qualifying stretch of conversation state so a status change or new reply invalidates a stale wait), `due_at`, staleness reclaim, and pause/resume-on-feature-flag logic. Very heavily commented — read this file directly rather than relying on a summary if working on delayed automations.
- `app/listeners/automation_rule_listener.rb` — subscribes to `conversation_updated`, `conversation_created`, `conversation_opened`, `conversation_resolved`, `message_created` (via the app's event dispatcher). Loads active rules for the event/account, runs `ConditionsFilterService`, and either executes immediately or arms a pending execution.
- `app/services/automation_rules/conditions_filter_service.rb` (`AutomationRules::ConditionsFilterService < FilterService`) — turns a rule's `conditions` array into a SQL query against `conversations`/`contacts`/`messages`/`tags` (reusing the same `lib/filters/filter_keys.yml` filter-key definitions as the regular conversation/contact filter UI) and returns whether the current conversation matches. Handles the special `attribute_changed` filter operator separately (against the `changed_attributes` passed in by the listener, not SQL).
- `app/services/automation_rules/condition_validation_service.rb` (`AutomationRules::ConditionValidationService`) — validates that each condition's attribute key/filter operator/query operator are structurally sound (checked at match time, not just at save time — a custom attribute deleted after the rule was saved makes the rule invalid going forward).
- `app/services/automation_rules/action_service.rb` (`AutomationRules::ActionService < ActionService`) — iterates `@rule.actions`, dispatches each via `send(action[:action_name], action[:action_params])`, and rescues+reports (not re-raises) any single action's failure so the rest of the rule's actions still run. Implements automation-specific actions: `send_attachment`, `send_webhook_event`, `send_message`, `add_private_note`, `send_email_to_team`.
- `app/services/action_service.rb` (`ActionService`, the base class, also used directly by `Macros::ExecutionService`) — implements the actions shared with macros: `mute_conversation`, `snooze/resolve/open/pending_conversation`, `change_status`, `change_priority`, `add_label`/`remove_label`, `assign_agent` (including the `last_responding_agent` shortcut), `assign_team`, `remove_assigned_agent`/`remove_assigned_team`, `send_email_transcript`.
- `app/jobs/automation_rules/trigger_pending_executions_job.rb` — the sweep. Purges old terminal rows, pulls due/stale-processing rows (`AutomationRulePendingExecution.sweepable`, capped by an `InstallationConfig` — `AUTOMATION_PENDING_EXECUTIONS_SWEEP_LIMIT`, default 1000), and enqueues one `ProcessPendingExecutionJob` per row. Enqueued by `app/jobs/trigger_scheduled_items_job.rb` alongside the other periodic jobs (campaigns, snoozed-conversation reopen, SLA-style scheduled work).
- `app/jobs/automation_rules/process_pending_execution_job.rb` — per-row worker. Atomically claims the row (`claim!`), re-checks it's not expired/rule-inactive/conversation-gone/episode-moved/no-longer-matching-conditions (skips with a `skip_reason` if so), then runs the same `AutomationRules::ActionService` used for immediate execution.
- `app/controllers/api/v1/accounts/automation_rules_controller.rb` — CRUD + `clone`, admin-only (`AutomationRulePolicy`, `administrator?` on every action). Gates `execution_delay` behind the `delayed_automations` feature flag both on permitted params and on `clone` (refuses to clone a delayed rule into an instant one for a non-flagged account).
- `enterprise/app/models/enterprise/automation_rule.rb` (`Enterprise::AutomationRule`, prepended via `prepend_mod_with('AutomationRule')`) — adds `sla_policy_id` to the allowed condition keys and `add_sla` to the allowed action names.
- `enterprise/app/services/enterprise/action_service.rb` (`Enterprise::ActionService`, mixed into the base `ActionService` via `include_mod_with('ActionService')`) — implements `add_sla`, gated on the `sla` feature flag and only applied if the conversation has no SLA yet and `sla_applicable?`.
- `enterprise/app/models/enterprise/audit/automation_rule.rb` — wires the rule into the `audited` gem (`associated_with: :account`), included via `AutomationRule.include_mod_with('Audit::AutomationRule')`.

Not read in detail: `lib/filters/filter_keys.yml` (the shared filter-key definition file both filter services load) and the base `app/services/filter_service.rb` — sampled only enough to see how `ConditionsFilterService` extends them; treat their exact filter-operator SQL as unverified beyond what's quoted above.

## How It Fits Together

- **Trigger side**: `AutomationRuleListener` is a `BaseListener` subscriber, so it plugs into the same event dispatcher used across the app (see [[events-listeners]]). It guards against automation-caused infinite loops via `performed_by_automation?` (checks `event.data[:performed_by].instance_of?(AutomationRule)`) and skips auto-reply-flagged conversations for the creation/open events.
- **Matching**: `ConditionsFilterService` is a sibling of `Conversations::FilterService` / `Contacts::FilterService` (both under `app/services/`) — all three inherit from `FilterService` and share `lib/filters/filter_keys.yml`, so a new filterable attribute added there becomes available to automation conditions, saved conversation filters, and contact filters together. See [[conversations-services]] and [[contacts-services]].
- **Acting**: `AutomationRules::ActionService` (immediate path) and `ProcessPendingExecutionJob` (delayed path) both bottom out in the same class, so behavior is consistent between the two triggering modes. Actions call into [[messages-services]] (`Messages::MessageBuilder` for `send_message`/`add_private_note`/`send_attachment`), `WebhookJob` for `send_webhook_event`, `TeamNotifications::AutomationNotificationMailer` for `send_email_to_team`, and directly mutate `Conversation` (status, priority, labels, assignee, team) — see [[conversations-services]], [[models]], [[assignment]] for `assign_agent`/`assign_team`.
- **Delayed automations**: gated end-to-end by the `delayed_automations` feature flag (`config/features.yml`) — checked in the listener before arming a row, again in `ProcessPendingExecutionJob` before claiming, and via `AutomationRulePendingExecution.for_enabled_accounts` in the sweep query so one account's disabled flag can't starve others. `Account#resume_delayed_automations` (an `after_update` hook firing when the flag flips back on) calls `AutomationRulePendingExecution.reschedule_paused` to replay anything that came due while paused. See [[jobs]] for the Sidekiq/queue conventions this participates in (`scheduled_jobs` and `medium` queues).
- **Reauthorization**: `AutomationRule` includes the same `Reauthorizable` concern used by channel-auth objects ([[whatsapp]], Facebook/Instagram tokens). Two condition-validation failures in a row auto-disable the rule and email the account admin (`AdministratorNotifications::AccountNotificationMailer#automation_rule_disabled`) via `handle_automation_rule_reauthorization`.
- **Auditing**: enterprise overlay audits rule changes via the `audited` gem, associated with the account — relevant to any audit-log page ([[models-services]] / [[controllers-jobs-listeners]] on the enterprise side).
- **Authorization**: `AutomationRulePolicy` (see [[authorization-policies]]) restricts every controller action to account administrators.

## Product Behavior

The official user guide's "How to use Automation" article and the "Automation and Routing" lesson (Chatwoot 101) cover this feature from the admin's point of view: building rules from event + conditions + actions in the dashboard, alongside auto-assignment/routing as a related concept. This module is the backend that evaluates and executes those rules. The delayed-execution feature (`execution_delay`, pending-execution sweep) is newer product surface — the user guide summary provided for this page doesn't call it out separately, so treat "delay before firing" as an implementation detail not yet confirmed as documented product copy.

## Notes for AI Agents

- **Adding a new action or condition key requires two coordinated edits**: the allowlist on `AutomationRule` (`conditions_attributes` / `actions_attributes`, or the enterprise equivalents) *and* an implementation method on `ActionService`/`AutomationRules::ActionService` (for actions) or an entry in `lib/filters/filter_keys.yml` (for conditions). The model validation (`json_conditions_format`/`json_actions_format`) will reject unsupported keys at save time regardless of what the service can execute.
- **Actions/conditions are jsonb arrays of hashes, dispatched via `send`** (`action[:action_name]`) — there's no polymorphic action-class hierarchy here; every action is just a private method name on `ActionService`/`AutomationRules::ActionService`. A typo or unhandled key would raise `NoMethodError`, but the model validation is what actually prevents that in practice.
- **Per-action failures don't abort the rule**: `AutomationRules::ActionService#perform` rescues `StandardError` per action and reports via `ChatwootExceptionTracker`, then continues to the next action. Don't assume "action 3 failed" implies actions 4+ didn't run.
- **`filter_keys.yml` is read via a relative path** (`File.read('./lib/filters/filter_keys.yml')`) in both `ConditionValidationService` and `ConditionsFilterService` — this assumes the process CWD is Rails root, consistent with how the rest of the app runs, but worth knowing if you ever see this raise `Errno::ENOENT` in an unusual execution context.
- **Delayed-rule condition restrictions are enforced by two separate model validations, not one**: `execution_delay_supported_conditions` forbids `attribute_changed` filters on any delayed rule (the fire-time re-check has no way to reconstruct "what changed"), and `execution_delay_supported_event` additionally restricts conversation-level delayed rules (i.e. `event_name != 'message_created'`) to only `status`/`inbox_id` conditions (`AutomationRule::DELAYED_CONVERSATION_ATTRIBUTES`) — because the delayed episode is keyed on `status_changed_at`, and any other mutable condition could silently span multiple real "episodes" under one key.
- **Episode-key mechanics are the trickiest part of this module** — `AutomationRulePendingExecution` uses different "arm-time" vs. "fire-time" key computations (`arm_episode_key_for` vs `episode_key_for`) because `message_created` dispatches asynchronously and some state (`waiting_since`) may not have settled yet when the listener runs. The class-level comments walk through why (`awaiting_agent:` vs `reply_chase:` vs `status:` key prefixes, `microsecond_stamp` integer-not-float rationale, the `with_lock`-guarded compare-and-write in `rearm_or_advance_episode`). Read the model directly before touching this rather than trusting a paraphrase.
- **`processing` vs `executing` status matters for crash safety**: a row stuck in `processing` (claimed but action not yet started) is safely reclaimed by the next sweep once its lock goes stale (`STALE_PROCESSING_TIMEOUT`, 15 min). A row stuck in `executing` (actions in flight) is *never* reclaimed — the actions are customer-facing (messages/emails/webhooks) and the code deliberately prefers a stranded row over a duplicate send. `AutomationRulePendingExecution.abandoned` exists purely to make that failure mode observable in the sweep's log line, not to recover it.
- **Twitter/tweet conversations are special-cased**: `conversation_a_tweet?` (defined on the base `ActionService`) skips `send_message`/`add_private_note`/`send_attachment` for tweet-type conversations.
- **`Current.executed_by = rule`** is set for the duration of `AutomationRules::ActionService#perform` and reset in an `ensure` block — this is almost certainly how the listener's `performed_by_automation?` loop guard is populated on the resulting events; if you add a new mutation path in an automation action, make sure it still goes through a path that reads `Current.executed_by`/sets `performed_by`, or it risks re-triggering the same rule.
- **Enterprise action/condition extension is via `prepend_mod_with`/`include_mod_with`**, not a hard fork: `AutomationRule.prepend_mod_with('AutomationRule')` and `ActionService.include_mod_with('ActionService')`. Follow this pattern (not editing the OSS files) for any new enterprise-only condition/action, per the repo's enterprise-overlay convention.
