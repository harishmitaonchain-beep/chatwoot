# SMS, Telegram, Line, TikTok, Twitter, Twilio Voice

## Purpose
This module covers the six "smaller" first-party messaging channels that don't get their own dedicated wiki page: SMS (Bandwidth-style generic SMS API and Twilio SMS), Telegram, Line, TikTok Business Messaging, Twitter (legacy tweets + DMs), and Twilio's voice-calling add-on. Each channel follows the same shape as WhatsApp/Facebook/Instagram: an inbound webhook controller/job hands a provider payload to an `Incoming*MessageService`, which resolves a `Contact`/`ContactInbox`/`Conversation` and builds a `Message`; outbound replies go through a `Base::SendOnChannelService` subclass that calls the channel's own client and stamps `source_id` back onto the message. Twilio additionally carries WhatsApp-via-Twilio, CSAT template provisioning, Content Template sync, and (in the Enterprise overlay) full Twilio Voice calling on the same `Channel::TwilioSms` record.

## Key Files & Classes

**SMS** (`app/services/sms/`) — generic SMS API (e.g. Bandwidth), used by `Channel::Sms`
- `incoming_message_service.rb` — builds contact from `From` number (via `TelephoneNumber` gem), creates/reuses conversation, attaches media (skips `.smil`/`.xml`), downloads media with the channel's `api_key`/`api_secret` as HTTP basic auth
- `send_on_sms_service.rb` — thin `Base::SendOnChannelService` subclass, calls `channel.send_message`
- `delivery_status_service.rb` — maps Bandwidth `message-delivered`/`message-failed` webhook types to Chatwoot message status
- `oneoff_sms_campaign_service.rb` — iterates contacts tagged with a campaign's audience labels, renders the message via `Liquid::CampaignTemplateService`, sends via `channel.send_text_message`, rescues per-contact and logs (does not abort the whole campaign)

**Telegram** (`app/services/telegram/`)
- `incoming_message_service.rb` — handles both regular bot messages and Telegram *Business* messages (`business_message` payloads get remapped onto `message` via `transform_business_message!`); ignores group chats (`private_message?`); for business chats, distinguishes messages the *linked human agent* sent from their own Telegram client (`business_message_outgoing?`, compares `chat.id` vs `from.id`) and stores those as outgoing with no `sender`; attaches location, contact-card, and file attachments
- `param_helpers.rb` (`Telegram::ParamHelpers`, mixed into the above) — all the payload-shape branching (callback_query vs message vs business_message)
- `send_on_telegram_service.rb` — thin, calls `channel.send_message_on_telegram(message)`
- `send_attachments_service.rb` — groups attachments into media-group (photo/video), audio-group, and per-file documents; media/audio go by URL (`sendMediaGroup`), documents are uploaded as multipart (Telegram only accepts PDF/ZIP/GIF by URL); writes attachments to a temp file under `tmp/uploads/telegram-<message_id>` to preserve the original filename before uploading
- `update_message_service.rb` — handles Telegram's `edited_message`/`edited_business_message` webhook, finds the existing Chatwoot message by `source_id` and updates its content

**Line** (`app/services/line/`)
- `incoming_message_service.rb` — iterates `params[:events]`, fetches the sender's LINE profile via `inbox.channel.client.get_profile` for name/avatar, renders stickers as a markdown image referencing LINE's public sticker CDN (deliberately not downloading/storing the sticker asset itself, to respect creator ownership — see the comment in the file), downloads other media via `client.get_message_content`
- `send_on_line_service.rb` — builds LINE's `push_message` payload (text, image/video attachments, or a Flex "input_select" button message for structured replies), explicitly uses `attachment.file_url` (permanent) over `download_url` (5-minute-expiring signed URL) since LINE's client lazy-loads images; updates message status to delivered/failed based on the HTTP response

**TikTok** (`app/services/tiktok/`) — TikTok Business Messaging API
- `auth_client.rb` — OAuth2 (`OAuth2::Client`) authorize-URL builder plus raw HTTParty calls for short-term token exchange/refresh and webhook-callback registration; reads `TIKTOK_APP_ID`/`TIKTOK_APP_SECRET` via `GlobalConfigService`
- `client.rb` (`Tiktok::Client`) — per-request API wrapper (business account details, media upload/download, send text/image message, `image_send_capable?` capability check); comment says "Always use `Tiktok::TokenService` to get a valid access token" rather than constructing this directly
- `token_service.rb` — refreshes the channel's short-lived access token when near expiry, using a Redis lock (`Redis::LockManager`, key from `Redis::Alfred::TIKTOK_REFRESH_TOKEN_MUTEX`) so concurrent requests don't double-refresh; if both access and refresh tokens are expired, calls `channel.prompt_reauthorization!`
- `message_service.rb` — shared inbound/outbound message builder; decides incoming vs outgoing by comparing `channel.business_id` to the payload's `to_user.id`; for outgoing (agent-sent-via-TikTok-app echoes) it dedupes on `source_id` before creating; supports text, image, and `share_post` (embed) message types, flags unsupported types via `is_unsupported` content attribute
- `messaging_helpers.rb` (`Tiktok::MessagingHelpers`, mixed into `MessageService`/`ReadStatusService`) — contact/conversation resolution, and `tiktok_conversation_capabilities` which probes `image_send_capable?` once and caches the result on `conversation.additional_attributes['tiktok_capabilities']`
- `send_on_tiktok_service.rb` — validates before sending: TikTok can't mix text+attachment or send multiple attachments in one message, only JPEG/PNG under 3 MB, and only if the conversation's cached capability flag allows image sending; sets message status to delivered/failed explicitly (no async delivery webhook is relied on for the happy path)
- `read_status_service.rb` — turns TikTok's read-receipt webhook into a `Conversations::UpdateMessageStatusJob`, ignoring the business account's own outbound read receipts

**Twilio** (`app/services/twilio/`) — powers `Channel::TwilioSms`, which serves both plain SMS and WhatsApp-via-Twilio (`enum medium: { sms: 0, whatsapp: 1 }`)
- `incoming_message_service.rb` — resolves the channel by `MessagingServiceSid` or by `(AccountSid, To)`; for WhatsApp-via-Twilio it delegates identity resolution to `WhatsappIdentifierHelper`/`Whatsapp::IdentifierSyncService` (Twilio can send a phone-shaped `From` like `whatsapp:+E164` or a BSUID-only identifier); logs a warning (not silent) when no channel matches
- `whatsapp_identifier_helper.rb` — the BSUID-vs-phone-number disambiguation logic for Twilio WhatsApp specifically; builds an ordered, deduped list of candidate source ids (phone-derived, `ExternalUserId`, `ParentExternalUserId`) and hands them to `ContactInboxSourceIdResolver`
- `referral_params_helper.rb` — pulls Meta "click to WhatsApp ad" referral fields (`ReferralSourceId`, `ReferralCtwaClid`, etc.) off the Twilio webhook params into `message.content_attributes[:referral]`
- `send_on_twilio_service.rb` — supports plain body+media sends, Twilio Content Template sends (looks up `template_params`/`content_sid` via `Twilio::TemplateProcessorService`), and a public `send_csat_template_message` entry point used by the CSAT survey flow; on any `Twilio::REST::TwilioError`/`RestError` it marks the message failed with the provider's error message rather than raising
- `delivery_status_service.rb` — maps Twilio's `sent/delivered/read/failed/undelivered` statuses (undelivered → `failed`) onto the message, with an i18n fallback error string when Twilio gives an error code but no message text
- `webhook_setup_service.rb` — points either the Messaging Service or the phone number's `sms_url` at Chatwoot's callback endpoint, called on inbox creation/update
- `template_sync_service.rb` — pulls the account's approved Twilio Content Templates (`client.content.v1.content_and_approvals`) and caches them denormalized on `channel.content_templates`, deriving a template type (text/media/quick_reply/call_to_action/catalog) and a heuristic category from the friendly name
- `template_processor_service.rb` — converts Chatwoot's outgoing template parameters (either flat `processed_params` or WhatsApp-Cloud-API-shaped `parameters`) into Twilio's numbered `content_variables` hash, handling media-header vs body components separately
- `csat_template_service.rb` / `csat_template_api_client.rb` — creates/deletes/status-checks a Twilio Content Template used for CSAT surveys (`twilio/call-to-action` type with a survey-response URL button), submits it for WhatsApp template approval, and generates non-colliding template names via `CsatTemplateNameService`

**Twitter** (`app/services/twitter/`) — legacy Twitter (X) Account Activity API: tweets + Direct Messages
- `webhooks_base_service.rb` — shared helpers: resolves `@inbox` from the webhook's `for_user_id` via `Channel::TwitterProfile`, and `find_or_create_contact` (creates the contact via `inbox.channel.create_contact_inbox` and kicks off `Avatar::AvatarFromUrlJob`)
- `tweet_parser_service.rb` — dedupes by `source_id`, ignores tweets when the user has blocked the account or when replies are disabled (`tweets_enabled?`), threads tweet-reply conversations together by matching `additional_attributes->>'tweet_id'` (the *root* tweet of the thread), falling back to walking to the existing message's conversation if the id-based lookup misses
- `direct_message_parser_service.rb` — ignores DM echoes that originated from Chatwoot itself (compares `source_app_id` to `ENV['TWITTER_APP_ID']`), keeps all DMs for a contact in a single `type: 'direct_message'` conversation, downloads image attachments via an `OAuth::AccessToken` built from the channel's stored Twitter tokens
- `send_on_twitter_service.rb` — branches on `conversation.additional_attributes['type']` (`tweet` vs DM) using the `Twitty` gem; tweet replies prefix the reply with `@screen_name`
- `webhook_subscribe_service.rb` — Twitter's Account Activity API only allows one webhook URL per environment, so this unregisters whatever's currently registered before registering Chatwoot's callback URL, then ensures a subscription exists

**Cross-cutting**
- `app/services/base/send_on_channel_service.rb` — the shared base class for every outbound send service across all channels (including WhatsApp/Facebook/etc, not just this module): validates the message belongs to the right channel type, skips private notes, skips messages that echoed back in from the channel itself (`message.source_id.present?`), and skips `content_type == 'voice_call'` bubbles (call status indicators, not real deliverable messages)
- `app/models/channel/twilio_sms.rb` — carries `voice_enabled`/`twiml_app_sid`/`api_key_sid`/`api_key_secret` columns even in OSS, but the OSS `client`/`send_message` only use `auth_token`-based auth for messaging
- **Twilio Voice is an Enterprise-only feature**, not present under `app/services/twilio/`. It lives in `enterprise/` and is layered onto the same `Channel::TwilioSms` model via `prepend_mod_with('Channel::TwilioSms')`: `enterprise/app/models/enterprise/channel/twilio_sms.rb` adds TwiML app provisioning (`before_validation` hooks that call `Twilio::VoiceWebhookSetupService` when `voice_enabled` turns on) and teardown (`enterprise/app/services/twilio/voice_teardown_service.rb`, which deletes the TwiML app and clears the number's voice webhooks on disable); `enterprise/app/controllers/twilio/voice_controller.rb` handles the actual TwiML call/status webhooks; `enterprise/app/services/voice/provider/twilio/token_service.rb` mints short-lived Twilio Voice SDK access tokens (JWT, `VoiceGrant`) for agents to make/receive browser calls

## How It Fits Together
- All six channels use `ContactInboxWithContactBuilder` (or, for Twilio, `ContactInboxSourceIdResolver` via `WhatsappIdentifierHelper`) to resolve/create the `Contact`/`ContactInbox`, and all follow the same `lock_to_single_conversation` branch (reuse last conversation vs. open a fresh one only if the last is resolved) seen throughout the channel layer — see [[models]] for `Contact`/`ContactInbox`/`Conversation`.
- Inbound webhooks arrive via `app/controllers/webhooks/{sms,telegram,line,tiktok}_controller.rb` and `app/controllers/twilio/callback_controller.rb`, are queued as jobs (`Webhooks::SmsEventsJob`, `Webhooks::TelegramEventsJob`, `Webhooks::LineEventsJob`, `Webhooks::TiktokEventsJob`, `Webhooks::TwilioEventsJob`), and those jobs instantiate the `*IncomingMessageService` classes documented above. Twitter is routed differently — through `Api::V1::WebhooksController#twitter_events` → `Webhooks::Twitter` — which then calls `Twitter::TweetParserService`/`Twitter::DirectMessageParserService`.
- Outbound sends go through the standard message-creation → `SendReplyJob` (see [[jobs]] and [[messages-services]]) path, which dispatches to the appropriate `Base::SendOnChannelService` subclass based on `inbox.channel_type`.
- SMS and Twilio SMS one-off campaigns (`Sms::OneoffSmsCampaignService`, `Twilio::OneoffSmsCampaignService`) are invoked from the campaigns feature; see [[jobs]] for the scheduling side.
- CSAT template provisioning (`Twilio::CsatTemplateService`) ties into the survey/CSAT feature — the generated Content Template's button links to `#{base_url}/survey/responses/{{1}}`.
- Delivery-status webhooks (`Sms::DeliveryStatusService`, `Twilio::DeliveryStatusService`) update `Message#status`/`external_error`, which flows into the conversation UI's delivery ticks — same pattern used by WhatsApp (see [[whatsapp]]).
- TikTok's `image_send_capable?` capability is fetched once per conversation and cached in `additional_attributes`, then enforced client-side in `Tiktok::SendOnTiktokService` before every send — an unusual "ask-then-cache-then-gate" pattern not seen in the other channels here.
- Enterprise Twilio Voice reuses the same `Channel::TwilioSms` row and Twilio account credentials as SMS/WhatsApp messaging (`api_key_sid`/`api_key_secret` for Voice Grant JWTs, `auth_token` for the REST client fallback), so a single Twilio inbox can carry messaging and calling simultaneously once `voice_enabled` is true.

## Product Behavior
- The user guide's "Other channels" setup section covers Telegram (bot token), Line (channel secret/access token), SMS, and TikTok as distinct channel-creation flows in inbox settings — each maps 1:1 to the `Channel::*` model and its inbound/outbound service pair documented above.
- The "Voice Channels" guide category's Twilio Voice topic corresponds to the Enterprise `voice_enabled` toggle on a Twilio inbox: enabling it provisions a TwiML Application against the inbox's phone number so agents can place/receive calls from the dashboard, using the same phone number already used for Twilio SMS/WhatsApp messaging.
- Twitter/X is listed in "Other channels" for historical reasons but the code shows it depends on Twitter's now-restricted Account Activity API (webhook subscription with a single URL per environment) — worth treating as a legacy/lower-confidence integration when advising users, since Twitter/X has significantly changed its API access tiers since this code was written.
- LINE's sticker-as-markdown-image behavior and TikTok's text/attachment mutual-exclusivity are both real product-visible limitations baked into the backend, not just UI restrictions — reproducing them requires respecting the same constraints in any client code.

## Notes for AI Agents
- Every `*IncomingMessageService` in this module (SMS, Telegram, Line, Twilio) repeats the same `set_conversation` logic (reuse last conversation if `lock_to_single_conversation`, else find/create based on `resolved` status) almost verbatim — if you're fixing a bug in this logic for one channel, check whether the same bug exists in the sibling implementations here (and in WhatsApp/Facebook, see [[whatsapp]] / [[facebook-instagram]]) rather than assuming it's channel-specific.
- Twilio's `IncomingMessageService` intentionally logs (`Rails.logger.warn`) rather than raising when no channel is found for a webhook payload — mirrors a documented gotcha where inbound messages can silently vanish if the channel lookup fails; don't "fix" this into a silent no-op without also fixing the logging, and don't assume webhook 200s mean the message was processed.
- `Twilio::WhatsappIdentifierHelper` is the load-bearing place for the WhatsApp-via-Twilio BSUID vs. phone-number identity problem; this is the Twilio-specific counterpart to `Whatsapp::PhoneNumberNormalizationService`/`Whatsapp::IdentifierSyncService` used by the native WhatsApp Cloud API channel (see [[whatsapp]] and the maintainer's own notes on WhatsApp coexistence duplicate-conversation bugs) — don't assume Twilio WhatsApp and Cloud API WhatsApp share identity-resolution code; they don't, they call into the same `Whatsapp::*` services from two different helper modules.
- `Base::SendOnChannelService#invalid_message?` explicitly excludes `content_type == 'voice_call'` bubbles from being sent to any channel — if you add a new channel's send service and don't inherit from this base class, you must reimplement that guard yourself.
- TikTok's `Tiktok::Client` is explicitly documented (in its own top comment) to require going through `Tiktok::TokenService` for the access token rather than reading `channel.access_token` directly — bypassing this risks using an expired token, since refresh is lazy and lock-guarded.
- Twilio Voice is entirely absent from OSS `app/services/twilio/` — an AI agent asked to "find the Twilio calling code" starting only in that directory will conclude it doesn't exist; it's under `enterprise/`, wired onto the same model via `prepend_mod_with`, following the standard Enterprise override convention (see `enterprise/app/models/enterprise/channel/twilio_sms.rb`).
- `Telegram::IncomingMessageService` has an explicit `TODO` acknowledging that Telegram Business "read" receipts aren't being sent back to Telegram, meaning Telegram Business contacts may see their messages as perpetually unread on their end even after an agent replies in Chatwoot — a known, not-yet-fixed gap if a customer reports this.
- Line's `send_on_line_service.rb` deliberately prefers `attachment.file_url` (permanent) over `download_url` (5-minute signed URL) — if you see LINE image messages that fail to load client-side, check whether this preference was accidentally reverted before looking elsewhere.
